# C 1.70 整包更新的确认页与摘要启动

分析固件并执行原始菜单对象后，已将普通整包更新路径的摘要认证启动
定位到执行选项之后。候选收集、版本读取、确认页初始化及返回选项
均未进入该认证路径。因此，到最终 Yes/No 页选 No，不能用来触发
本次更新的 K8 生成。

这回答了已追踪 C 1.70 路径的先后顺序；尚未证明完整菜单返回、
物理 USB 重连或整个 PTP 会话生命周期一定保留上下文。
它也不提供“选 Yes、校验后取消”的实机流程。

## 原始确认页，而非有名服务包装

原始菜单经 `0x1063CB3A` 读取版本，经 `0x1063CC1C` 查询资格，
执行更新经 `0x1063CB3E`。此前观察的 `0x10767048 / 0x10767092`
是另一组有名服务包装，不能作为菜单查询必经入口。

从原始初始化数据恢复的类型 2 菜单对象，确认页 ID 为 `0x2D8`，
地址为 `0xB2BBEF2C`。它的回调表 `0x1096A858` 指向初始化函数
`0x1070261E`。选择行使用对象 `+0x16` 与 `+0x18` 的和。
属性记录指向原始行数据和事件表指针数组：

| 行 | 控件标识 | 事件表 | 事件 `0x27D` 的回调 | 行为 |
| --- | --- | --- | --- | --- |
| 0 | `0x20BE` | `0x1180C208` | `0x1070297C` | 执行更新，对应 Yes |
| 1 | `0x20BF` | `0x1180C3F8` | `0x1063AEC2` | 返回上一层，对应 No |

原始分派函数 `0x1044E636` 按所选行取出事件表，经
`0x10637CC0` 查找事件后调用原始回调。本轮没有用合成回调表
替代这些绑定。执行确认页初始化后，原始逻辑默认选中第 1 行。
显示树未构建，故这不是菜单画面渲染验证。

## 认证事件在执行选项之后

[离线对照程序](../../tools/menu_update_confirmation_probe.py)使用本地
原厂 C 1.70 更新包，SHA-256 为
`fc0e94f57500a1f0e287c6b9a036c81a5ffceccb8432a377d645b3fa35a19b6a`。
原始目录收集得到一个整包候选，原始选择函数选择槽 13，版本查询
得到一个整包版本条目。已装版本为明确的合成 01.70，目标版本由
原始包产生，也是 01.70，与用户反馈的同版本确认相对应。

候选收集、选择、版本查询和确认页初始化期间，非零合成校验上下文
保持不变；认证任务 `0x103F6938`、整包认证 `0x1039C638`、
摘要入口 `0x103AFE82` 和清零入口 `0x103AED1C` 均未执行。
这些入口设为拒绝边界，意外进入即使对照失败。

第 0 行经原始分派进入以下链条：

```text
0x1044E636  原始菜单事件分派
0x1070297C  执行选项回调
0x1063CB3E  菜单执行 API
0x103F67A4  更新入口
0x103F6474  更新控制器
0x103610CC  将向 0xB1887D24 投递事件 0x10
```

本轮在最后一个入口停下，核对事件对象和掩码，没有真正投递事件，
也没有执行认证任务或编程。原始任务 `0x103F6938` 对整包调用
`0x1039C638` 的绑定及认证成功后同一控制调用进入更新准备，
已在[执行阶段分析](ptp_service.md#菜单时序的已知部分与未验证部分)
记录。两者共同把本次菜单路径的认证启动置于执行选择之后。

执行选项中的显示、拍摄状态和任务就绪由环境提供，不能据此宣称
QEMU 已完成真实菜单刷机，或证明相机上存在认证后的可取消窗口。

## 返回选项目前证明到哪里

第 1 行的回调 `0x1063AEC2` 直接返回；原始分派器返回导航结果
`0x43B`，没有调用执行选项。再执行原始页退出分派 `0x1061DB80`，
它调用该页的 `0x1070271C`，同样直接返回。上述执行保留非零
合成上下文，没有观察到其原始写入。

这证明返回回调及该页退出回调自身不清空上下文。后续通用导航的
新增覆盖和仍未执行的边界如下，不能把局部保留扩展成完整流程保留。

### 通用导航、资源退出及目标页初始化

同一离线程序新增 `no_navigation` 对照。它提供类型 2 的三层合成
菜单栈 `0x1 → 0x2D7 → 0x2D8`，栈内对象、属性和回调来自原始
初始化数据；栈层次是运行环境输入，并非实机捕获。

原始结果处理 `0x1063837C` 接收 `0x43B`，使用原始栈查询选择目标，
进入 `0x1063A7A6`。该导航控制器执行确认页退出及
`0x10639E20` 资源清理。与先前空显示树对照不同，这次确认页的
显示资源指针为非零；原始清理调用环境提供的释放端点后，确实将
对象 `+0x24` 清为零。

原始 `0x1063C260` 将栈深度从 3 减至 2，当前页变为 `0x2D7`。
随后执行该目标页的初始化 `0x107017A0`、回调 `0x10701812 / 0x10701820`
及 `0x10701D8A`。这些步骤均未写入校验上下文，也未进入认证或编程。

对照停在 `0x1063AA28`，下一步才会调用父页初始化包装
`0x1063A54E`。因此报告仍明确保留
`generic_page_return_completed: false`：父页初始化、异步显示工作、
USB 重连及完整 PTP 生命周期尚未证明。

显示分配、控件填充、刷新调度、参数与拍摄状态为合成环境；
事件 `0xB181B3A8 / 0x8` 被截获，等待完成位由环境提供。
释放端点同样由环境提供，尚未验证真实释放器或显示任务是否影响
上下文。完整替代端点清单随 JSON 保存，不能将这些未运行端点算作
原始执行覆盖。新增结论仅限：在这些输入下，原始导航控制器、
确认页资源退出及目标页初始化保留非零合成上下文。

## 修正旧菜单观察结论

旧菜单扫页仅观察两个有名服务包装；它们不在上述原始菜单查询的
直接路径上。旧运行“未命中”不能证明条目派发没有发生，也不能
单凭实验资源仅有头部就把原因归为缺少派发数据。
本轮已在 master 初始化数据中找到原始菜单对象、选项和事件表。

`menu_fwupdate_probe.py` 的观察点已改为实际菜单查询 API
`0x1063CC1C / 0x1063CB3A`，并在报告中记录两处地址。
本轮没有重新进行整机扫页；旧报告保留为历史记录，不作为新观察点
已执行的证据。原生菜单自然导航、完整显示与存储任务的联动仍待验证。

在 `tools` 目录可以执行离线对照，输出为分析元数据，不含固件字节：

```bash
python ./menu_update_confirmation_probe.py --master ../../../Temporary/2610/07/Z_72/eg1840_mas_01700.bin --package ../../../Temporary/2610/24/z72/Z7_2_0170.bin --output ../.local/menu-confirmation.json
```

结果见[确认页分派记录](../../artifacts/ptp_service/menu_confirmation.json)。
未连接或操作实机；未编译或修改设备模型。
