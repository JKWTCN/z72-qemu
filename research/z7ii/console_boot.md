# 字符接口与库初始化边界

启动任务调用原厂 `0x294`，传入基址 `0x2C090000`、端口索引 0 和模式参数 1，
再调用 ARM 初始化 `0x180`。以下代码位置均为 C 1.70 EG 文件偏移，运行时加
`0x10020000`。master 与 slave 的这段指令相同，保存参数的 RAM 地址各属其角色。

## 原厂配置与发送

| 端口偏移 | 宽度 | 本次原厂写入顺序 |
| --- | --- | --- |
| `0` | 字节 | `1` |
| `1` | 字节 | `0`、`0x80`、`0x81` |
| `2` | 字节 | `0` |
| `3` | 字节 | `0x80` |
| `4` | 半字 | 字符数据；初始化不写 |
| `6` | 半字 | `0x363` |
| `0xC` | 半字 | `0`、`0xC`、`0x405` |

共 10 次初始化写入。参数 1 选择最后的 `0x405`，随后原厂代码设置偏移 1 的位 0，
恢复 R4/R5 和调用者栈后正常返回 `0x2A8`。字段的完整硬件命名和波特率仍待确认。

原厂发送例程 `0x1EC` 读取基址／端口参数，在 `0x1FC` 轮询偏移 3 的位 1，
再用半字写偏移 4。另一条参数路径先读回数据，用 `BFI` 替换低 9 位。
这些指令支持字符发送接口的判断，不表示兼容某个标准 UART 寄存器布局。

## 有限模型

`nikon-z72-uart` 映射单个 16 字节端口，仅接受上表的宽度和地址。
配置字段保存原厂写入，偏移 3 的 TX-ready 位 1 由设备提供；当前同步发送模型
始终可接受下一个字符。数据半字完整保存在锁存字段中，低字节发送到可选 QEMU
字符后端。没有后端时正常完成发送。洞、字访问和错误宽度产生数据异常。
32 位写保持整次事务，在拆分为半字或发送字符之前拒绝；非法访问不能误发字符。
复位清零配置；设备状态格式为版本 1，完整机器迁移未验证。
接收、FIFO、UART 中断、字符时间和控制位的完整硬件语义均未实现。

可选日志连接方式：

```sh
-chardev file,id=z72-console,path=console.txt -global nikon-z72-uart.chardev=z72-console
```

`-global nikon-z72-uart.enabled=off` 关闭接口，用于保留原厂首字节写异常负对照。
此时 DFAR 为 `0x2C090001`，DFSR 为 `0x1808`；此前未映射设备的历史记录为 `0x808`。

## 原厂执行与下一边界

2026-10-10，两个角色各通过原厂和关闭接口场景。双核执行原厂复位、就绪发布和
任务调度；原厂场景逐条检查 10 次配置写入、读回、最终寄存器及调用者栈／寄存器
恢复，没有写入 PC、返回值、固件指令、页表或握手字。

之后的 Thumb 库初始化写入配置字 `0x04280030`，触发数据异常：

| 角色 | 原厂写指令 | 写入值 |
| --- | --- | --- |
| master | `0x1E0EF0` | `0x410` |
| slave | `0x33BD4` | `0xCB7` |

DFAR 为 `0x04280030`，DFSR 为 `0x808`。随后代码会遍历 12 组、每组 5 个配置值，
目标基址为 `0x04282000`；master 还继续修改其他配置字段。这组接口尚未接入。
本阶段原厂流程尚未输出日志文本。合成检查实际发送 `Z72\r\n` 字节、验证寄存器
宽度、复位和每个角色的 10 个非法访问场景。它证明模型发送功能，不证明原厂日志。
LCD、菜单、输入和双处理器协作仍待实现。

## 复现

```sh
python tests/test_uart.py --qemu .build/build/qemu-system-arm --destination .local/uart-run
python tools/console_boot_probe.py --master /path/to/eg1840_mas_01700.bin --slave /path/to/eg1840_sla_01700.bin --qemu .build/build/qemu-system-arm --destination .local/console-run
```

输出目录必须不存在，原厂输入先执行身份和结构检查。
