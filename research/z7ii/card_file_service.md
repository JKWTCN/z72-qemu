# 存储卡文件服务与跨引擎复制

## SD 初始化能力窗口

带卡启动的读取观察确认，`0x1008B75A` 对 `0x2A810150` 执行
32 位读取。初始化 `0x100C6644` 经 `0x100C65F0` 连续读取
偏移 `0x150`、`0x154`、`0x158`、`0x15C`，保存到运行时
`0xC144D5C0` 起的四个字。后续 `0x100C7D5A` 使用首字的低四位
和第 4..7 位；这与公开 UHS-II 能力结构的 DAP/GAP 字段及四字布局
相符，因此按 UHS-II 能力快照解释。字段定义见
[Linux UHS-II 主控头文件](https://raw.githubusercontent.com/torvalds/linux/master/drivers/mmc/host/sdhci-uhs2.h)。

当前通用主控实现传统 SD 通路，新增能力窗口固定返回零，不宣告
UHS-II 通路。窗口只接受四个对齐的 32 位读取，不接受写入，
也不提供就绪或完成位。零值是实验配置，不能作为真机能力值。
补齐后，带卡原始启动已完成主控时钟配置，四核异常状态均为零。

## 资源 9 协议

原厂文件服务通过资源 9 在两个引擎间传递请求。队列帧头为
操作号 `u32`、资源号 `u8`、序号 `u8`、载荷长度 `u16`，均按小端存储。

| 请求 / 回复操作 | 本路径的用途 |
| --- | --- |
| 13 / 14 | 打开文件，返回句柄或负错误值 |
| 15 / 16 | 普通文件读取，返回状态及实际字节数 |
| 19 / 20 | 请求主引擎复制数据，并确认复制结果 |
| 3 / 4 | 预读通路；需要已有预读上下文，不能替代普通读取 |

普通读取的静态发送链为 master 成员偏移 `0x4B3D82` →
`0x59EA28` 的文件系统操作 12 → `0x59D66C` 的资源 9、操作 15。
操作 3 的诊断输入返回过 `0x90000003`，对应未建立的预读上下文；
它不是更新包摘要拒绝。

普通读取不是直接回复文件字节。从引擎先读取卡内容，再发送操作 19，
包含主引擎目标地址、从引擎源地址、按 8 字节对齐的复制长度。
主引擎原始分派器 `0x105BDF84` 执行数据复制，发送操作 20；
随后从引擎才准备操作 16 的读取回复。

## 共享视图与内存传输

一次 20 字节文本文件读取中，从引擎源缓冲区 `0xC5B9F300` 已包含
正确内容。主引擎原始地址转换得到 `0x45B9F300`，但先前模型只接通
从引擎访问主引擎的方向。现在主引擎 `0x40000000..0x4FFFFFFF`
映射到从引擎 `0xC0000000..0xCFFFFFFF` 的已有存储，保留空洞和
原有高优先级窗口。主引擎自己的 `0xC5B9F300` 等帧池地址不变。
两个方向的读写、所属存储更新、本地隔离和空洞异常均有定向检查。

原始文件复制通过 `0x105BC398` → `0x1038A222` 提交内存传输。
观察到通道 1 使用模式 `0x10`，行宽和源、目标间距均按字节计数。
原模型将此模式判为不支持，复制确认返回 -1；即使文件服务随后返回
状态 0 和请求长度，目标内容仍为零。因此必须同时核对复制确认、
实际长度和内容摘要，不能只检查读取返回码。

内存设备现支持模式 `0x10` 的字节复制，保留模式 0、填充模式 1
及地址范围、间距、只读目标、溢出和不支持格式的拒绝检查。

## 验证边界

`tools/filesystem_peer_probe.py` 使用明确构造的队列输入，执行原始
接收任务、文件操作、主引擎复制分派及复制确认。打开回复由实验
客户端在回调入口消费并返回原调度器；最终读取回复在原始发送入口
观察，尚未交给 SDK 消费。没有执行 SDK 发送端或菜单调用。

本地参考文件只用于比较前 64 字节，不向运行时提供文件内容。
诊断缓冲区原值须为零，结束后恢复；卡写入隔离在临时覆盖层中。
重新编译后的原始文件服务已读取 20 字节文本文件，以及
48,494,024 字节原厂升级文件的前 64 字节。两项复制确认、读取状态
均为 0，长度和 SHA-256 与本地参考一致，四核异常状态为零。
修复前后的状态、输入身份及构建摘要见
[原始文件读取验证](../../artifacts/native_peer_file_read/report.json)。
该验证仍不证明整包读取、更新文件自动选择、整包认证、烧写或复位后
启动完成。这些条件需要通过完整原厂调用路径继续验证。
