# 存储卡文件服务与跨引擎复制

## SD 初始化能力窗口

带卡启动的读取观察确认，`0x1008B75A` 对 `0x2A810150` 执行
32 位读取。初始化 `0x100C6644` 经 `0x100C65F0` 连续读取
偏移 `0x150`、`0x154`、`0x158`、`0x15C`，保存到运行时
`0xC144D5C0` 起的四个字。后续 `0x100C7D5A` 使用首字的低四位
和第 4..7 位；这与公开 UHS-II 能力结构的 DAP/GAP 字段及四字布局
相符，因此按 UHS-II 能力快照解释。字段定义见
[Linux UHS-II 主控头文件](https://raw.githubusercontent.com/torvalds/linux/master/drivers/mmc/host/sdhci-uhs2.h)。

当前通用主控实现传统 SD 通路，新增能力窗口固定返回零，不宣告
UHS-II 通路。窗口只接受四个对齐的 32 位读取，不接受写入，
也不提供就绪或完成位。零值是实验配置，不能作为真机能力值。
补齐后，带卡原始启动已完成主控时钟配置，四核异常状态均为零。

## 资源 9 协议

原厂文件服务通过资源 9 在两个引擎间传递请求。队列帧头为
操作号 `u32`、资源号 `u8`、序号 `u8`、载荷长度 `u16`，均按小端存储。

| 请求 / 回复操作 | 本路径的用途 |
| --- | --- |
| 13 / 14 | 打开文件，返回句柄或负错误值 |
| 15 / 16 | 普通文件读取，返回状态及实际字节数 |
| 19 / 20 | 请求主引擎复制数据，并确认复制结果 |
| 3 / 4 | 预读通路；需要已有预读上下文，不能替代普通读取 |

普通读取的静态发送链为 master 成员偏移 `0x4B3D82` →
`0x59EA28` 的文件系统操作 12 → `0x59D66C` 的资源 9、操作 15。
操作 3 的诊断输入返回过 `0x90000003`，对应未建立的预读上下文；
它不是更新包摘要拒绝。

普通读取不是直接回复文件字节。从引擎先读取卡内容，再发送操作 19，
包含主引擎目标地址、从引擎源地址、按 8 字节对齐的复制长度。
主引擎原始分派器 `0x105BDF84` 执行数据复制，发送操作 20；
随后从引擎才准备操作 16 的读取回复。

## 共享视图与内存传输

一次 20 字节文本文件读取中，从引擎源缓冲区 `0xC5B9F300` 已包含
正确内容。主引擎原始地址转换得到 `0x45B9F300`，但先前模型只接通
从引擎访问主引擎的方向。现在主引擎 `0x40000000..0x4FFFFFFF`
映射到从引擎 `0xC0000000..0xCFFFFFFF` 的已有存储，保留空洞和
原有高优先级窗口。主引擎自己的 `0xC5B9F300` 等帧池地址不变。
两个方向的读写、所属存储更新、本地隔离和空洞异常均有定向检查。

原始文件复制通过 `0x105BC398` → `0x1038A222` 提交内存传输。
观察到通道 1 使用模式 `0x10`，行宽和源、目标间距均按字节计数。
原模型将此模式判为不支持，复制确认返回 -1；即使文件服务随后返回
状态 0 和请求长度，目标内容仍为零。因此必须同时核对复制确认、
实际长度和内容摘要，不能只检查读取返回码。

内存设备现支持模式 `0x10` 的字节复制，保留模式 0、填充模式 1
及地址范围、间距、只读目标、溢出和不支持格式的拒绝检查。

## 验证边界

`tools/filesystem_peer_probe.py` 使用明确构造的队列输入，执行原始
接收任务、文件操作、主引擎复制分派及复制确认。打开回复由实验
客户端在回调入口消费并返回原调度器；最终读取回复在原始发送入口
观察，尚未交给 SDK 消费。没有执行 SDK 发送端或菜单调用。

本地参考文件只用于比较前 64 字节，不向运行时提供文件内容。
诊断缓冲区原值须为零，结束后恢复；卡写入隔离在临时覆盖层中。
重新编译后的原始文件服务已读取 20 字节文本文件，以及
48,494,024 字节原厂升级文件的前 64 字节。两项复制确认、读取状态
均为 0，长度和 SHA-256 与本地参考一致，四核异常状态为零。
修复前后的状态、输入身份及构建摘要见
[原始文件读取验证](../../artifacts/native_peer_file_read/report.json)。
该验证仍不证明整包读取、更新文件自动选择、整包认证、烧写或复位后
启动完成。这些条件需要通过完整原厂调用路径继续验证。

## 原生 SDK 整文件读取

`tools/sdk_file_probe.py` 在原始资源 8 的任务栈上运行临时诊断调用体，
调用原始 SDK 初始化、打开、循环读取和关闭。SDK 发送端、资源 9
文件任务、跨引擎复制、回复回调及事件等待均由固件执行，没有主机
构造的文件服务回复，也不跳过回复回调。诊断调用体替换的是调用者，
因此仍不等于原厂菜单调用链。回调指针、诊断对象和调用体代码在结束后
恢复；原始零填充函数清理读缓冲区，原任务栈指针恢复到调用前位置。

本地参考文件只用于比较和摘要计算。原生 SDK 已完整读取
48,494,024 字节的 C 1.70 原厂升级包，以 512 KiB 为容量执行 94 次
读取，包含末次零字节 EOF。整文件 SHA-256 为
`fc0e94f57500a1f0e287c6b9a036c81a5ffceccb8432a377d645b3fa35a19b6a`，
与参考文件逐块及整文件一致。打开、读取、关闭均返回 SDK 成功值
`0x043A0080`；关闭后句柄为 `0xFFFFFFFF`，四核异常状态为零。
20 字节文本文件也通过读取、EOF 与关闭检查。

不存在的 `B:\MISSING.BIN` 返回 SDK 打开错误 `0x043A0084`，
没有进入读取或关闭。SDK 状态应按完整值比较，不能只检查符号位。
正反两类结果见[原生 SDK 文件记录](../../artifacts/native_sdk_file_read/report.json)。

## 本地目录查找器的边界

在相同整机配置中，临时调用体执行原始更新文件查找器
`0x1039C236`，选择 SD 根目录并保留另一根目录的回退标志。
第一次目录打开 `0x1049D2E6` 返回 `0x80001003`。实时观察确认
原始卷名查找 `0x1047E2D6` 的未匹配分支 `0x1047E2FC` 被执行，
查找名称为 `B:`；主引擎两个本地卷记录的名称均为空，就绪字段为零。
尚未执行文件名匹配、SDK 打开或整包认证。这不是摘要拒绝；
跨引擎 SDK 文件读取成功也不能证明主引擎本地目录命名空间已建立。
该错误只限定这条本地查找通路；下面的 SDK 候选收集不依赖此表注册。

## 原始候选收集的整机执行

更新代码另有候选收集入口 `0x1039D984`，通过 SDK 目录存在性检查
`0x104D3EF0` 与枚举 `0x104D3E92` 访问存储卡。这与直接调用
`0x1039C236` 的本地目录查找不同，不能用本地查找错误概括 SDK 通路。

`tools/native_update_collect_probe.py` 在原始资源 8 的任务栈上调用
该入口，模式为 0；选择字段低四位显式设为 2，保留原有高位。
这是诊断调用输入，尚不是菜单自动选择的结果。原始收集代码分配
两个目录向量，检查 `B:\firmware\` 和 `B:\`，经原始回调
`0x1039D6B4` 收集实际目录记录，再执行 `0x1039D71C` 枚举、
`0x1039D5BC` 类别检查和 `0x1039D4D4` 记录构造。
诊断程序不注入目录条目、文件字节或 SDK 回复，也不代替固件分配和
释放内存；文件内容来自虚拟 SD 卡的实际扇区。

含 C 1.70 原厂包的卡生成 `B:\Z7_2_0~1.BIN` 记录，匹配数为 1、
类别为 4、整包标志为 1；无升级包的对照卡匹配数为 0，整机包记录
路径为空。两项收集均正常返回 1，两个向量指针在释放后归零，
诊断调用返回原始调度器并恢复任务栈，四核异常状态为零。
主引擎本地卷表仍未由诊断程序注册；SDK 通路能完成目录访问。
记录见[原始候选收集验证](../../artifacts/native_update_collection/report.json)。

这把目录收集从先前的主机目录夹具推进到整机原生文件服务执行。
通过的是候选构造层，尚未调用整包认证或更新执行入口。
原厂菜单如何选择候选、发起认证并处理结果仍需验证；不能据此宣称
修改包获准安装。

## 写入通路的无固件对照

拍摄观察开始保留独立卡副本后，运行中的卡头出现了重复片段，原根
目录位置也不再包含初始条目。虚拟机停止后的只读复核仍不能识别
该副本的有效文件系统；启动扇区总扇区数字段已变为 `0xffff`，原根
目录位置为空。保留该副本，不作修复；变化来源尚未定位，不能把
扇区变化当作有效照片写入。原始卡镜像未修改。

为区分主控传输与上层文件系统问题，扩展 `tests/test_sd_host.py` 并
检查通过：在临时快照中分别写入并读回对齐 PIO、先 33 个字节再按
对齐边界切换宽度的 PIO，以及 ADMA2 的完整 512 字节扇区。混合
宽度访问按数据指针低两位选择数据端口字节位置。三个扇区逐字节
一致，对其他扇区的写入未改变最初的参考扇区；复位和 IRQ 243 检查
仍保留。该结果限定这些主控路径，没有定位原厂运行中的卡头变化。

下一次介质对照已在私有目录准备分区式 FAT16 镜像，使用已验证文件
服务的原有卡分区，分区起点 63、长度 1032129 扇区，簇大小 8192
字节。分区及现有文件均位于保留的 512 MiB 内，源镜像未修改。
只读目录检查能识别分区与原有 20 字节文件；尚未以该副本证明拍摄
写入，也不据此认定原先 65536 字节簇或无分区布局就是问题来源。

该分区镜像已分别用于直接参数请求、控制模式参数请求和默认参数
拍照对照。虚拟机正常关闭后，三个独立副本均能通过只读归档检查，
仍列出原有 20 字节文件；直接参数请求副本的文件内容 SHA-256 为
`00339db3277e73d2331bdb28b0976f9fc23594696f3031c2e945f93e94770ef5`，
与源文件一致。后两项拍照接口均返回 4，未接受拍摄，故这些结果
仅证明该布局在所覆盖的启动和查询期间仍可读取，不证明可拍摄
或已经修复写卡。相关记录见[短曝光与介质对照](sampling_sync.md)。

## 介质容量与地址单位对照

[512 MiB 原厂命令跟踪](../../artifacts/capture_sd_trace/report.json)
定位了启动扇区异常的具体来源：固件发出 `CMD25 ARG=1` 时，卡模型
写入的字节地址也是 `1`；`ARG=0x22/0x43` 同样落在字节偏移
`0x22/0x43`。这些写入覆盖了启动扇区，解释了头部片段重叠现象。
当前运行路径使用扇区号，而该容量使设备采用 SDSC 字节寻址。
不需要据此猜测簇大小不被支持，也不需要修改主控的 DMA 数据。

`--trace-sd-host` 从启动开始启用命令、ADMA、寄存器与卡块写入跟踪，
公开报告最多保留前 256 个控制事件并记录总数和截断标志。数据端口
读写内容不进入报告，原始跟踪留在私有工作区并随正常工作目录清理。
无固件检查覆盖元数据筛选、顺序、截断及数据端口排除。实际 ADMA
缓冲和描述符均位于已有的从引擎 `0xc5...` 存储，并未使用猜测的
未建模总线别名。

[保留完整 4 GiB 容量的对照](../../artifacts/capture_sdhc_card/report.json)
使用相同源分区的原始完整镜像，未改写源介质。命令 `ARG=0x268`
写入字节偏移 `0x4d000`，`ARG=0x40` 写入 `0x8000`，符合乘以
512 的高容量卡寻址。该次运行 390.516 宿主秒，提交后 2 秒计数器
窗口达到，四核异常字段均为零，拍照接口接受且释放通知计数为 1。
编码器当前描述符仍为零，配置与启动入口均未命中。

[虚拟机停止后的只读检查](../../artifacts/capture_sdhc_card/card_check.json)
通过文件系统完整性检查，MBR 和分区引导区签名及哈希均保持，原有
20 字节文件内容哈希保持。原厂新建 `DCIM`、`NIKON/Z_7_2` 目录
及 512 字节 `NIKON001.DSC` 目录记录。该文件不是照片；本次尚未
取得可验证照片码流。SDSC 与 SDHC 两种容量模式的主控专项均已
检查 OCR、PIO/ADMA 写回和扇区零保护。

## 原厂服务的整包认证与拒绝返回

`tools/native_update_collect_probe.py --execute-service` 在收集后执行原始
日志初始化 `0x104E08C4(0)`、选择记录 `0x1039DAA4(13)`、服务资格检查
`0x10767048` 和执行请求 `0x10767108`。资格检查成功才继续执行请求。
这些入口仍由诊断调用体发起，尚未经过菜单条目派发。

日志初始化是卡激活的原始依赖：`0x1047179E`、`0x10471832` 分别以
参数 0、1 调用它。它通过原始分配器申请 256 字节日志缓冲，保存于
`0xB181A4F4`，并准备日志文件。单独调用执行服务而略过此初始化时，
拒绝日志在 `0x103A032A` 向地址 0 写入，产生 `DFSR=0x805`。
调用原始初始化后，日志经 SDK 打开、写入、关闭并正常返回；没有
补写缓冲指针、跳过日志函数或替换执行结果。

原始执行入口 `0x103F6474` 经状态检查后，用 `0x103F60CA` 申请
60 MiB 缓冲，并以事件位 `0x10` 唤醒原始工作任务。任务分派
`0x103F6938` 读取选中记录的整包标志，进入 `0x1039C638`。
完整升级包由原始 SDK 单次读满，再执行原始解码、八字节变换与
SHA-1 例程；没有主机运算原语代替这些步骤。

默认实验引导窗口 `0x10000088` 的八字节为零。这里的零值是 B8，
不是最终附加字节 K8；后者仍经过机型变换。原厂包在该输入下的
摘要比较返回 0，整包检查返回 3。原始工作任务写入状态并发送事件
`0x20`，服务等待者消费该事件，再将失败返回调用者。
该结果验证认证拒绝路径，不表示原厂包在相机上被拒绝。
完整输入身份、缓冲摘要及返回链见
[原厂服务认证记录](../../artifacts/native_update_service/report.json)。

大块原始解码和 SHA-1 运算期间，跨引擎队列索引可能保持不变。
服务观察因此同时记录四核执行位置、解码指针及异常状态，在同一个
运行实例中继续等待；缓冲比较分块捕获并只保留 SHA-256。
认证成功、CRC 后续分支、编程及复位后启动仍需有效引导材料和
完整原始调用路径继续验证。

官方升级说明要求更新文件位于卡根目录，并将卡插入当前选择的主插槽。
主插槽可以选择 CFexpress/XQD 或 SD，不能据此排除 SD 更新。
这项介质条件与上述本地卷注册错误、包认证条件应分别验证。
参考[原厂升级说明](https://downloadcenter.nikonimglib.com/en/download/fw/561.html)
及[主插槽选择](https://onlinemanual.nikonimglib.com/z7II_z6II/en/09_menu_guide_03_04.html)。
