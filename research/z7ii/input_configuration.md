# 输入处理配置与拍摄界面

当前复位观察已直接记录十四项格式输入全为零，并由原厂指令主动向
`0x20068500` 写零；零值不表示设置函数未执行。
第一组几何配置为零也不代表全部输入几何缺失。2026-10-29 补采的
第二组几何明确为 1380×918、12 位打包、2080 字节行长；实验输入
源已向原厂配置缓冲写入黑白块像素，见[输入路径](input_path.md)。
有效 LCD 帧与拍照仍未证明，早期模式观察见
[初始化后的模式请求](capture_mode_requests.md)。

分析固件可见，`0x102097fa` 将十四项格式参数打包到
`0x20068500` 的低十四位。此前首次写入在 `0x10209848`
发生访问异常，阻止后续设备配置。

新增输入配置设备映射 `0x20068400..0x2006bfff`，仅接受已解码的
配置字。各引擎独立保存状态，复位清零，并纳入迁移状态。
此读回形式用于实验检查，尚未确认全部硬件读回与控制位语义。

| 配置区域 | 固件中的用途 |
| --- | --- |
| `0x20068500` | 十四位输入格式组合 |
| `0x20068508..0x2006917c` 中的已实现字 | 输入格式、尺寸、裁剪及查表参数 |
| `0x20069500..0x20069f00` 中的已实现字 | 几何参数、处理通道及缓冲地址 |
| `0x2006a000..0x2006a024`、`0x2006a040` | 第一组上下文参数与控制字 |
| `0x2006a200..0x2006a370` | 分析参数、四组配置及三组打包参数 |
| `0x2006a400..0x2006adff` 中的已实现字 | 图像通道配置及多平面缓冲地址 |
| `0x2006b000..0x2006b200` | 129 个由半字输入扩展为字访问的表项 |
| `0x2006b800..0x2006b980`、`0x2006ba00..0x2006bab8` | 次级分析配置、查表及行配置 |
| `0x2006b310..0x2006b3fc`、`0x2006b400` | 分析参数与控制字 |
| `0x2006b400..0x2006bdff` 中的已实现字 | 另一组图像通道配置 |
| `0x2006be00..0x2006be24`、`0x2006be40` | 第二组上下文参数与控制字 |

以上区间不是连续开放的普通内存；实际接受地址由设备中的范围和
通道字段解码决定。`0x1020a1b6` 等入口写入包含多个位域的完整字，
不能把这些分析参数统一限制为十六位。格式字以外的配置保留完整
三十二位值。已解码的结果地址只读；未实现字段、字节及非对齐访问仍拒绝。

配置存储不会执行像素处理、修改缓冲内容或自动生成采样及传输完成
事件。已有输入控制和事件银行继续由独立窗口处理。
`tests/test_input_configuration.py` 使用主、从引擎实际执行的 ARM
读写指令，检查字段边界、三十二位打包、状态隔离、复位、拒绝访问，
以及写入缓冲配置后目标数据保持原样。

组合运行使用未修改的原厂主、从及控制器固件，显式实验驻留数据、
供电输入和诊断参数。诊断参数不是实际机身校准数据。
显示控制台采集的是图形表面，尚未实现完整 LCD 扫描输出。
正常启动和菜单交互必须继续单独验证，不能由配置写入成功推断。

最终配置模型的原厂运行已完成 `0x10209848` 的写入，并自然到达
操作 14 完成入口 `0x10247dea`。继续执行后从模式 2 转入模式 3，
图形上传增加到 254 次，执行 392 条绘制命令，无不支持命令或失败请求。
`0xbec5f200` 的图形表面输出 720×480 画面，该检查点已出现原厂
曝光模式字母 A；不能据此认定整个界面已绘制完成。

进一步观察中，系统转入模式 8，前台返回 `APPIDLE`，图形表面被清空。
四个引擎核的指令与数据异常寄存器以及控制器故障字均为零。
因此当前已确认初始化完成回调及初始界面绘制，仍需追踪后续退出原因，
验证稳定拍摄界面和菜单输入。没有通过注入采样事件、替换完成回调或
修改固件代码促成上述状态。记录见
[输入配置验证](../../artifacts/input_configuration_validation/report.json)。

随后用相同最终模型和实验输入追踪实际模式切换入口 `0x1020d384`，
再次观察到模式 2 转入模式 3。在上传 258 次、执行 396 条绘制命令的
检查点，720×480 图形表面已经显示曝光模式 A、S、MF、白平衡和
画质图标等原厂拍摄状态栏；所有引擎及控制器故障字均为零。
这是初始拍摄界面的可见输出，尚不证明传感器画面或菜单交互。

同次追踪捕获了后续模式链：

| 当前模式 → 目标模式 | 切换入口参数 `r2` / `r3` | 调用者返回地址 |
| --- | --- | --- |
| 2 → 3 | `6` / `9` | `0x10247e17` |
| 3 → 1 | `1` / `9` | `0x10246919` |
| 1 → 8 | `1` / `3` | `0x1020db6b` |

`0x102468c4` 设置模式上下文的完成位，在所需完成位全部到达时，
由 `0x10246914` 发布通知。此处已读到后续目标字段为 1，
不能仅凭回调名字认定是绘制失败或温度提示。
模式 3 的请求入口 `0x102467be` 会先将该目标字段改为 1，
再进入通用请求处理；下一步应追踪调用该入口的原始请求。
记录见[拍摄界面与模式切换观察](../../artifacts/shooting_interface_validation/report.json)。

后续已捕获退出请求的生产者：应用计时器槽 0 投递 `0x03000003`，
最后启动参数为五秒。同次运行存在电池通信失败状态和供电限制策略，
见[启动后的五秒时限](startup_idle_timer.md)。

后续启用实验电池串行对端后，模式 3 → 1 的参数变为 `6 / 9`，
模式上下文目标字段保持为 6。前台 `APPLV` 和绘制继续运行，不能沿用
上文供电失败时的退出结论。完整采样和独立复现见
[界面持续运行观察](../../artifacts/shooting_persistence_validation/report.json)；
当前画面有 `Err`，尚未验证菜单输入或完整采集链。

## 相位源推进后暴露的配置访问异常

在自动输入握手、限次计时修复后的构建上，增加默认关闭的实验相位源。
它在既有定时采样源上、仅主引擎且采样开启、同步掩码位 7 为 1 时
锁存同步组 2 位 7；周期仍为实验选择的约 30 Hz，不产生像素就绪位
或像素数据。最初 240 宿主秒内没有达到完整交互就绪，后续用
`--boot-watch 120` 保存了实际失败状态，见
[补表前快照](../../artifacts/masked_frame_phase_startup/report.json)。

该快照的应用索引已为 3、管理器就绪，但交互准备为假。主核的数据
异常地址为 `0x2006b000`，状态 `0x808`；其余三个引擎核的异常寄存器
均为零，状态列表为空。LCD 平面仍为 `0xcbf33000`、1024×682、
全字节 16。门控字段为零时界面尚未完成，不能解释成快门已解锁。
这补足了旧相位实验没有取得失败快照的缺口，不能再仅因未就绪就
把所有周期相位事件归为无效。

原厂 `0x1020b130..0x1020b140` 从输入读半字，以字写入递增目标，
循环 129 次，地址正好覆盖 `0x2006b000..0x2006b200`。
`tools/input_lut_probe.py` 用原始指令和合成输入独立执行该函数，
验证每次地址、访问宽度、表值及末端之后未写入，见
[表与参数合同](../../artifacts/input_lut_contract/report.json)。
模型只新增这一精确配置范围，复用已有隔离、清零与迁移存储，
不搬运传感器数据、不触发 DMA 完成。

补齐查表后，[下一次快照](../../artifacts/playback_frame_phase_lut/report.json)
中的异常地址前进到 `0x2006a27c`，同样为写访问异常 `0x808`；
这不是先前 B000 访问继续失败。原厂设置器 `0x1020afb4` 正是从
该字开始写分析参数。继续核对相邻设置器后，使用原始指令执行
`0x1020aea8/0x1020aed6/0x1020af14/0x1020afb4/0x1020b056/0x1020b094`，
取得 93 个不同的字写入地址，其并集完整覆盖
`0x2006a200..0x2006a370`，据此补齐该配置范围。设置器的分支由
合成输入选择，不表示所有参数分支已在整机执行；相邻结果窗口
`0x2006a3e0` 仍未开放。

配置检查覆盖两个范围首尾、相邻拒绝访问、两引擎隔离与复位；原始
表写入合同和增量编译均通过。相位开关继续默认关闭，补齐后的
原厂启动、播放停止、LCD 像素及照片输出仍须独立验证。

补齐分析参数后，[失败快照](../../artifacts/playback_frame_phase_parameters/report.json)
中的写异常进一步变为 `0x2006be00`。使用
`tools/device_registration_probe.py --frame-phase --watch-input-write 0x2006be00 --report-unready`
从复位观察，首次写入后移除观察点并单步执行，然后结束观察；
不会读取被拒绝的 MMIO，也不重试或替换写入。
[原始写入位置](../../artifacts/input_be00_writer/report.json)为
`0x10209efe`，主核执行，`r0=0xb18067c4`、`r2=0x2006a000`、
`r4=0x1e00`，返回地址 `0x10239f5d`。同一运行首次命中此前未见的
会话报告门 `0x102323ec`，入参正是根上下文，`+0x41` 为零；
该门并未防止后续 BE00 配置调用。

描述符 `0xb18067c4+0xc` 的初始化值为 `0x1e00`；另一描述符
`0xb18067b4+0xc` 为零。原厂 `0x10209ef6` 使用同一个设置器，
分别写 `0x2006be00..0x2006be24` 和 `0x2006a000..0x2006a024`，
每组十字。控制函数 `0x10209fea` 另写基址 `+0x40`，值为
`r1 | (r2 << 4)`。独立原始指令探针已覆盖两种描述符与控制打包，
模型按这两个精确配置范围补齐；结果读取函数 `0x10209f4a` 和
控制状态 getter `0x10209ffa` 对应的窗口继续单独保留，不能混作
可写配置。新增边界的隔离、复位及拒绝访问检查通过。

随后[运行快照](../../artifacts/playback_frame_phase_context/report.json)
的主核异常地址为 `0x2006b800`，仍是被模型拒绝的写访问；另一主核
的指令异常为 `0x1010000c`，不能把这次四核状态整体称为无异常。
原厂 `0x10208e96` 写 `0x2006b800..0x2006b81c`，
`0x10208cb0` 经指针表写后续 24 字，`0x10208db6` 写 65 个表项，
三者的并集是 `0x2006b800..0x2006b980`，共 97 个字。
`0x10208cf4`、控制设置器和三行配置用例则覆盖
`0x2006ba00..0x2006bab8`，共 47 个字。原始指令探针逐项核对
这两个集合及字访问宽度，模型据此接受固定范围；三行是合成输入
用例，不代表已测量物理硬件的最大行数。相邻 `0x2006b98c` 和
`0x2006babc` 仍拒绝，配置测试继续验证无像素搬运。

## 配置之后的结果读取

[次级参数补齐后的快照](../../artifacts/playback_frame_phase_secondary/report.json)
中，主核异常变为读取 `0x2006bb70`，状态 `0x8`，其余三个引擎核
异常寄存器为零。原厂结果 getter `0x10208e0a` 会读取该字及
`BB74/BB78/BB7c/BC78/BC7c/BD78/BD7c`，组装调用方的结果结构。
其地址和访问宽度已由原始指令探针独立验证，不能将它当成配置写入。

模型新增以下已解码结果字的只读访问：上下文结果
`0x2006a100..0x2006a12c`、`0x2006bf00..0x2006bf2c`，上下文状态
`0x2006a044/0x2006be44`，四个分析结果字
`0x2006a3e0..0x2006a3ec`，状态 `0x2006b988`，以及上述原先未接受的
`BB70/BB78/BB7c/BC78/BC7c/BD78/BD7c`。所有结果复用已有寄存器
数组，实验初态为零，没有像素处理生产者，也没有自动完成副作用；
这一初态不是实测的物理复位值。已有可写字段 `BB74/BB80` 不据
getter 的存在而改成只读。

另一个独立设置器 `0x10208e7e` 明确写 `0x2006b984`，打包
`r1 | (r2 << 4) | (r3 << 8)`；该控制字作为可写配置单独接受，
不混入其后 `0x2006b988` 的只读状态。原始指令探针核对控制写入
及十组结果 getter 的访问地址；模型检查验证结果初始读零、写入
被拒绝且数值保持不变。该改动使原厂能够读取尚未产生的结果状态，
并不证明图像处理、LCD 实时像素或曝光完成。

## 最终组合运行：启动通过，后续停在另一地址读取

[配置与只读结果补齐后的记录](../../artifacts/playback_frame_phase_results/report.json)
使用原厂三份映像、卡覆盖层、显示完成源、自动 GPIO 握手和默认关闭
的相位源选项。没有启用 `--local-stop-events` 或按断点注入 GPIO。
冷启动在约 42 个宿主秒达到应用索引 3、管理器就绪及交互准备，
开始按键观察时四个引擎核的全部异常字段为零。驱动的待处理状态
已为 20，与关闭相位源的旧稳态不同。

播放触点产生原厂动作 `0x1a`，操作 18 API 和任务、捕获状态到 3 的
迁移均命中。之后还命中驱动状态请求（目标 `0x12`）、准备请求
`0x103c5342` 和通知 `0x042f0027`。但本次未命中局部停止等待及
操作 18 完成生产者，结束应用仍为 3，因而半按返回与后续全按
阶段没有执行。不能将启动恢复解释为播放停止已经成功。

末次第二个主核出现读异常 `DFAR_S=0x5d170000`、`DFSR_S=0x8`；
其余三个引擎核的异常字段仍为零。该地址不属于本次补齐的输入
配置区，下一步需要恢复它的读取位置与用途，而不是继续扩大输入
配置窗口。两次计数相差 `14757862 / 48000000`，约 0.307 个相机
计数器秒，宿主观察窗为 60 秒；异常本身有直接寄存器证据，但
不能由观察窗推断正常情况下的完成时长。

LCD 在观察前后均为 `0xcbf33000`、1024×682、全字节 16，摘要
保持 `c0f9197b11cc9b47402450d1ae93522deeffff37173f6ce54523720c3ac518e0`。
快门门控仍为 1。当前进展是相位源能够推进原厂上下文配置并通过
初始界面准备，LCD 实时像素、照片输出和完整播放往返仍未实现。
