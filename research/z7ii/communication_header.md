# Z7 II C 1.70 通信区头部初始化

本记录基于主从固件分析与独立执行实验。代码位置为 EG 成员文件偏移；
通信区地址为各角色使用的软件地址，尚未确定两者之间的物理映射。

| 项目 | master | slave |
| --- | --- | --- |
| 完整初始化函数起点 | `0x367E08` | `0x40CC0` |
| 本次执行起点 | `0x367E20` | `0x40CD8` |
| 本次停止位置 | `0x367E30` | `0x40CE8` |
| 本地通信区 | `0xB7CF0000` | `0xC60F0000` |
| 初始化表清零长度 | `0xC618` | `0xC618` |

执行窗口为 16 字节 Thumb 代码，包含七条指令：加载本地地址、将 `r1` 置零、
加载两项标识，然后用 `STR`、`STRD`、`STR` 写入四个小端字。
本次从前置系统调用之后进入，在恢复栈的 `POP` 之前停止。

| 通信区字偏移 | 写入值 | 局部行为 |
| --- | --- | --- |
| `0x00` | `0x00C00108` | 第一项标识 |
| `0x04` | `0xAA550001` | 第二项标识 |
| `0x08` | `0` | 清零 |
| `0x0C` | 保持原值 | 本段未写入 |
| `0x10` | `0` | 清零 |
| `0x14` | 保持原值 | 本段未写入 |

保留字段不能仅凭这段代码命名。初始化表中的整区清零和这里的局部头部写入是
不同操作；本实验人为污染目的数据，以区分实际写入和先前清零产生的结果。

`analyze/firmware_structure.py` 在完整镜像长度、哈希和 CRC 验证后，检查本段指令、
解析 Thumb PC 相对 literal，并要求同地址存在唯一的 `0xC618` 清零记录。
报告新增 `communication` 字段，记录写入项和执行边界。

`tools/structure_probe.py` 为每角色执行两次头部写入，分别用 `0xA5`、`0x5A`
填充 24 字节头部，逐字节比较四项写入、两项保留字段及前后四字节保护值。
沿用启动结构实验的命令和主从独立实例配置，报告新增 `communication_header`。

本实验未执行初始化函数前面的系统调用，也未验证队列收发、通知机制、完整启动
或双处理器协作。两个通信窗口仍为普通 RAM。

2026-10-10 验证：`virt`（QEMU 10.0.0）和原地址主板（QEMU 10.2.4）均通过
两个角色的头部写入检查，已有三条早期复制、四条表复制和通信区清零实验也通过。
20 项 Python 测试、270 项图形合成检查（ASan/UBSan），以及两个
原地址主板的 RAM／ARM 检查均通过。结构与局部执行结果见
[验证记录](../../artifacts/communication_validation/report.json)。

## 运行时队列观察:请求入队、无消费者

分析 C 1.70 master 提交与消费两端:服务请求提交入口(文件
`0x368326`)把条目写入本引擎通信区 `0xB7CF0000` 的环形队列——
条目步长 `0x108`(指令序列 `add r0,r0,lsl #5; lsl #3`),
参数在条目 `+0x18`、服务号字节在 `+0x1c`,写索引在区头 `+0x8`
(`0xc0` 回绕),入队后经通知层(文件 `0x367ee2`,最终进入
ARM 态 `svc #6` 系统调用)唤醒对端。消费入口(文件 `0x367f84`)
经指针转换(文件 `0x30b75c`)读**对端**同名结构的环并以相同
步长出队;两引擎镜像同基址,同一代码在两侧运行。

`tools/comm_area_probe.py` 的整机会话观察(见
[验证记录](../../artifacts/comm_area_validation/report.json)):
两个通信区头部魔数 `0xAA550001` 均有效;两侧传输控制块
(主 `0xB1808928`、从 `0xC1006F68`,各由镜像内相差 0x10 的两个
字面量同基寻址)的魔数对 `+0x28/+0x2c` 也都已写入
`0xC00108/0xAA550001`——**握手在两侧都已完成**。写游标(区头
`+8`)与消费游标(`+0x10`)在两侧分别相等且跨采样静止:
此前"请求入队无人消费"的解读**予以撤回**,游标相等表示队列
已排空。断点观察确认消费入口(运行 `0x10387F84`)在稳态持续
执行(调用者 `0x103880C7` 的消费循环)。因此请求已被对端消费,
缺失的是从引擎供应方的**应答**。消费回调(从引擎文件
`0x40F38`)按事件位查五槽处理器表 `0xC144F570` 并调用;
运行时该表**只有槽 4 注册了处理器**(从引擎文件 `0x3E798`,
运行 `0x1005E799`),其余四槽为零,事件计数 `0xC144F3AC`
为 5——事件到达但多数事件位落在空槽上,请求被消费后无人
处理,应答永不产生。`0x4219`→`0x041b` 通知链的阻塞点因此
定位在**从引擎供应方的槽位注册**:捕获/视频供应方的注册路径
(应写入槽 0..3)未执行,其背后是传感器接口设备栈这块仍未
建模的硬件。
