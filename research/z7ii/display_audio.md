# Z7 II C 1.70 显示、音频和长曝光固件观察

以下偏移均为解码后 master 文件偏移。依据为原厂指令、字面量、描述符和数据表，不是已完成的实机功能验证。输入身份见 [容器记录](container.md)。

## 显示条件

原厂 `0x600346` 读取状态结构 `+0x19E`，与 2 比较后执行属性和模式限制；`0x539EE2` 读取同一字段并与 2 比较，后续 `0x539F14` 调用前一资格函数。状态 RAM 的字面量为 `0xB202BE70`。

九个 `0x444` 位于 `0x2399844`，其前一字为零。按 `0x14000` 初始化记录换算，前一字的 RAM 地址为 `0xB181F8AC`，九个数据项从 `0xB181F8B0` 起。描述符表 `0x92AA24` 的第 32 项（`0x92AAA4`）为该指针；控件使用运行时表地址 `0x1094AA24` 并读取 `+0x80`。

这些关系支持状态字段、资格函数和控件数据的关联。两处判断目前均要求状态字段为 2（工作名称 `DISP`）；状态 3 的画面含义、掩码各位语义、LCD/EVF/HDMI 的布局及绘制结果均未确认。

|---|---|
| `0x241548` | 音频数据路径，读取状态和资源表字段、组装参数 |
| `0x241596` | 音频配置路径 |
| `0x2415D8` | 状态结构字面量 `0xB21E2630` |
| `0x2415DC` | 资源表字面量 `0x118E492C` |

| `0xB201BD08`（RAM） | 七项对象类型指针表，单个对象步长 44 字节，见[对象类型表](menu_objects.md) |

音频函数有结构字段访问和参数组装证据，不能只凭入口字节相似就认定接口可直接调用。文件读写、堆分配、消息队列、完成回调、停止播放、拍摄触发、属性查询、双卡路径和静音连拍行为仍需研究。已定位位置在 master，尚未证明完整音频行为不涉及 slave。下文记录可选设备模型及逐步取得的原厂执行证据，尚未实现完整文件播放。

### C1.70 音频寄存器契约

[寄存器证据与映射检查](../../artifacts/audio_register_contract/validation.json)
记录完整固件摘要及八个代码窗口的摘要，不包含固件字节。以下地址为
执行地址，文件偏移需减去 `0x10020000`。

`0x1036e4b6` 将通道 1 转为位移 `0x100`，其他输入返回 0；两个原厂
回调分别传入 0、1。寄存器窗口基址为 `0x2c080000`，两组通道寄存器
起点为 `+0x100`、`+0x200`。`0x1036d7fa` 分别用中断号 167、168
注册回调 `0x1036d7d7`、`0x1036d7b7`。这不表示其他通道编号合法。

| 通道内偏移 | 原厂访问证据 |
| --- | --- |
| `0x04` | `0x1036e4c4` 的合并输出写入目标 |
| `0x08` | 控制字；发送轮询检查位 9，位 1 选择分离输出路径 |
| `0x0c` | 格式配置；`0x1036da06`、`0x1036da82` 更新位字段 |
| `0x10` | 状态字；发送轮询检查位 25，中断处理读取并应答位 16、17 |
| `0x14` | 分频配置；位 24..28、18..20、16..17 分别为 5、3、2 位字段 |
| `0x18` | 端口格式配置，两个格式函数执行读改写 |
| `0x30`、`0x34` | 分离输出路径分别写入偶数、奇数源索引的数据字 |
| `0x5c`、`0x60` | `0x1036e3a4` 起读取的两个输出监视值 |

发送函数 `0x1036e4c4` 在 `0x1036e4fe` 循环读取控制、状态，直到
状态位 25 或控制位 9 为 1 才写入下一数据字。`0x1036db04` 先清除
分频寄存器位 30，再更新三个分频字段，最后置位 30。该序列证明
字段宽度及编程顺序，不能单独证明输入时钟频率或分频计算公式。
`0x1036e542` 的输出 DMA 配置按通道选择请求值 3、7；请求值与
具体 DMA 实例的路由仍需核对。

补齐设备前，`nikon-z72-lab` 的实际设备树显示 `0x2c010000..0x2c08ffff`
由优先级 0 的 `z72-release-block-lab` 普通 RAM 覆盖，音频窗口没有
设备覆盖层。因此寄存器可读写不代表已具备队列消费、状态变化或
中断行为；发送轮询也不能靠这种 RAM 映射自行完成。

后续设备实现需以真实队列占用推导输出状态，并核对复位、停止及
中断应答。PCM 打包、物理声道顺序、FIFO 深度和阈值、真实采样率、
输入源、从引擎归属及完整原厂播放流程均未验证；不能用固定就绪位
或直接跳过发送函数替代这些设备行为。

### 可选音频轮询输出设备

`-global nikon-z72-boot-config.audio-output=on` 在主引擎上用独立设备
覆盖 `0x2c080000..0x2c0803ff`。默认关闭，从引擎保持原映射；输入及
双通道块传输尚未接入，相关启动或未支持寄存器访问返回访问
错误，不发布虚假的完成状态。启用音频设备时暂不支持迁移。启动
配置布局升至 66，拒绝旧布局，未验证迁移往返。

每路支持合并数据字和两侧分离数据字，队列满时拒绝新字，保留已有
内容。分离模式等待两侧均有数据才一起消费；就绪表示至少一侧仍有
空间，使原厂交替写入的轮询不会卡在半对数据上，各侧写入仍独立
检查容量。非空时改变队列容量或合并/分离模式会失败。停止或关闭
时钟取消消费但保留队列；单通道复位清空该路队列、配置和监视值，
不影响另一通道。整机复位清空两路。

队列容量由模式位 25 选择 1 或 16 个字，就绪阈值按状态位 30..31
选择 1、12、8、4 个空位并限制在容量内。这些深度和阈值是功能
约定，尚未证实为物理硬件值。定时消费采用名义 48 MHz，周期为
`(字段24..28+1) × 4×(字段18..20+1) × 16×(字段16..17+1)` 个时钟，
向上取整到纳秒。它提供确定的状态推进，不代表已恢复真实采样率。

状态位 25 和控制位 9 从队列推导；空队列消费产生欠载位 17，写零
清除。就绪、输出空和欠载各自受对应中断使能控制，路由至 167、
168。监视值在合并模式记录数据字低/高 16 位，分离模式记录两侧
各自低 16 位；这是数据消费观察约定，不是 PCM 解码或宿主声音输出。

[设备及原厂轮询验证](../../artifacts/audio_output/validation.json)
记录编译和 `tests/test_audio_output.py` 结果，覆盖单字及 16 字队列、
两路中断、阈值、欠载应答、分频、停止、复位、半对数据保留和默认/
从引擎负对照。既有拍摄反馈测试也通过。

隔离调用未经修改的原厂 `0x1036e4c4`，在单字容量下分别提交 4 个
合并字和 6 个分离字，原厂索引正确推进并返回，监视值匹配已消费
的数据。返回时最后一个字或最后一对仍在队列中，符合该函数负责
提交数据的范围。这只验证主引擎通道 0 的原厂轮询函数，不代表完整
启动、文件播放、输入录音、DMA 或实际声音已经可用。

### 合并输出的 DMA 请求

原厂 `0x1036d89e` 绑定音频 DMA 时检查资源范围 `0x132..0x139`，
对应第二组八通道控制器 `0x2c030000`。两个音频通道的输出选择值
分别为 3、7。与之相对，串行初始化 `0x103705fe` 检查发送资源范围
`0x12a..0x131`，对应第一组 `0x2c020000`。因此不能仅凭相同的选择值
将串行发送和音频输出请求混合或广播到两组。

启用 `audio-output` 现在自动创建主引擎的两组外设 DMA，将音频请求
接至第二组的 3、7。主引擎串行发送请求只连接第一组；串行接收和
从引擎的既有路由暂不改变，不能把发送侧证据扩大到这些未核对路径。
音频输出已启用、非分离模式且队列有空间时，控制位 15，或状态位
29 配合就绪位 25，可以产生请求。每个传输单位都实际写入音频队列，
队列满后撤销请求，消费后恢复。停止及复位撤销请求，不能让 DMA
在无空间时继续搬运。分离输出 DMA 仍返回不支持，避免将两侧写入
误当成已实现的块传输。

[DMA 验证](../../artifacts/audio_dma/validation.json) 覆盖两种请求使能、
两个音频通道、不同 DMA 通道、停止后恢复、完成中断及确认。相同
选择值的第一组 DMA 不会因音频请求搬运；串行发送请求也不会唤醒
第二组。既有主从 DMA 和镜头传输检查通过。

隔离执行原厂描述符构造 `0x1036de50`、配置 `0x102dc41e`、启动
`0x102dc4ec`，得到控制字 `0x29e00000`，两个目标分别为
`0x2c080104`、`0x2c080204`。第二组通道 5、2 各搬运四个数据字，
完成状态均为 5，源地址按原厂描述符要求重载，输出监视值与前三个
已消费的数据相符，最后一个字仍在音频队列中。DMA 完成表示提交
结束，不表示音频已播完。完成等待使用本项目编写的短轮询代码；
没有运行完整固件初始化或播放回调，实际声音、文件播放及录音仍未验证。

### 控制台启用与原厂启动

网页控制台及机身探针现在接受 `--audio-output`，通过同一启动参数
启用主引擎音频设备；探针将此选项写入运行跟踪和启动超时报告。
默认不启用，不改变现有未选择音频模型的启动方式。

[控制台启动验证](../../artifacts/audio_console_boot/validation.json) 使用
实际命令行解析及 HTTP 状态接口，启动 C1.70 原厂主从和控制器固件。
启用既有实时预览、显示完成及处理资源头部，未触发拍摄或启用静照
预处理跳过。拍摄应用 3、界面及输入就绪，按键已释放，采样的四核
故障字段均为零。设备树确认主引擎音频窗口由优先级 1 的设备覆盖，
原始 SD 卡的运行前后摘要相同，临时运行目录已清理。

两路分频寄存器 `0x2c080114`、`0x2c080214` 均由原厂写为
`0x43030000`，与设备复位值 0 不同，证明初始化实际到达设备。
控制字均为 `0x200`（模型推导的输出空状态），位 13 未置位，
模式寄存器为 0，故本次尚未开启音频输出。该观察补齐启动与分频
初始化的兼容证据，不代表采样率校准、文件播放、实际声音或录音。

控制台 29 项检查通过，两种启动工具的帮助和参数解析接受新选项。

### 原厂普通输出配置

原厂 `0x1036dd7c` 在普通输出配置中也会读写通道偏移 `0x40`、
`0x48`，即使参数中的块传输标志为零。设备现在保存 `0x40` 的
输入位 0、输出位 8，以及 `0x44`、`0x48` 的低 16 位计数配置，
并在通道复位时清除。超出已知字段的写入被拒绝。

这些寄存器仅支持配置和读回。输出块标志置位时，输出启动和入队
仍被拒绝；正在输出或队列非空时也不能切换到块传输。输入启动
继续不支持，保存输入配置不代表已实现录音。

[配置验证](../../artifacts/audio_config/validation.json) 隔离调用 C1.70
原厂格式函数 `0x1036da06`、配置函数 `0x1036dd7c`、启动函数
`0x1036dd04` 和停止函数 `0x1036dd1c`。两路均正常返回，模式为
`0x06800000`，输出计数和回调地址匹配参数，控制字从启动后的
`0x2200` 变为停止后的 `0x200`。验证时未开启音频时钟或提交数据，
因此仅证明配置及启停兼容，未验证文件播放、实际声音或块传输。
设备检查另覆盖字段边界、拒绝后的状态保持和复位清除。

### 原厂中断状态转交

[回调入口验证](../../artifacts/audio_callback/validation.json) 隔离执行
原厂输出掩码设置 `0x1036e3ec`、公共状态解码 `0x1036d758` 和两路
处理入口 `0x1036d7d6`、`0x1036d7b6`。测试提供描述符及回调指针，
在回调入口停下检查寄存器，不替代或执行原厂上层回调。

两路空队列就绪均转交状态 `0x18`，通道标识分别为 `0x410a1401`、
`0x410a1500`。开启时钟后，由设备实际空队列消费产生欠载；测试
等待欠载出现，再关时钟以固定观察状态。原厂处理函数转交 `0x38`，
并把状态寄存器从 `0x0a0a0000` 清为 `0x0a080000`，保留原有使能
字段。再次调用只转交 `0x18`，没有重复报告已清除的欠载。两路的
空回调指针分支也正常返回。

这证明原厂状态读取、W0C 确认和回调参数与模型兼容。处理入口由
测试直接调用，尚未证明 GIC 异常分发、RTOS 上层回调、文件播放或
实际声音；不能将本次结果作为完整中断链路已经运行的证据。

### 原厂输出初始化与首块消费

原厂 `0x102debaa` 使用 `0xb1cf7468 + 通道 × 56` 的缓冲区状态，
依次设置格式、注册补充数据的回调、设置 DMA 请求、提交首块，最后
开启输出。普通输出路径由 `0x102deaa6` 计算缓冲区地址，再经
`0x1036de84`、`0x1036e542` 构造并启动 DMA。它提交后推进状态
`+0x24` 的缓冲区索引；不能把该索引推进解释为播放已经完成。

[初始化验证](../../artifacts/audio_start/validation.json) 在两路分别
运行上述完整初始化入口及原厂被调用函数。测试预置两块缓冲区、
描述符、已绑定资源标志及 DMA 对象，提供全局 DMA 使能和名义音频
时钟；没有执行资源管理器或完整任务启动。两路返回 0，缓冲区索引
从 0 变为 1，控制字 `0x45002200`、模式 `0x0e880000`、状态
`0xe2000000`，目标分别为 `0x2c080104`、`0x2c080204`。

原厂登记的补充数据回调分别为 `0x102deb99`、`0x102deb75`。
DMA 状态到达 5 后继续等待队列清空，最终监视值为 `[4, 0x4444]`，
对应首块最后一个字，证明首块四字均被消费。CPU 中断保持屏蔽，
完成与排空等待使用测试轮询；本次未自动调用补充数据回调，也未
消费第二块。下一步需验证 DMA 完成分发与持续补充数据，文件来源、
PCM 格式解释和实际声音仍未验证。

### DMA 完成分发与补充数据边界

[完成分发验证](../../artifacts/audio_refill/validation.json) 使用真实首块
DMA 完成状态，直接调用原厂分发入口 `0x102dc2fa`，参数为第二组
控制器及通道号。原厂保存状态 `0x00030005`，将 DMA 控制字从
`0x29fd0000` 确认为 `0x29e00000`，随后调用初始化登记的回调。
两路分别经过 `0x1036de43 → 0x102deb99` 和
`0x1036de35 → 0x102deb75`，进入共同处理函数 `0x102deb2a`。

该函数在检查剩余缓冲区并继续提交前，先通过 `0x103610cc` 设置
事件。原厂代码切换到 ARM 状态，在 `0x10104858` 执行 SVC 6，
服务选择值 `r12=0x802e0200`；两路事件位 `r1` 分别为 2、4。
测试在 SVC 指令执行前停下，事件句柄使用明确的哨兵 `0x1234`，
没有伪造 RTOS 服务返回。此时缓冲区索引仍为 1，第二块尚未提交。

这验证了 DMA 确认和原厂回调链，但未验证 GIC 异常入口、事件对象、
调度器或持续播放。当前边界来自隔离测试未初始化 RTOS，不能据此
推断存在设备寄存器缺口。下一步应在完整启动环境中使用真实事件
对象验证服务返回、第二块提交及缓冲区用尽分支。

### 完整启动后的音频服务状态

[待机状态采样](../../artifacts/audio_runtime/validation.json) 使用完整
C1.70 主从及控制器启动，开启可选音频设备，在拍摄应用 3 和输入
就绪后暂停读取原厂 RAM。事件句柄 `0xb1807abc` 为 `0x0100014b`，
其后四个资源指针均非零。两路缓冲区状态的 `+0x18` 分别指向
`0xb1805ba8`、`0xb1805bdc`，对应资源编号 `0x108`、`0x109`。

两路缓冲区地址、长度、数量均为零，停止字段 `+0x2c` 均为 1；
六个音频 DMA 绑定指针及占用标志均为零。两路输出使能未置位，
分频值均为 `0x43030000`。注册的通道 IRQ 回调为 `0x102deedd`、
`0x102deedb`，原厂指令均仅返回；它们与 DMA 补充数据回调不同。
这表明基础音频初始化已运行，但当前待机状态没有播放请求，不能
将未发生 DMA 解释为设备拒绝了已经提交的数据。

原厂 `0x102df1c2` 创建事件后以 `0x102df04f` 注册服务任务。该任务
等待掩码 `0x3f`，清除收到的事件，并分别消费事件位 2、4。下一步
应定位播放请求的正常提交接口，再验证真实事件服务与后续缓冲区
提交；本次只读采样没有发起请求或执行隔离调用。
