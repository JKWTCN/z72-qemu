# 输入通路配置与启动异常

分析固件并检查原厂运行，实验温度参数使前台进入 `APPLV`、系统模式为 2
后，主引擎第二个核仍可能因外设访问异常停止。仅检查应用管理器和
模式状态不足以证明引擎继续正常执行。

本次异常寄存器为 `DFAR_S=0x20068000`、`DFSR_S=0x808`，
预取异常寄存器均为零。保存的现场包含指令地址 `0x1020aae2`，
该指令向 `0x20068000` 写 `0xfff`；下一条指令还会向偏移 4 写同值。
故障后进入 RAM 中的异常输出代码，轮询未就绪的串行状态。
这解释了前台状态保持不变的一项直接原因，不能把该循环解释成正常空闲。

## 已确认的寄存器访问

驱动代码 `0x1020a50c` 根据布尔参数选择向偏移 4 或 0 写同一位掩码；
`0x1020a518` 对应偏移 `0x10`、`0x14`。
现在分别提供置位／清除和置位／清除的配置状态；第一组清除地址为 0，
置位地址为 4，第二组置位地址为 `0x10`，清除地址为 `0x14`。
成对地址读回同一状态，复位清零。读回形式是实验模型的配置接口，
不能据此推断未观察到的硬件读回细节。

偏移 `0x18` 在 `0x1020a524` 中通过读、或／与非、写方式更新。
其他已观察到的配置字包括 `8`、`0xc`、`0x20..0x28`、`0x60`、
`0x70..0x78`、`0x80`、`0x88`、`0x8c`、`0x100` 和 `0x104`。
驱动查询的 `0x7c`、`0x84`、`0x140`、`0x144` 当前保持只读零值。
未建立采样来源，不将这些零值称为有效采样数据。

八组事件相关配置地址为 `0x200..0x2e0`，间隔 `0x20`；
对应状态地址为 `0x210..0x2f0`。原厂处理中读取状态，使用配置掩码
分发通知，再把读取值写回状态地址，因而状态写入按写一清除处理。
软件不能通过写入制造事件。外部事件通路与中断连接见下文；
采样传输和自动事件生产者仍待实现。

窗口仅映射已确认的字地址，其他偏移、非对齐和字节访问保持拒绝。
两个引擎使用各自的独立配置状态。配置与缓冲区阶段的板级状态版本为 28；
外部事件加入边沿状态后版本为 29，更早版本不接受恢复。
迁移往返尚未验证。

第一次补齐后，原厂已越过 `0x20068000`，继续向偏移 `0x10` 写入，
进一步确认了第二组控制字的启动用途。不能只把最初两条存储映射为
普通字存储而忽略后续成对操作。

`tests/test_board.py` 检查两个角色的配置读回、成对掩码更新、复位、
软件不能制造数据和状态，以及保留偏移和非法访问的拒绝。
原厂验证必须同时检查四个引擎核的执行异常寄存器和实际显示输出。
修正后的组合运行初次到达模式 2 时，四个引擎核的上述异常寄存器均为零。
继续观察后还发现主引擎访问帧缓冲区总线地址 `0x36d59800` 的写异常，
不能推广早期无异常的结果。
操作 14 的完成回调仍保存在 `0xb23f701c`，捕获控制状态
`0xb23f6a80` 为 1；未观察到完成处理
`0x10247dea`、前台画面启动 `0x10540770` 或菜单启动 `0x1044e3ae`。
图形显示请求仍为零，不能认为本次配置映射已提供采样完成。
编译和两个角色的板级检查均通过。
实验参数的来源及限制见[启动温度检查](temperature_parameters.md)。

## 捕获缓冲区的两种地址

原厂缓冲区准备代码 `0x10238336` 为类别 `0x28` 分配 `0x1c8000` 字节。
本次分配描述符保存的缓存地址为 `0x62059800`，经 `0x103c5a7a`
转换为总线地址 `0x36d59800`，然后使用原厂清零入口初始化缓冲区。
主引擎页表 `TTBR0_S=0xb2b74000` 对缓存地址的节描述符为
`0x62014422`，说明实际物理地址仍为 `0x62059800`。

运行时地址表 `0xb2b4145c` 给出缓存区 `0x5f900000..0x62700000`
与总线区 `0x34600000..0x37400000` 的对应关系。
模型现在为缓存区提供 `0x2e00000` 字节存储，总线区作为同一存储的别名。
没有复制或另建第二份缓冲区，也没有改写固件地址表或页表。
这组存储属于主引擎的捕获分配区，不能将它与对端消息地址混用。

越过上述清零后，原厂继续访问缓存地址 `0x50560000`。
同一地址表给出 `0x50300000..0x54900000` 与
`0x30000000..0x34600000` 的对应关系，模型也补齐该存储和总线别名。
两组别名均直接连接本地缓存区，保留其他已存在的地址区域。

板级检查还覆盖缓存区及总线区边界、实际故障地址的共享读回，
以及通过合成 ARM 存储指令从总线地址修改缓存内容并保留相邻数据。

补齐两组存储后，原厂组合运行到达模式 2，再继续观察 15 秒。
开始与结束时四个引擎核的执行异常寄存器均为零，控制器故障寄存器也为零。
这次观察中前台仍为 `APPLV`，捕获控制状态为 1，操作 14 回调仍在等待，
显示请求为零；未到达上述完成、画面启动或菜单启动入口。
因此本次已验证配置访问和缓冲区初始化继续推进，尚未验证采集完成和菜单。
记录见[输入通路与缓冲区验证](../../artifacts/input_path_validation/report.json)。

等待结构的后续恢复见[捕获就绪边界](capture_readiness.md)：

数据异常向量 `0x10100010`，`DFAR_S=0x5d170000`、`DFSR_S=0x8`。

[描述符与转换记录](../../artifacts/capture_grid_descriptor/report.json)

[初始化与转换合同](../../artifacts/capture_memory_contract/report.json)。

### 2026-10-28：处理工作池的首个写异常

[完整写监视](../../artifacts/input_return_write_fault/report.json)再次完成
应用 `3 → 2 → 3`，在随后全按观察阶段捕获第二主核的
`0x10361044`。原指令 `stmhs.w r0!, {r2,r3,ip,lr}` 的目标为
`0xb0100000`，四个写入寄存器均为零。移除监视并单步后，PC 为
`0x10100010`，异常字段为 `DFAR_S=0xb0100000`、`DFSR_S=0x808`。
段表 `0xb2b76c04` 的值 `0xb0114422` 明确把该虚拟地址映射到
相同物理地址。捕获前该核的异常字段均为零。

这是原厂清零函数 `0x10361034` 的首轮存储；现场 `r1=0xa8` 是
已减去 `0x20` 后的值，完整请求为 `0xc8` 字节。现场还满足
`r6=r5+0x98`、`r8=r5+0xba`，与 `0x10271abe` 描述对象构造函数
的寄存器准备一致；该函数在 `0x10271ae4` 清零 `r4` 指向的对象。
静态调用者从共享状态 `0xb186ac94` 取得分配描述符，再读取首字
作为工作地址。该共享状态在 `0x1026fc4e..0x1026fc56` 保存
`0x103a354e(0x268250,1)` 的分配结果。

工作池初始化器 `0x103a34c0` 从常量 `0xaf200000` 加 `0xf00000`

### 2026-10-29：第二组几何与实验 RAW12 输入帧

[扩展通道采集](../../artifacts/input_channel_geometry/report.json)记录
主通道和两组十通道的完整已知控制、多平面地址。结果前后相同，

此前快照的 `input_geometry` 只读取 `0x20069500..0x20069508`。
原厂 `0x1023994c` 实际调用 `0x1020c2d4 → 0x102090a0`，设置

[第二组采集](../../artifacts/input_geometry_banks/report.json)记录到：

| 地址 | 原厂值 | 含义 |
| --- | --- | --- |
| `0x20069514` | `6` | 当前输入模式和打包格式 |
| `0x20069518` | `0x05640000` | 水平方向 1380，起点零 |
| `0x2006951c` | `0x03960000` | 垂直方向 918，起点零 |
| `0x20069a08` | `0x820` | 对齐后的行字节数 2080 |

原厂 `0x10239a42..0x10239a80` 按格式分别计算宽度乘 2、宽度乘
7/4 或宽度乘 3/2，再向上对齐到 16 字节。当前 12 位格式正好
得到 `align16(1380×3/2)=2080`。单帧有效打包行 2070 字节，
余下 10 字节为行填充；918 行合计 1909440 字节。

模型原有但未实现的 `frame-generate` 属性现在提供默认关闭的实验
输入源。只在主引擎、采样源和逻辑通道 `0x200` 已启动时工作，
使用原厂四个地址 `0x54900000/0x56b0d000/0x58d1a000/0x5af27000`
轮换 DMA；地址来自配置，不由宿主硬编码选择。源使用已有实验
相位时钟，周期为功能选择的约 33.333 毫秒，尚非实机测量值。

当前只接受模式字 6、零裁剪起点、偶数宽度和匹配的对齐行长。
每个相邻像素对同取零或 12 位全满值，形成按帧翻转的 64 像素
黑白块；三字节全零或全一使两种常见打包位序在这些样本上等价。
这不宣称已恢复任意亮度的打包位序或 Bayer 顺序。
行填充清零；整帧预先验证必须落在单个可写 RAM 区域，长度上限
16 MiB，跨边界、MMIO、空地址和不支持的配置均不写入。

输入启动请求 `0x20068008` 累积运行通道；精确停止命令 3 清除
`0x600` 通道，使同步 DMA 在后续帧停止，重新启动可继续。其余
已恢复停止命令也清除对应运行位。运行位、DMA 计数和末次地址
纳入迁移状态，版本为 38；复位清零。只读诊断属性为
`input-dma-count` 和 `input-dma-address`。

`tests/test_input_dma.py` 覆盖开关、角色、采样源、启动前不写入、
帧地址轮换、块边界、行填充、目标前后保护、停止/重启、复位、
格式/裁剪/行长拒绝、无效目标与拒绝时无部分写入。
输入 DMA 默认不生成传输完成中断、统计结果或处理完成事件。

[原厂输入源运行](../../artifacts/native_raw12_input/report.json)开启
该属性后正常达到拍摄应用，观测前后 DMA 计数从 1 增至 28，

### 软禁用的结束确认

同一[启动/禁用契约](../../artifacts/input_run_controls/report.json)进一步
执行原始禁用编排 `0x1023c796`、原因解码 `0x1020ad46` 和九组
已登记回调。合成边界为无竞争锁、一个注册掩码组、两项 DMA 句柄指针
和任务/通知记录；寄存器写入、原因翻译、等待字更新均由原始代码执行。
两项句柄指向原始散布初始化描述符 `0xb18067b4/0xb18067c4`，
其 `+8` 操作数分别为 `0x40/0x80`。早期契约将这两个字段设成
合成值 `0x20/0x40`，会错误推导物理通道；当前检查已改用原厂字段。

| 编排等待位 | `0x2006800c` 操作数 | 结束原因（bank / bits） |
| --- | --- | --- |
| `1` | `1` | `0 / 0x200` |
| `2` | `4`、`8` | `0 / 0xa000` |
| `4` | `0x800` | `1 / 0x800` |
| `8` | `0x10` | `0 / 0x80000000` |
| `0x10` | `0x40` | `0 / 0x20000` |
| `0x20` | `0x80` | `0 / 0x80000` |
| `0x40` | `0x20` | `0 / 0x8000000` |
| `0x100` | `0x400` | `1 / 8` |
| `0x200` | `0x200` | `1 / 0x80` |

每组完成回调更新 `0xb26b38c8`，只有全部等待位归零才投递任务
事件 `0x1000`；检查也覆盖另有一位等待时不投递。原始任务
`0x10238d4a` 在禁用标志成立时将它翻译为 `0x041a0004`。
上层输入处理再以任务位 `0x10` 进入 `0x102302ea`，其配置掩码
`0xb1887dcc` 为零时才回收暂存队列并执行后续清理。因此停止
RAW 生产本身不能替代禁用结束确认，也不能直接调用拍摄完成回调。

逻辑通道 `0x80` 独立处理：编排器只写 `0x2006800c=2`，没有
在本次禁用中新增中断使能；整机既有第 7 组掩码 `0xff39` 已包含
结束位 `8`。契约确认其原因解码为逻辑 `2`，回调 `0x102394dc`
使用中断组参数 `0x41072804` 向低层任务发送 `0x20`，再经
`0x041a0006` 向输入任务发送 `0x20`。处理器 `0x10235944`
清除配置/要求掩码中的 `0x80`，并按剩余配置继续停机。它不使用
其他通道的聚合等待字，不能遗漏或用普通聚合完成替代。

[暂存回收契约](../../artifacts/input_pending_masks/report.json)另外直接执行
`0x102302ea`：配置掩码为 `1` 或 `0x80` 时，对等待位 `1` 的
暂存对象保持原样；掩码为零时，原始链表回收该对象、清零等待字，
依次发送 `0x041a0008` 和 `0x041a000c`，状态从 `4/2` 改为
`5/0`。宿主仅记录回调和事件标志更新，并代行无竞争锁，不提供
硬件完成，不改变拍摄上下文计数。

模型在已有 `input-stop-complete` 实验选项下补充上述结束原因。
它先按运行位停止后续生产，只为实际从启用转为禁用的已覆盖通道锁存
结束原因，再通过原有掩码、中断和确认路径交付；重复禁用不再次完成。
当前传输同步执行，因此没有在途 DMA，这一时序是假设，不代表原机
延迟。操作数 `0x20/0x40/0x80` 分别锁存第 0 组位 `27/17/19`，
原厂使能掩码决定回调交付。操作数 `2` 的独立结束原因使用
第 7 组位 `8`；未知位不产生新原因。
