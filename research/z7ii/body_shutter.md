## 引脚与原厂解码

控制器 `0x0803de88` 从 ROM `0x0804ef8f` 读取 17 个资源号，
经资源解析器建立 RAM `0x200184c8` 的描述符指针表。
快速采样映射 `0x0804f021` 的六组二字节记录中，`[9, 1]` 表示
描述符 9 → 半按状态字节 1，`[11, 2]` 表示描述符 11 → 全按状态字节 2。

| 触点 | 资源号 | 描述符索引 | 端口 / 掩码 | 机身开关位 |
| --- | --- | --- | --- | --- |
| 半按 | 97 | 9 | G1 / `0x2` | `0x80000000` |
| 全按 | 109 | 11 | G13 / `0x2000` | `0x40000000` |

两个触点低电平有效。运行中直接读取描述符的 `+8` 端口与 `+12`
掩码，确认上述接线；不是通过扫描尝试引脚得出的猜测。
回调 `0x0803d710` 将状态字节 1、2 分别汇总到 `0x200114e6+3/+4`，
主引擎 `0x10434000..0x1043401c` 解码到首开关字的最高两位。
master 文件 `0x914410/0x914438` 的名称为
`ID_SW0_RELEASE_HALF/ID_SW0_RELEASE_ON`。
外接快门另名为 `ID_SW0_RELEASE_HALF_10PIN/ID_SW0_RELEASE_ON_10PIN`，
其位掩码为 `0x08000000/0x04000000`。

交互台现使用 G1/G13，启动时显式释放机身和外接触点。全按仍先闭合
半按触点，松开全按后保留独立按住的半按。HTTP `/key` 统一调用
`Machine.set_key` 校验输入，修复旧入口仍限定 24 路、拒绝编号 24/25
的问题。五项检查覆盖触点沿、交叠、释放、扩展器路由及实际 HTTP 请求；
HTTP 检查也验证无效编号和布尔值被拒绝。

## 带卡的整机 HTTP 验证

交互台新增 `--sd-card`，把 raw 镜像挂到从引擎 SD 总线，启用已有
SD 主控与链路配置。会话写入临时覆盖层，关闭模拟器或点击“重启模拟器”后丢弃；输入镜像

## 当前边界与旧等待解释的修正

上述整机运行的捕获状态保持 `(2, 0)`；操作 3、14 回调槽均为零，
主引擎卡 presence 槽字仍全零。槽状态仅偏移 `+0x28` 后来为 1。
卡主控报告存在不能证明固件卡服务已就绪；快门开关字正确也不能证明
已经触发曝光、传感器读出或文件写入。

原厂请求路径的另一次观察已确认：`0x10322950` 的模式检查返回 1，
`0x10322966` 走配置分支，`0x1032297e` 的配置返回 1；输入管线入口
`0x10232de6` 在 `0x10322a18` 返回 0，沿常规续行。

`0x103ce6ac` 在同步等待之前尚未命中；它们位于通知续延路径，不能

旧文档“操作 3/14 长期挂起、队列为空，因此初始化不能完成”的结论
只适用于当时更早的模型和输入。本次回调槽为空不是完整初始化的充分

后续应区分实时图像传输、固件卡服务就绪及快门动作接受三个条件。

## 事件 1 的实际来源与参数索引纠正

`0x104bd5d4` 在 `0xb2bb1080` 的 449 条参数记录中查找，确实把
`0x1812` 返回为索引 1。但消费者 `0x104bd90e` 使用字节数组：
使能在 `0xb201c4f0+index`，更新标记在 `0xb201c739+index`。
该路径不会写入上述字事件 `0xb201bdd4`，不能据此推导门控清除。
探针已删除错误的 `event1_parameters` 字段；旧运行记录保留实测
寄存器和门控值，并明确标注此解释修正。

真正的通知映射表在 `0x1094559c`，共 44 条八字节记录。
`0x104bfd24` 查询通知编号并返回应用事件索引，未找到时返回 `0x64`。
相关记录如下：

| 通知 | 应用字事件 | 标记地址 |
| --- | --- | --- |
| `0x0410000b` | 0 | `0xb201bdd0` |
| `0x0410000d` | 1 | `0xb201bdd4` |
| `0x0410000f` | 2 | `0xb201bdd8` |
| `0x0410000e` | `0x22` | `0xb201be58` |

通知路由 `0x104be90a` 在 `0x104be91a` 查询该表，将索引保存在
栈 `+8`；在 `0x104befb6..0x104befba` 把索引与处理后的载荷指针
传给 `0x104bd99e`。后者先写载荷数组 `0xb201c984+index*4`，
再把 `0xb201bdd0+index*4` 写 1。`0x0410000d` 的专用分支
`0x104be9ee` 另把内部状态字节置 2，随后进入这条共有投递路径。
因此初始化操作 14 的成功通知 `0x0410000e` 并不是门控等待的事件 1。

还有另一张三项表 `0xb181c8a8`：`0x041d→1`、`0x1b00→2`、
`0x1b14→3`。它由 `0x104bfcbc` 查询，供 `0x104bd612` 写入
`0xb201bdc0+index*4`，也不等于应用字事件 1。
这三套索引必须按各自基址和写入宽度区分。

`tools/device_registration_probe.py --watch-release` 从复位开始观察
操作 13 的检查入口、异步任务、回调分支、事件 1 的通知映射、门控
清除入口，并记录事件字和门控字的原始写入。API `0x103f24e4`
的参数为零时只是同步检查：操作 14 在 `0x103f254c` 正是这样调用；
仅命中该 API 不能证明已提交操作 13 的异步请求。

[120 秒复位观察](../../artifacts/release_event_boot/report.json)中：
操作 14 的 API、异步任务、回调和界面完成再次全部命中，结果为 0；
操作 13 的 API 仅记录到 `r0=0`、返回地址 `0x103f2551` 的同步检查。
操作 13 异步任务入口 `0x103ef2bc`、回调分支 `0x1020e9c0`、
事件 1 映射结果及门控清除入口均未命中。

事件字观察只记录到 `0x104bddb4` 将 0 写回 0（通知处理期间的复位），
没有记录到置 1；观察次数未达到八次上限。门控字先由初始化复制写 0，
再在 `0x105b05f2` 从 0 写为 1，调用返回地址 `0x105403e9`；
之后没有清除写入。这把先前静态恢复的置位调用点与实际启动联系起来，
也排除了本次 120 秒窗口内事件 1 已投递后被提前消费的解释。
这些入口均为一次命中记录；操作 13 接口的首次同步命中本身不排除
后续再次调用，异步任务与回调各有独立观察点。

下一步需要恢复 `0x0410000d` 对应请求的自然触发条件，不能通过
强写事件字或门控字代替该完成过程。当前仍未观察到有效取景像素，
也未证明曝光、读出或照片文件写入。

## 初始化后的请求与运行时接口核对

[90 秒接口观察](../../artifacts/release_request_entries/report.json)再次确认
初始化操作 14 返回成功，但没有操作 13 的异步任务或状态更新。
操作 13 的请求标志 `0xb23f6a7c`、回调槽 `0xb23f7018` 均为零；
门控仍为 1、事件 1 仍为零。因此当前证据并非“操作 13 已提交后
硬件始终不完成”，而是尚未观察到它的请求。

后续发现另一条独立的全局通知路径：`0x04160003` 经总路由直接
产生 `0x0410000d`，无需操作 13 请求或回调槽。因此上述零值只能
描述操作 13 的局部路径，不能单独解释门控为何未解除，详见
[驱动双位就绪与全局通知](capture_global_ready.md)。

状态更新函数 `0x103edd08` 使用该请求标志。完成分支
`0x103eddaa..0x103eddb4` 取走操作 13 的回调，有回调才经
`0x102282b4` 发送 `0x0410000d`。从复位观察此状态更新入口未命中。
不能把捕获初始化的成功回调当作这条操作 13 完成链的替代品。

同时核对了共享接口 `0x1036096a/0x1036096e/0x10360972`（直接返回 0）
与 `0x10360976`（直接返回 1）：运行时代码与输入固件一致，没有在
启动中被替换为请求跳转。前三个入口在观察窗内均未命中，故不能认定
这些常量返回本身造成当前请求缺失，也不根据相邻地址把它们命名为
操作 13 的公共接口。

后续用 `tools/capture_request_history.py` 对用户提供的全部 12 个
历史更新包做相同的静态对照，见
[历史引用记录](../../artifacts/capture_request_history/report.json)。
每个 master 均通过自身 CRC，包和 master 的 SHA-256 单独记录；
不输出映像内容。操作 13 的入口用固定前序指令与参数 13 的组合
唯一定位，再解码首 `0x780000` 字节中的 BL / 无条件 B.W 目标。
所有版本均只有一条此类直接边，调用前均为 `movs r0,#0`；
全映像中该入口的偶数地址与带 Thumb 位地址均未作为普通四字节
绝对指针出现。三个代表版本为：

| 更新版本 | 入口 | 唯一直接调用点 |
| --- | --- | --- |
| C 1.01 | `0x103e9d70` | `0x103e9dd8` |
| C 1.62 | `0x103f15fc` | `0x103f1664` |
| C 1.70 | `0x103f24e4` | `0x103f254c` |

这不支持把异步调用缺失归为 C 1.70 新增的调用结构差异，但扫描
不覆盖计算得到的目标、其他分支编码或其他执行映像。不能把阴性
结果升级成异步 API 永远不可达，也不能把该 API 当作已经确认的
正常取景启动生产者。实际配置请求的进一步边界见
[配置掩码与工作入口](capture_mode_requests.md)。

全局捕获状态回调登记入口 `0x103f22ca` 则实际执行：收到
`0x10204e3d`，调用者 `0x1020d4b9`，结束后槽 `0xb18695ac`
仍保留该回调。它经 `0x1020e3fe` 进入全局通知处理，与操作 14
使用的跳板 `0x10204d47` 不同。这排除了全局状态回调根本未登记
这一解释；仍需跟踪初始化成功后的父级状态分发与取景请求条件。

## 播放键触发的操作 18 与下级停止等待

`tools/body_shutter_gate_probe.py --playback` 使用原厂播放触点输入 8，
保留心跳并观察停止请求，不写入捕获状态。
[30 秒记录](../../artifacts/playback_capture_stop/report.json)确认：

| 阶段 | 实测 |
| --- | --- |
| 应用动作 `0x1053ba0e` | 动作 `0x1a`；开关字 `0x200 / 0x2 / 0` |
| 操作 18 API `0x103f25ec` | 回调 `0x10632e81`，调用返回地址 `0x10633195` |
| 原厂捕获任务 `0x103ef386` | 实际接收请求 |
| `0x103e7312` | 内部请求 8、参数 3 |
| `0x103e6e94` | 捕获状态从 2 转向 3 |
| 下级请求 `0x103237d4` | 经原厂队列进入驱动 |
| 驱动状态请求 `0x10323198` | 目标 6，原状态 2 |
| 驱动分支 `0x10323392` | 实际状态为 11、模式字段为 0 |
| 子系统请求 `0x10322e3e` | 参数 1，调用返回地址 `0x103233d3` |
| 返回检查 `0x103233d2` | `r0=1`，未执行返回 0 时的同步完成分支 |

原厂状态查表 `0x10225b04` 使用表 `0x118f9c5c`，每原状态一行
20 字节；实测原状态 2、目标 6 的结果为 11。驱动状态转到 11 后
处理器正常返回，不能称为整个核心卡死在一个调用中。

观察结束时捕获状态为 `(3,0)`，驱动状态保持 11、模式字段为 0，
控制块 `+0x14` 字段 `0xb23f6a90` 为 `0x13ec`；操作 18 的一次性回调槽
`0xb23f702c` 仍为 `0x10632e81`，其完成生产者 `0x103e6c0a`
未命中。这与操作 16、17 保留通知回调的情况不同，不能互相套用。
此路径是操作 18，不能根据“停止”名称推断它经过操作 15。

门控仍为 1、输入几何仍为零；播放动作被接受和驱动状态确实改变，
所以该实验提供了超出全按被门控拦截的下游证据。`r0=1` 本身尚未
确定为错误或拒绝，下一步需跟踪 `0x10322e3e(1)` 的队列、异步回调
与驱动状态 11 的后续迁移，不能强制清空回调或控制字段代替它们。

后续加长观察已确认：该短窗口只覆盖不足一个相机计数器秒，驱动并非
永久停在 11。操作 18 后来以失败结果完成，状态列表出现 `0x3f`；
首个事件等待本身返回成功。委托链、计数器时长和结果区分见
[播放停止与观察时间](playback_stop.md)。
