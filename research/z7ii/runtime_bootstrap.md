# 运行时入口与初始 RTOS 配置

本阶段分析 C 1.70 的运行时入口，接通原厂缓存维护、RAM 页表安装和 RTOS 配置前段。
偏移为 EG 文件偏移，运行地址为 `0x10020000 + offset`。固件文件和指令保持不变。

## 连续启动路径

| 步骤 | master | slave |
| --- | --- | --- |
| ARM 入口 | `0x416C60` | `0x1474A8` |
| 取两个范围边界 | `0xD780` | `0xD7C0` |
| Thumb 库初始化封装 | `0x1E0000` | `0x32F40` |
| 原厂缓存维护 | `0xC0CC` | `0xC118` |
| 16 KiB ARM 复制函数 | `0x340F44` | `0x1475B8` |
| MMU 页表切换函数 | `0xD6C0` | `0xD700` |
| RTOS 初始化前段 | `0xE3C18` | `0x156C8` |
| 本批停止入口 | `0xE8F9C` | `0x1A970` |

入口先通过原厂两条 ARM 指令切换为 Thumb；边界获取函数返回 master
`0xB2B70000..0xB2B74000` / slave `0xC18E0000..0xC18E4000`。库初始化封装保存
这些参数，执行种子为 1 的 55 字随机状态初始化和两个默认数据指针设置，然后恢复参数。
随机状态每步计算 `value + (value >> 16)`，以原厂乘数和增量更新，并按索引 54 到 0
写入；两个游标也通过内存检查。这里尚未证明边界的完整分配器用途。

随后返回 ARM，执行两次原厂缓存维护。其中第一次后向 `0x04008FFC` 写入
`0xBABEBABE` 并执行屏障和事件发送。这是次核释放标记的实际写入，模型仍只有一个 CPU，
因此不是多核启动验证。缓存维护按模型 CPU 的缓存描述执行并保存调用者寄存器，
没有替换为空操作。

原厂代码将 `0x10030000` 的 16 KiB 页表复制至 master `0xB2B74000` / slave
`0xC18E4000`，随后短暂关闭 MMU，将 TTBR 切换到该副本，再重新启用 MMU。
源和副本保持逐字节一致。独立负对照在复制后仅将副本的代码段项清零，原厂切换
必须触发取指异常；观察后恢复副本项。源页表始终不变。

## 初始配置结构

RTOS 前段读取处理器访问控制和核编号，走核零分支，清零 48 字节配置对象，然后调用
原厂 `0x2F4` 填入字段。对象位于 master `0xB2B42298` / slave `0xC18B2D14`。
精确地址和字段由 `analyze/runtime_bootstrap.py` 从原厂字面量解码。

| 对象偏移 | 观察到的内容 |
| --- | --- |
| `0x00`, `0x04`, `0x0C`, `0x10`, `0x14` | 五个原厂回调地址 |
| `0x08` | 零 |
| `0x18` | CBAR 基址加 `0x2000` |
| `0x1C` | CBAR 基址加 `0x1000` |
| `0x20` | 定时器中断号 29 |
| `0x24` | 中断槽数 256 |
| `0x28`, `0x2C` | 两个角色相关的内存边界字面量 |

代码将中断相关字段复制到另一记录，读取并保存两级缓存参数，执行 16 字节状态对象及
1024 字节数组初始化，设置状态对象引用，最后发布就绪字 1。本批验证这些内存效果，
停在下一服务初始化入口；该就绪字仅表示本前段完成，不能代表 RTOS 已开始调度。

## 私有外设和中断模型

先前实验 CPU 默认 CBAR 为零。由于固件从 CBAR 动态计算 GIC 地址，本阶段明确选择
实验基址 `0x04000000`，使用原厂页表已有的原地址映射；实际硬件基址尚未确认。
标准 QEMU GICv2 位于 `+0x1000`（分发器）与 `+0x2000`（CPU 接口），一个 CPU、
256 个中断槽，启用安全扩展。该区域与临时栈不重叠。

CPU 通用定时器的非安全物理、虚拟、管理程序、安全物理输出分别接入 PPI 30、27、26、29，
GIC IRQ/FIQ 接入 CPU。GIC 版本和连线是实验配置；安全物理定时器 29 与固件设置相符。
这不是仅返回完成位的寄存器模型：合成 ARM 程序实际接收软件中断 1 和定时器中断 29，
读取 IAR、执行 EOI 和异常返回，最终 IAR 为无待处理中断的 1023。
该实验不验证原厂中断处理程序、任务切换、tick 频率或真实硬件布局。

源码集成增加 GIC 构建依赖，并能更新已有的主板配置段而不重复添加。
配置设备状态布局仍为版本 6；完整主板迁移尚未验证。

## 验证与复现

```sh
python tools/runtime_boot_probe.py --master /path/to/eg1840_mas_01700.bin --slave /path/to/eg1840_sla_01700.bin --qemu .build/build/qemu-system-arm --destination .local/runtime-run
python tests/test_interrupts.py --qemu .build/build/qemu-system-arm --destination .local/interrupt-run
```

2026-10-10，五个原厂启动场景通过：两个角色的原厂路径、两个角色的无效页表副本负对照、
slave 选择位置位路径。成功场景从原厂复位连续执行，未重新指定 PC 或替换指令；
页表由原厂代码复制并安装。
页表目的区、配置及状态对象使用实例 RAM 填充和边界保护，检查原厂写入效果。
状态数组与状态对象相邻，因此保护字位于整个范围外，避免把后续合法写入误判为越界。

两种主板中断合成检查、主板存储／清零检查、22 项 Python 检查、270 项渲染器 ASan/UBSan 检查通过，内存启动、结构和显示回归通过。
证据见 [验证报告](../../artifacts/runtime_boot_validation/report.json)。
下一阶段继续执行 `0xE8F9C` / `0x1A970`，验证原厂服务与中断初始化；完整初始化调度、
任务调度、LCD 和菜单仍未验证。
