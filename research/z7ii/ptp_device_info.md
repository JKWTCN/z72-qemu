# GetDeviceInfo 操作码公告表

C 1.70 中，`GetDeviceInfo (0x1001)` 的操作码列表来自独立的公告数组，
不是逐项遍历命令回调表生成。原始构造函数生成的默认 95 项，与
`ptp_info.json` 中的 Z 7_2 / V1.70 实机记录逐项、按顺序完全一致。
原始镜像及记录的 SHA-256 见
[验证元数据](../../artifacts/ptp_device_info/report.json)。

以下以运行地址为主；master 成员偏移等于运行地址减去 `0x10020000`。

## 构造位置

| 位置 | 用途 |
| --- | --- |
| `0x104643F6`，成员偏移 `0x4443F6` | `0x1001` 的执行回调，依次写入 DeviceInfo 字段 |
| `0x10464354`，成员偏移 `0x444354` | 初始化公告数据的计数、锁和默认列表 |
| `0x10464228`，成员偏移 `0x444228` | 根据内部模式和状态值选择或构造操作码列表 |
| `0x1046417C`，成员偏移 `0x44417C` | 合并已排序的半字数组 |
| `0x104641F0`，成员偏移 `0x4441F0` | 构造少量条件附加操作码 |
| `0x10482844`，成员偏移 `0x462844` | 写出操作码数组字段，转入通用数组序列化 |

`0x104643F6` 在成员偏移 `0x44449E` 调用 `0x10478B44` 取得状态值，
再从 `0xB188B910` 读取内部模式，传给构造函数。偏移 `0x4444B2`
调用操作码字段序列化函数。实机记录的 `functional_mode` 是数据集
中的另一个字段，不能直接当成该内部模式参数。

默认列表由以下两段原始启动复制数据组成：

| 地址 | 内容 |
| --- | --- |
| `0xB188B934` | 19 个标准操作码 |
| `0xB188B97C` | 76 个厂商操作码，末项为 `0x9535` |
| `0xB2A4E71C` | 构造结果：32 位数量加半字操作码数组 |
| `0xB188B911` | 缓存的配置档编号 |
| `0xB188B918` | 缓存的结果指针 |

在模式 0、状态值 0、条件标记关闭时，原始代码构造 `19 + 76 = 95`
项。操作码字段单独序列化后为 194 字节：四字节数量及 95 个两字节
操作码，已核对原始序列化函数的输出。这里没有把整个 DeviceInfo
事务或 USB 收发模拟完成。模式 4、状态值 0 也选择同一配置档，
所以列表匹配不能唯一反推出内部模式。

## 选择、条件附加项与缓存

构造函数把内部模式和状态值映射到编号 0–6 的配置档。已检查模式
0–4、两种状态值，以及涉及的条件分支。部分配置档直接使用
`0xB188BA14` 起的预置数组，其他配置档合并标准、厂商和附加数组。

已确认的配置依赖为：

- 配置读取索引 `0x14`：原始读取函数检查配置基址的第 5 字节是否
  为 `0x6A`。在模式 0 下，条件成立会附加 `0x942B` 和 `0x944B`。
- 配置索引 `0x21C`：影响模式 1 的两组预置数组选择。
- 模式 3 会附加 `0x9010`。

缓存只按计算出的配置档编号命中。条件字节改变而配置档编号相同时，
单独调用构造函数可能直接返回旧列表。探针验证：默认 95 项，改变
标记后仍为 95 项，显式使缓存失效后才变为 97 项。因此比较配置条件
时必须控制缓存状态，不能只改字节再观察同一个结果指针。

## 0x92F0 与配置 0x4D6

实机记录没有公告 `0x92F0`，与默认公告数组一致。已检查的构造分支
不读取 `0x4D6`，也没有把这项配置作为诊断操作码的公告条件。
将 `0x4D6` 分别设为 0 和 1，并使公告缓存失效，默认列表都保持
同样的 95 项，均不包含 `0x92F0`。

与此同时，原始 `0x92F0` 准备回调确实读取 `0x4D6`：零值时返回
失败并发送 `0x2005`，值为 1 时允许继续。公告和准备门槛是两条
独立路径。由实机列表缺少 `0x92F0`，不能推断实机 `0x4D6` 为零；
启动夹具的零值也不是实机配置快照。

## 0x9535 的公告与执行差异

本次确认了公告与已分析执行入口之间的具体不一致：

1. `0x9535` 是 76 项厂商公告数组的最后一项，故实机公开它有明确
   的原始固件来源，不需要假设第二个公告构造器。
2. 命令记录位于表 1 的 `0x119E1D24`，准备与执行函数分别为
   `0x1076F0E8` 和 `0x1076F110`。
3. 分类函数 `0x104789B6` 把 `0x9530–0x953F` 归入选择值 5。
   该表有 `0x9530–0x9533`，没有 `0x9535`。顶层查找返回零。
4. 向原始包检查入口 `0x10463E8E` 提交一参数的合成 `0x9535`
   命令后，观察到返回失败和 `0x2005`；两项命令回调均未进入。
   这比单独查表返回零多验证了实际拒绝分支，但仍是局部执行结果。

已识别的普通命令处理路径在成员偏移 `0x443A26` 调用包检查，
仅成功时于 `0x443A2E` 调用执行包装器。完整镜像中的 Thumb BL /
无条件 B.W 引用检查，未找到另一个直接调用 `0x74F110` 的入口；
该执行函数指针只出现在上述表 1 记录中。通用表选择及查找函数的
已识别直接宽分支引用，也仍集中在当前顶层查找函数。

这不能证明所有其他路由均不存在。普通检查前还有 `0x040F0019`
观察通知，完整 DeviceInfo 序列化后还有 `0x040F0082` 观察通知；
本次没有验证所有运行时订阅者、计算目标的间接调用或其他处理器的
处理路径。公告结果本身也不能证明某个操作已在实机执行成功。
是否存在能处理 `0x9535` 的其他路径，仍需要该操作的实际请求／响应
记录或运行轨迹来进一步区分。当前输入仅记录公告列表，没有这项
操作的响应码，不能把原始镜像中的路由差异直接定性为实机故障。

## 复现

```text
python tools/ptp_device_info_probe.py --master /path/to/eg1840_mas_01700.bin --capture /private/ptp_info.json --output .local/ptp-device-info/report.json
```

[探针](../../tools/ptp_device_info_probe.py)使用原始初始化、列表合并、
配置读取、数组序列化和包检查代码。主机替代边界为合成锁对象、锁、
批量复制和响应捕获。配置变化均在局部实例中完成；没有发送 USB
命令、修改固件或编译项目。发布记录只保存必要的操作码、地址、计数
和哈希，不复制原始通信文件。
