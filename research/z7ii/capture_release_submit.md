# 拍摄提交入口对照

应用门控解除后，机身全按仍未生成照片。为定位实际提交路径，先从
本地命令路由恢复独立入口，再与原厂机身输入的整机执行比较。
本页没有连接 USB 相机，也没有向真实设备发送命令。

## 本地路由与提交契约

`tools/capture_release_contract.py` 执行原厂查找器 `0x10463d70`，
恢复以下三条本地命令记录中的回调地址：

| 命令码 | 记录 | 三项回调 |
| --- | --- | --- |
| `0x100e` | `0x119e15ec` | `0x10490695 / 0x10490a03 / 0x1049063f` |
| `0x90c0` | `0x119e16b0` | `0x10490a7b / 0x10490ac9 / 0x1049063f` |
| `0x9207` | `0x119e18e0` | `0x10490acf / 0x10490b2f / 0` |

这些命令的共有处理路径 `0x10490974` 调用 `0x103ba6ea`。
后者在通过其检查后可调用释放阶段函数 `0x103ba164`，该函数再提交
下级请求并等待完成。静态调用关系不证明机身按键会采用相同路径。

另一入口 `0x103f36fa` 登记操作 `0x3b` 的回调，然后将 12 字节
请求排入任务入口 `0x103f19c1`。该回调槽为 `0xb23f70d0`。
[原厂执行契约](../../artifacts/capture_release_contract/report.json)
使用独立合成参数，验证回调有效且槽为空时返回 0、登记回调并入队；
无回调或槽已占用时返回 1、不入队。宿主仅记录队列提交，不执行
捕获任务。该契约不验证曝光、图像传输或文件写入。

## 原厂任务中的单张请求诊断

`tools/body_shutter_gate_probe.py --capture-submit-on-ready` 在处理过有效
预览帧且原厂门控归零后，提交一次独立的诊断调用。它使用原厂资源 8
任务的调用栈，通过临时回调调用 `0x103ba6ea`，请求五个字为
`(0,1,0,0,1)`：标准拍摄、默认格式和目标、原厂请求标志、单张计数。
这与机身按键观察分开运行，不代表按键已经进入该接口。

`--capture-jpeg` 将请求字节 1 改为 2，对应原厂单张请求的格式
`0x3801`，其余四个字保持相同。[请求构造契约](../../artifacts/capture_request_contract/report.json)
执行 `0x10490872`，覆盖三种格式与默认、卡槽 1、卡槽 2 的九种
组合；默认格式字节为 0，`0x3800/0x3801` 分别为 1/2，明确卡槽
字节为 3/4。宿主只提供合成命令参数及单张模式查询，不执行拍摄
接口，也不以构造正确替代实际编码和文件验证。

`--capture-storage 0/1/2` 分别保留默认目标、选择卡槽 1、选择卡槽 2。
调用器的九种默认/`0x3800`/JPEG 与目标组合逐字对照上述原始构造结果，
不改变调用体或直接写入相机的主插槽状态。实际目标可用性、编码
及卡内文件仍由整机和停机后的检查确认。

`--capture-format-3800` 与 `--capture-jpeg` 互斥，将请求字节 1 设为 1。
同一契约另执行原厂 `0x103ba934..0x103ba94a` 的选择片段：提供
当前格式 getter 的返回值 3 后，默认请求保持 3，`0x3800` 选择内部
格式 1，JPEG 选择 3。没有执行该 getter 的上游状态检查，也不能
单凭此选择把另一分支命名为已实现的 RAW 照片保存。

### 主从程序的不同装载基址对照

[双载荷比较](../../artifacts/compute_program_pair/report.json)在主引擎
中找到相似但不相同的载荷。原始初始化器 `0x1024493a` 使用
文字池 `0x10244a30`：从 `0x122d4740` 读取长度 `0x27800`，
在 `0x10244966` 请求将源 `0x122acf40` 复制到 `0x50200000`，
随后 `0x1024498c` 使用入口 `0x5020c000` 配置服务。这里核对的是
静态代码和文字池，尚未观察这次主引擎装载实际执行。

主程序完整摘要为
`88d114df0058b7680220001fdf2f88dab0acbd753145523a36209224aa19312e`。
两份 161792 字节载荷中，156954 字节原本相同。两组重复地址表
保持相同目标偏移：`+0x2420a` 和 `+0x24e32`，但主程序分别使用
`0x5022420a/0x50224e32`；相邻的十项消息地址表完全一致。

逐字节扫描四字节小端窗口，得到 241 处候选数值，其差正好为
装载基址差 `0x30100000`，且从程序数值落在已装载范围内。
仅在离线副本中用从程序对应字节替换这些窗口后，入口偏移
`0xc000` 起的前 64 字节全部一致，但整段仍有 4356 字节不同。
这些窗口在代码中可能混合操作码与立即数字段，不能全部命名为
指针，也不能把替换规则用于重定位或执行程序。

相比孤立尝试指令集，这份同构对照给出了用于区分地址相关字段与
不变字段的具体位置。它仍未证明两份程序的完整语义等价，尚不能
据此产生计算完成通知或实现 RAW 算法。

双载荷比较进一步识别出一种分散数值候选。将六字节窗口读作小端
32 位字 `A` 和 16 位半字 `B`，仅匹配
`(A & 0xffe00000) == 0xf0000000` 且
`(B & 0xf003) == 0xb001` 的位置，再计算：

```text
value = ((A & 0x1fffff) << 11) | (((B >> 2) & 0x3ff) << 1)
```

该数值反向编码可完整恢复匹配窗口的两个字段。两份载荷均有
12 处模式匹配，其中五处数值随已知装载基址变化，并落在各自
已装载范围内，且相对偏移相同：

| 载荷偏移 | 还原的目标偏移 |
| --- | --- |
| `0x8` | `0xc000` |
| `0x48` | `0x26b84` |
| `0xc04a` | `0x26d80` |
| `0xc0d6` | `0xc0ae` |
| `0xc0f8` | `0xc0de` |

第一处分别还原 `0x5020c000/0x8030c000`，与主从配置入口一致，
给出了外部原厂装载信息的交叉核对。其余七处模式匹配数值在两份
载荷中未随基址变化，仍全部保留在报告，不能当成程序内地址。
该结果只恢复数值字段，尚未识别操作码、执行条件或分支行为；
六字节观察窗口也不能直接当作处理器指令长度。

[候选指令解码检查](../../artifacts/compute_instruction_survey/report.json)
使用本地从发行版源码编译的 GNU Binutils 2.42（启用全部目标），

`0x8030c000` 及两处表目标 `0x8032420a/0x80324e32` 各观察

`tools/controller_actuator_contract.py` 在原始控制器散布初始化后，

提供任务超时事件 `0x80`；这不是整机中的自然超时证明。

原始 `0x0803c324` 的 16 个输入组合验证：模式 0/1 在两路均为高

初始化 `0x08035508` 将资源 `0x26/0x27` 登记在
`0x20018718+0x18/+0x1c`，对应读取包装 `0x08035324/0x08035338`，
即 C6/C7。不能用一个无条件就绪布尔量替代这两路反馈。

`0x0803c5c8` 建立当前位置索引 2、目标 4、方向字段 1、阶段数 3。
在本配置下，反馈顺序为：

| 输入 | 原厂配置的回调 | 位置索引 | 原厂处理后的结果 |
| --- | --- | --- | --- |
| 初始 C6=0、C7=0 | C6 上升沿 `0x0803c22d` | 2 | 等待位置变化，未发结果 |
| C6 上升，C7 仍低 | C7 上升沿 `0x0803c2a9` | 3 | 消费任务 `0x4000`，继续动作 |
| C7 上升，两路为高 | 无需下一位置边沿 | 4 | 动作状态 1，发送 `0x02060021`，随后 `0x02060015/20` |

保持输入不变并执行原始超时事件，则得到 `0x0206001f`、首字节 3。
继续运行原始适配链 `0x08035480→0x08034edc`，该值写入
底层 `0x2001756e` 并投递任务 `0x20017598` 的事件 `0x20`。
实际执行底层任务后，经 `0x080369a0` 将 3 写入通道 9 的状态
`0x200135a0`，投递 `0x200135f0` 的 `0x10000`。

因此位置反馈缺失可以通过原厂代码产生候选连线实验中观察到的
同一通道状态 3。这是对失败来源的有界解释，尚未在那次整机启动中
直接捕获超时入口。实际电机方向、校准、速度、传感器物理连线及
整机拍照仍未验证；本轮没有增加自动反馈或修改整机状态。

模式 1/2 分别经 `0x03030024/25`、任务事件 `0x10/20` 转为处理通知
`0x03030004/05`。计时器 `0x10242124` 只降低输出，不清除活动状态，
也不产生完成通知；输入回调 `0x102422ec` 才负责取消计时器并完成通知。
GPIO、计时器和任务接口在隔离执行中由记录器接收，输入回调显式调用，
故这不是整机自然完成的证据。

[采样生产者整机观察](../../artifacts/capture_second_step_producers/report.json)
使用与上一轮相同的可选握手及执行器配置，未供给宿主 G8 或位置边沿。
观察 474.922 宿主秒、4.680786 计数器秒，提交后 3.001873 秒，达到
3 秒目标。第一次 GPIO 请求及输入回调均命中，控制器在 129436549 tick
重新开放 G8 上升沿；最终仍为步骤数 1、动作 2，未出现第二次请求或结果 9。
诊断调用者仍为 fixture，完成计数为零；完整 RAW 一帧、处理帧 34，
LCD 缓存含 16、235。该窗口未验证照片编码或写卡。

当前采样模式为 5，`0x102e9482` 的阶段 5 对该模式不直接发出
`0x04200285`，不能把此处未命中当作异常。另一生产者位于采样任务
`0x102e958a` 的事件 `0x400` 分支：它经下层委托将 `0x04200285`
转为 `0x04200185`。末尾计数器运行选择为 `0x160`，通道 5/6 的
事件配置均为 7，但没有捕获回调记录。通道 6 的双路捕获及实际输入
来源仍待验证；不能通过直接设置任务位或补发第二次完成跳过该边界。

集中探针现在每 15 宿主秒在私有运行目录保存标记 `incomplete=true`
的检查点，正常关闭时随目录清理。中断运行的检查点只能作为部分正向
记录，不能用来证明事件在完整观察窗口内没有发生。

[捕获配置观察](../../artifacts/capture_counter_configuration/report.json)

### 机身快门的系统模式输入路径

[系统模式通知观察](../../artifacts/body_system_notifications/report.json)
从处理后的预览就绪开始，在半按前安装七个只读观察点，保持既有输入、
帧处理和时钟配置。观察 120.750 宿主秒、6.845063 计数器秒；全按保持
0.2775980625 计数器秒，然后释放两级触点。

半按、全按、释放各进入一次 `0x102a6984`，紧接着进入
`0x1029993e`。实际系统模式对象是 `0xb1819604`，其首字指向
`0xb1818bd0`。三个转换中，当前/之前模式均为 `[4,2]`，系统上下文
`+0x320/+0x324/+0x328` 三组禁止字和 `+0x32c` 待处理请求均为零。
每个观察点的 32 次配额均未耗尽。

调用者 `LR=0x1020e05d` 与原始 `0x1020e052..0x1020e05a` 一致：
系统从当前对象 `+8` 取输入回调，传入原始输入对象
`0xb1f7a5ac`。该回调先检查输入组中的 `0x200` 变化；只有这一位变化
且根对象的 `+0xa4` 查询为零时，才发布通知 4。随后它无条件调用
`0x1029993e`，再转入 `0x102a7892`。不能把该回调没有发布通知解释成
全按丢失，也不能把其他模式的 `0x10245f5e` 策略套用到当前模式。

本窗口未命中 `0x102a6970` 系统通知、`0x1020dad2` 基类通知、
`0x1020d384` 模式请求，也未命中所观察的拍摄 API。
全按仍经过应用动作 `0x14` 及原始回调。处理帧为 184，主 RAW 为零，
拍摄状态最终 `(2,0)`。这排除了本次按键转换期间的三组模式禁止标志，
并不证明所有应用层拍摄条件均已满足；照片编码和写卡仍未验证。

### 原厂卡参数与有效 SDHC 介质的机身对照

观察工具现通过原厂参数描述符读取卡相关标量，而不再仅使用 SD 主控的
卡存在位。原始 `0x10101f52` 以参数编号高字节选择
`0x11906924` 的 28 字节组记录，取 `+0xc` 的起始索引，再加低字节；
`0x101017d8` 据此访问 `0x118fb024` 的 16 字节描述符并读取实际存储。
探针检查类型、大小及地址均匹配 C 1.70，再只读记录当前值。

`0x118af840..0x118af890` 中的名称记录确认了以下参数身份：

| 参数 | 含义 | 实际存储地址 |
| --- | --- | --- |
| `0x127a` | `eDSID_Setting_SlotEmptyReleaseLock` | `0xb258700c` |
| `0x2f00` | `eDSID_CardState_CardSlot1` | `0xb258bfa8` |
| `0x2f01` | `eDSID_CardState_CardSlot2` | `0xb258bfac` |
| `0x2f0e` | `eDSID_IsValidCardInfo` | `0xb258c0d0` |
| `0x1b04` | `eDSID_ImageSaveMedia` | `0xb255211c` |
| `0x2600` | `eDSID_ConnectStateUsb` | `0xb25526ac` |

原始 `0x1042c9f8` 根据这些参数计算 `0x3600`、`0x1916`；目前保留
它们的编号，不为其零值赋予未经证明的完整拍摄许可语义。

[512 MiB 介质记录](../../artifacts/body_card_admission/report.json)
观察 60.672 宿主秒、3.341782 计数器秒，
[4 GiB SDHC 记录](../../artifacts/body_card_admission_sdhc/report.json)
观察 90.688 宿主秒、5.096848 计数器秒。两者都在处理过的预览就绪后
半按、全按并释放，未调用诊断拍摄入口；卡使用临时快照。

| 参数 | 512 MiB，前/后 | 4 GiB，前/后 |
| --- | --- | --- |
| 无卡释放锁 `0x127a` | 1 / 1 | 1 / 1 |
| 卡槽 1 `0x2f00` | 0 / 0 | 0 / 0 |
| 卡槽 2 `0x2f01` | 2 / 2 | 1 / 1 |
| 卡信息有效 `0x2f0e` | 1 / 1 | 1 / 1 |
| 保存介质、USB、`0x3600`、`0x1916` | 均为 0 | 均为 0 |

旧容量下的 SD 字节/扇区寻址差异已有独立命令跟踪，见
[介质容量对照](card_file_service.md#介质容量与地址单位对照)。

不再把 512 MiB 镜像当作可写卡已经就绪的依据。

4 GiB 对照中，全按保持 0.2777949167 计数器秒，处理帧 134，
主 RAW 为零、捕获仍为 `(2,0)`，所观察拍摄 API 未命中，四核异常字段均零。

其他存储或应用层条件已经全部满足。尚无照片编码、照片文件或写卡完成证据。
