# 内部延时计数器

分析固件并检查原厂运行，设备配置任务的一处等待来自
`0x2c010000` 的十二通道模块。此前该地址范围只有寄存器存储，
不会随时间产生事件。本阶段增加实验性内部延时模式，并保留其他模式
的寄存器存储；尚未确认的外部时钟、捕获、比较和输出功能不产生事件。

## 地址与分发

通道编号为 0..11，下面两组地址使用相同编号：

| 地址 | 已观察到的用法 |
| --- | --- |
| `0x2c010000` | 初始化时写 1，再写 0 |
| `0x2c010004` | 初始化时写 1 |
| `0x2c011000` | 按通道设置或清除运行位 |
| `0x2c011004` | 暂存随后提交的初值 |
| `0x2c011008` | 写入接收该初值的通道位 |
| `0x2c01100c` | 初始化写 0；模型按通道中断屏蔽处理 |
| `A = 0x2c010000 + (通道 + 1) * 0x100` | 通道事件配置 |
| `A + 0x10` | 中断处理读取后原值写回的状态 |
| `B = A + 0x1000` | 配置前写 1，再写 0 |
| `B + 4` | 八位分频值，除数为写入值加 1 |
| `B + 8` | 终止计数值，该路径写 `0xfffffffe` |
| `B + 0xc` | 当前计数的只读接口 |

中断表 `0x1078a73c` 包含十二组 INTID 与处理入口，
INTID 为 `172 + 通道`。第 9 通道使用 INTID 181，入口
`0x1036ea72` 选择软件描述符 `0xb1806460`，进入公共处理入口
`0x1036ea8a`。公共处理读取 `A + 0x10`，原值写回，再携带通知码与
读出的状态调用注册回调。模型按写一清除处理状态，未清除的原因维持
对应中断线；两侧引擎使用各自独立的实例和中断控制器。

## 配置任务等待链

设备初始化 `0x10322886` 经 `0x10232de6` 提交配置。
任务分发入口 `0x10397b5c` 处理事件 `0x1000`，进入 `0x1039a062`，
把 `0xb1868310 + 1` 置为 2，然后调用 `0x10397526`。
保存的任务栈把等待进一步连接到：

`0x10397526 → 0x1026d7be → 0x102e9e72 → 0x102e91ec → 0x102e8f76`。

最后一级启动第 9 通道，并在 `0x102e7cb6` 等待事件对象
`0xb1868718` 的位 8，超时参数为 3000。运行上下文 `0xb1868830`
的 `+0x30` 字节为 1 表示计数进行中；`+0x38` 为目标次数 1，
`+0x3c` 是已观察次数。此次配置使用：

| 配置 | 值 |
| --- | --- |
| 通道 | 9 |
| `A` | 1 |
| `B + 4` | 0 |
| `B + 8` | `0xfffffffe` |
| 暂存初值 | `0xffffcb43` |
| 提交位 | `0x200` |

回调 `0x10371672` 把事件交给 `0x102eb748`。状态位 0 使次数递增；
达到目标后调用 `0x102eb7fa`，后者向 `0xb1868718` 设置位 8。
等待结束后的原厂清理路径 `0x102eb846` 停止通道。模型只提交硬件事件，
不写任务事件对象、次数、完成标志或业务回调表。

## 实验时序与边界

原厂延时换算先把输入乘以 50，再选择除数并取补码初值。
`0x102e7d84` 将除数减 1 写入配置字节；驱动随后将该字节写入 `B + 4`。
模型据此暂用 50 MHz 时钟：首次从提交的初值开始，到终止值的间隔为
`(终止值 - 当前值 + 1) * (分频值 + 1) * 20 ns`。
这是软件换算支持的实验假设，
尚无物理时钟测量或硬件规格确认。此次配置给出的首次间隔为 270000 ns。
到期后置状态位 0，并从零重新计数；同一配置的后续完整间隔约为
85.9 秒，不能把首次预置值当成每次重装载值。后者会在输入为零、
首次延时只有一个计数时造成错误的持续短周期中断。

通道提交时设置当前计数，随后只修改暂存字不改变已提交的初值。
停止保留当前计数和未确认事件，再启动从保留计数继续。屏蔽中断
不停止计数，重新开放可报告保留状态。通道复位清除计数和事件，
整机复位同时取消定时器。运行中修改终止值或分频值时先保存当前计数。

最初模型只对分频值 0 计时；后续原厂运行中，第 7 通道使用 `0x31`
并保持等待。此前把该字段称作其他时钟模式的解释已更正。
当前实现支持八位分频值：0、1、49 分别给出实验时钟 50 MHz、25 MHz、
1 MHz。高于八位范围的保留配置不自动计时。当前计数大于终止值的配置
也不自动计时；溢出绕回、物理引脚及捕获、比较功能尚未建立。
原厂第 5 通道的分频值为 1，事件配置为 7；计数可以推进，但没有外部
采样来源时，不产生边沿捕获事件。

专项检查 `tests/test_delay_counter.py` 使用合成指令，检查延时前后状态、
十二路中断映射、写一清除、停止后保留原因、通道与整机复位、
暂存初值锁存、动态计数、停止续计及两侧引擎隔离。
检查期间不需要固件或机身参数文件。

原厂组合运行使用实验性参数输入；这些输入不代表实际机身校准数据。
本次已经观察到第 9 通道回调，以及配置等待返回到 `0x10397562`，
随后执行 `0x10397022` 和 `0x102420ac`，在 `0x1039a0f0` 返回 1。
这证明该次配置等待已解除，尚不代表设备初始化或菜单完成。

修正首次预置与后续周期后，原厂上下文中的已观察次数保持为 1，
配置任务回到普通事件等待，不再连续执行计数器回调。
随后向主引擎发送各一次第 0、6 路输入上升沿并释放电平，原厂清除了
输入状态，但队列仍为空，操作 3 和 14 的回调仍在等待。
图形上传成功次数为 16，显示请求和表面地址仍为零；四个引擎核的执行
异常寄存器及控制器故障寄存器均为零。记录见
[延时计数器验证](../../artifacts/delay_counter_validation/report.json)。

## 分频延时后的下一处访问

继续运行时，第 7 通道的分频值为 `0x31`，终止值为 `0xfffffffe`，
首次预置值为 `0xfffff45b`，运行使能位已经设置。
原厂回调为 `0x102d6e92`，通过事件对象 `0xb18a764c` 的位 1 唤醒等待。
原模型没有对该分频值计时，当前计数保持为预置值。

补齐分频后，原厂中断 179 自然进入该回调，通知码为 `0x42181808`，
状态为 1。专项检查同时验证 49 分频的延后触发和计数速度，
以及保留高位配置不会产生时钟。

随后主引擎在 `0x10295bd4` 向 `0x20061004` 写字时发生访问异常：
`DFAR_S=0x20061004`、`DFSR_S=0x808`，保存的异常帧也给出该指令地址。
该入口先写 `0x20061004`，再写 `0x20061024`，属于采样同步配置。
另外三个引擎核和控制器未记录执行故障。显示请求仍为零，菜单未验证。
这是分频延时解除后暴露的新映射边界，不能继续沿用上一阶段四核无异常
的结论。记录见[分频延时验证](../../artifacts/delay_prescaler_validation/report.json)。

该访问已在后续[采样同步配置](sampling_sync.md)阶段接入，原厂能够
完成上述两项写入；后续输入处理配置和显示仍待完成。

## 有限次数配置与输出计时器

自动 GPIO 握手使返回流程越过旧等待后，输出计时器暴露了另一项
未建模能力。原厂描述符 `0xb18063ac + 通道 * 20` 的寄存器表
`+0x50/+0x54/+0x58` 仅对通道 0..4 非零，分别指向：

| 地址 | 当前恢复的用途 |
| --- | --- |
| `B + 0x38` | 限次控制使能 |
| `B + 0x3c` | 目标次数 |
| `B + 0x40` | 已完成次数读取 |

构造器 `0x10371a96` 将参数 0 转为 `(使能 0,次数 1)`，非零参数
转为 `(使能 1,原次数)`。配置函数 `0x1036e996` 对支持的通道写入
前两个寄存器，并将事件配置的位 3 置为 1；不支持时返回 2。
次数读取入口为 `0x1036e9e6`。
[有界原厂执行](../../artifacts/delay_limit_contract/report.json)直接执行
构造器和配置函数，覆盖参数 0、1、2 及不支持的第 7 通道，记录实际
寄存器写入。这里使用合成 MMIO，不模拟真实器件到期。

输出包装器 `0x10371828` 明确选择次数 1。返回流程的零延时参数
被 `0x10394ec8` 转为 1，最终终止值为 0、分频值为 49。旧模型
忽略限次配置，会持续以 1 微秒周期报告状态位 0；
[原厂快照](../../artifacts/playback_return_automatic_handshake/report.json)
中第 4 通道仍运行且原因挂起，处理与采样续行均未完成。

据上述配置及调用者只需要一次输出完成的行为，模型实验性解释为
有限次数运行：每次终止计数推进已完成次数，达到非零目标时附加
状态位 3 并停止重新调度。运行选择位保持软件锁存；后续寄存器
写入不会使已达限值的通道继续计时。状态确认不清除完成次数，
完成次数只读，通道复位及整机复位清零。通道 5..11 保持既有行为。
这一到期及停止语义仍需原厂运行核对，不能视为实测硬件规格。

编译与扩展后的 `tests/test_delay_counter.py` 检查通过：保留十二路
延后到期、分频、连续计数与隔离检查，并在两侧引擎检查前五路
次数 1、第 4 路次数 2、限次事件单独路由、分别确认状态位、
禁止修改完成次数以及复位重臂。原厂 LCD 像素与拍照写入仍待验证。

限次修复后的[原厂返回记录](../../artifacts/playback_return_limited_timer/report.json)
实际读到第 4 通道目标 1、完成次数 1、原因已清除。处理分支在
0.012151 个计数器秒返回，后续采样完成通知及拍摄应用主入口均已
命中。它支持本次限次解释在该原厂路径中的作用；尚未确认真实
器件的计时精度、全部计数模式或迁移行为。
