# 从引擎访问主引擎存储

传输复位完成后，从引擎已注册运行时服务，但初始化元数据时出现
`DFAR_S=0x42920f40`、`DFSR_S=8` 的访问异常。
异常上下文保存的 PC 为 `0x10167844`，对应 64 位读取指令；调用者
`0x10060dda` 正在复制 32784 字节，目标为本次分配的 `0xc1894940`。
该访问不是外设寄存器读取。

原厂转换函数 `0x10060f9c` 使用 24 字节记录，包含角色、范围长度、
总线基址和软件基址。运行中表位于 `0xc1014ad4`，共有五条记录。
角色 0 的记录为：

```text
00000000 10000000 40000000 b0000000 00000001 00000007
```

转换先检查请求落在原始范围内，再计算
`bus_base + source - software_base`。因此主引擎 `0xb2920f40`
对应从引擎视图中的 `0x42920f40`。
只读检查确认，前者实际包含待复制的元数据，而从引擎自己的
`0xc2920f40` 为零；使用本地同偏移 RAM 会读到错误内容。

双引擎机器现在把从引擎的 `0x40000000..0x4fffffff` 映射到主引擎
容器的 `0xb0000000..0xbfffffff`。别名共享已有 RAM，不分配副本，
保留源容器中的空洞。独立实验窗口保留较高优先级。
主引擎视图中的 `0x46000000` 仍指向从引擎消息区；从引擎同地址
则按照上述转换表指向主引擎 `0xb6000000`，不再覆盖为本地消息区。

修改后，原厂 `0x101356c6` 执行且复制函数返回 1。
随后卡服务回调 `0x100b5d22` 收到槽位 1 的查询请求。
后续清零 `0xc5307240` 又遇到 RAM 缺口：原厂初始化表包含
`0xc5004000` 起的 `0x00fbf140` 字节清零记录，终点为 `0xc5fc3140`。
从引擎启动存储现补到 `0xc6000000` 之前，保留消息区边界。
此范围是实验 RAM 映射，不能作为实际内存芯片容量结论。

最终有界运行越过这两处访问，进入新的外设访问边界。
异常 PC 为 `0x1008a3b4`，输入寄存器中的设备基址为 `0x2b200000`。
该设备合同仍需分析；本阶段尚未观察到菜单启动或正常启动完成。

`tests/test_peer_memory.py` 使用合成 ARM 64 位读写检查多个主引擎
RAM 区域、写入回到所属 RAM、本地 RAM 隔离及空洞访问异常。
板级检查包含新增从引擎启动存储地址；两种角色均通过。
共享别名检查已加入 CI，未声称执行远程 CI。
验证记录见 [共享内存验证](../../artifacts/peer_memory_validation/report.json)。
后续已补齐该外设初始化所需的配置读回，见
