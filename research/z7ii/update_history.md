# 十二版本更新包与引导材料来源复核

2026-10-24 分析本地 Z7 II C 1.01 至 C 1.70 的全部十二个更新包，
用于核对早期版本是否提供新的 B8 来源。结果见
[检查元数据](../../artifacts/update_history/report.json)，复现入口为
[历史固件探针](../../tools/update_history_probe.py)。

另一次独立启动检查把每个更新包的主、从引擎分别加载到
`0x10020000`。全部 24 次运行都从成员入口执行了原始复位指令，
核对了六组模式栈、临时栈上的保存值、两次延时循环的终值和四个
配置寄存器的回读值。每次均在系统初始化入口 `0x10020394` 停止。
这个检查覆盖单引擎的早期启动。
见[逐版本执行结果](../../artifacts/early_boot_history/report.json)和
[复现工具](../../tools/early_boot_history.py)。

为同一工具提供 `--transport-reference` 并指定 C 1.70 从引擎镜像，
还会逐版本配对启动主、从引擎，开启传输链路。探针在各版本从引擎中
定位接收例程，执行到该处后，从主侧 `0xB7CF0000` 和从侧
`0x47CF0000` 读取同一队列头。十二次运行中，两侧的 24 字节均相同，
写入索引和消费索引均为 1。C 1.50、1.62、1.70 的接收观察点位于
从引擎成员偏移 `0x40F7E`，其余九版为 `0x40E36`。

从引擎消费启动消息后，十二版主任务都在 `0x10200192` 以参数 1000
调用等待函数，并返回到循环末尾的分支。此时按各自镜像的初始化复制表
定位控制器回调表，在主引擎 RAM 中核对表指针和前两个函数指针。
C 1.01 的表位于 `0xB1894F78`，C 1.70 位于 `0xB18A7A78`。
这次运行的观察终点是主任务等待返回，历史版本的菜单仍待验证。

`--controller-link` 单独启动带机身控制器的组合机型，三个固件成员取自
同一更新包。十二个包涵盖四份不同的机身控制器镜像。每次复位后均从
控制器 RAM 核对了搬运的向量表，然后在固件校验循环中读取接收缓冲区。
十二次均收到 256 字节的主引擎请求，载荷长度为 28，帧的八位累加和
为 `0xFF`，原始校验函数走到返回 1 的分支。

在同一次运行中，主引擎随后通过应答校验。逐字节比对主引擎接收缓冲区
和控制器 DMA 发送缓冲区，十二版均为相同的 256 字节，且发送剩余计数
为零。控制器接着在异常号 39 中执行确认回调，GPIO G6 输入为高。
主引擎接收缓冲区地址从现场寄存器读取，C 1.01 为 `0xB1D07F88`，
C 1.70 为 `0xB1D1AB28`。各版本的应答摘要和观察地址见
`controller_request.response`。

应答确认后，探针在控制器 I²C 总线地址 `0x22` 的扩展器上依次把
输入 9 置高、拉低、恢复高电平。每一步均等待机身控制器将三个端口的
样本写入 RAM，并从主引擎的按键解码例程读取第二个开关字。十二版
的 MENU 位均依次为 `0`、`0x8000`、`0`。该字地址由运行中的
寄存器取得，1.01 为 `0xB25D066C`，1.70 为 `0xB25EAEB0`。
各阶段数据见 `controller_request.menu_samples`。

探针还根据五个 GUI 事件名的固定顺序，从各版本初始化数据中定位应用
管理器，并在运行时核对 RAM 内的五个入口指针。C 1.01 的管理器位于
`0xB180E4AC`，C 1.70 位于 `0xB1811E40`。在首轮控制器应答后
立即做上述按键实验，十二版在三个采样点的初始化标志均为 0，
五个就绪标志均为 0，前台索引均为初始值 5。验证菜单切换需要先等到
拍摄应用就绪，再触发按键并检查前台索引与显示输出。

整机菜单探针按三个成员的摘要核对更新包，再从主引擎定位同步等待调用和
应用管理器，读取该版本已验证的开关字。对 C 1.01 和 C 1.70 使用相同的
实验电池对端、参数映像、资源头和同步脉冲条件。C 1.70 从拍摄前台进入
菜单，松开 MENU 后仍停在菜单；抓取的 720×480 图形表面有 480 行含非黑
像素。C 1.01 的 24 次基线采样覆盖至虚拟时间 6.77 秒，五个应用均就绪，
最后前台仍为 APPIDLE，同步等待断点未命中。此次 C 1.01 运行止于按键前，
其菜单响应仍待验证。[整机对照结果](../../artifacts/early_boot_history/menu_comparison.json)

C 1.01 的后续运行从模式对象表 `0xB1815178` 读到系统上下文
`0xB1814DAC`。转移禁止标志在此版的偏移为 `0x308`，C 1.70 为
`0x320`。15 个采样点中前五次系统模式为 0，随后为 1，前台始终为
APPIDLE。三组禁止标志均为 `[2, 0, 0x40]`，延迟请求标志均为零。
这些采样覆盖到虚拟时间 2.63 秒；采样之间的短暂请求仍需通过模式切换
调用点观察。原始计时和状态变化见同一对照结果的 `mode_followup`。

用 `--trace-modes` 从复位开始跟踪模式选择及延迟设置函数，两版都先请求
模式 0，再从 0 请求模式 1。1.70 在 87 个计数器 tick 后从 1 请求模式 2，
该次调用的返回地址为 `0x10246fa0`；随后又从 2 请求模式 4，并在菜单键
释放后保持 APPMENU。1.01 到第 15 次采样（约 3.00 秒虚拟时间）仍处于
APPIDLE，期间没有请求模式 2，也未进入发送同步脉冲和菜单键的阶段。
两版均未命中延迟设置函数。各次调用的参数和返回地址见 `mode_call_comparison`。

进一步跟踪事件入口及通知调用点（`mode_event_comparison`），1.70 在进入模式
1 后收到两个字节为 `01 01` 的事件。调用来自 `0x10204c6a`，随后在
`0x10246f9c` 发出参数为 `(8, 1, 0)` 的通知，回调指针为 `0x10204bdb`。
17 个计数器 tick 后，模式选择函数收到目标 2。此次运行进入拍摄前台并解码了
菜单按键，但在 15 个菜单启动窗口内仍停在拍摄前台。1.01 运行至虚拟时间
2.67 秒时，两处事件断点均未命中。其对应的间接调用在 `0x10204c6e`，
前面依次检查模式对象偏移 `0xd4` 和系统对象偏移 `0xbc` 处回调的返回值；
任一非零均跳过发送。两者均为零时还要经过后续分支。尚需运行时记录确定
1.01 是否到达这组检查，以及实际走了哪个分支。

后续运行在模式 1 的进入函数找到了更早的分歧。两版各执行一次配置完成
回调，当时子状态均为 5。进入模式 1 后，两版的首项检查均返回 1，随后
要求就绪位图的低两位同时置位。C 1.01 在 `0x10245b0e` 比较所得值 2
与要求值 3，转入等待，未执行上述两个发送前检查。C 1.70 在
`0x10246d32` 得到 3，继续发送通知，两个发送前检查均返回 0。
配置完成回调在两版各只命中一次；1.70 的第二次通知沿模式入口尾调用
保留了相同的返回地址。运行记录见 `mode_gate_comparison`。

1.01 的就绪位图来自系统上下文偏移 `0x330`，1.70 对应偏移为
`0x348`。1.01 的 `0x1020cbfa` 检查载荷首字节，为 1 时在
`0x1020cc18` 写入缺少的位 0，否则在 `0x1020cc08` 清零该位。
下一步可从这两处追踪启动期间收到的载荷及其来源。

三轴采样输入使 C 1.01 通过了这项检查。未连接加速度计时，控制服务
收到类型 4、1、2 的更新，待更新位图达到 `0x0d`；至 62038104 个
计数器 tick，系统仍在模式 1，没有命中就绪消息入口。C 1.01 的总线
写函数在 `0x103d1742` 指定地址 `0x1d`。在相同存储和按键配置下，
用 `--acceleration-sample 0 0 1024` 向该设备提供原始轴值，固件先发出
类型 8 更新，随后位图达到 `0x0f`。通知 7 的状态为 15，系统消息
`0x02000005` 的载荷为 1。至 56174606 tick 已请求模式 4，随后进入
APPLV 并识别菜单键。该观察止于拍摄前台，未看到菜单应用启动。

C 1.10 用相同轴值也执行了模式 0、1、2、4，最后一次采样的前台为
APPLV，观察窗口在按键前结束。C 1.70 未连接加速度计的对照运行已收到
类型 8 更新并进入 APPLV。三个版本的逐值首次命中时间及各次运行的终点
见 `acceleration_readiness_comparison`。这些轴值为模拟输入，单位为
有符号 12 位原始码。

本轮没有取得真实 B8 或 K8，没有验证任何版本的头部摘要，也没有完成
菜单整包刷机。结构校验、合成输入执行与真实整包认证分别记录。

## 更新结构与主固件调用点

十二版均包含 EX、TPJ、master、VR、slave 五类成员，目录头长为
`0xD0`。60 个成员 CRC 与 12 个容器 CRC 均通过；目录中没有独立
引导区成员。解码使用已核对的 C 1.70 查表数据，每个历史包再独立
检查标记、目录边界、成员 CRC、容器 CRC 和尾部填充。

下表偏移均相对于对应 master 成员。静态检查寻找加载
`0x10000088` 到 r0、传入栈地址与种子、连续调用设置与检查函数的
完整指令序列；这是有明确参数的调用候选，不等于已执行原始调用者。

| C 1.10-01 | `Ver.01.10.e0` | `0x2AC45A` |
| C 1.20 | `Ver.01.20.c0` | `0x2AC956` |

相同的连续两张变换表；表内容相同本身不能证明历史版本执行相同的
摘要算法，也不能证明各版本或各机身拥有相同 B8。

## 映射、初始化表与局部执行

24 份引擎成员的页表均把 `0x10000088` 恒等映射，描述符为
`0x1000C426`。这些是对包内页表的静态解释，未在本轮执行页表安装。
每份 master 初始化表有 20 条记录，slave 有 15 条；其中没有复制或
清零目标与 `0x10000000–0x1001FFFF` 相交。包内引擎成员从
`0x10020000` 开始，其文件前段也不能当作前面的引导区内容。

对十二处设置调用的目标分别执行两组输入：全零和固定非零合成字节，
共 24 次。主机设置 r0 为引导地址、r1 为所观察种子、r2 为合成
`Z_7_2` 字符串，准备独立栈与返回地址，然后直接进入设置函数。
固件自身的复制与字符串函数完整执行，没有主机函数替代。

全部调用均正常返回；内存访问记录覆盖给定引导地址的全部八字节，
没有向该范围写入。上下文 `+0x0C` 与所给合成输入逐字节相同，
`+0x14` 保存种子，`+0x18` 保存机型串。这确认这些设置函数消费
已有输入，而非在本次调用中产生它。

这没有执行原始调用者、完整启动或后续摘要比较；主机提供的合成
输入不是机身 B8。该结果也不排除其他例程、更早阶段或其他存储
主设备写入引导窗口。

## 有限连续字节候选

检查每份不同辅助成员的全部内容，以及每份不同引擎成员的前
`0x20000` 字节。按候选区域 SHA-256 去重后共 31 段，检查
6,977,345 个连续八字节窗口。每个窗口分别按原始 B8 和最终 K8
解释，对已锁定身份的原厂 C 1.70 包比较摘要，共 13,954,690 次，
没有匹配。C 1.70 的变换关系见[整包摘要说明](firmware_update.md)。

本轮没有遍历历史引擎成员的其余内容，也不覆盖任意指令构造、
非连续编码、运行时输入或整个八字节空间。未命中不能证明分发包
中不存在构造方法。报告仅保存来源偏移、哈希、地址、计数和结果，
不保存成员内容或候选字节。

## 复现与下一边界

```text
python -B tools/update_history_probe.py --master <C1.70-master> --packages <history-directory> --report .local/update-history/report.json
python -B -m unittest checks.test_update_history checks.test_update_container checks.test_upgrade_signature -v
```

需预先具备现有固件分析脚本使用的本地依赖。本轮使用指定的
Python 3.12，18 项针对性检查通过，没有编译项目。探针不导出固件，
不修改原始输入，也不运行存储编程或菜单安装。

历史版本扩展了输入范围，但尚未补上真实引导内容或初始化程序。
可继续验证的输入是覆盖主引擎低端引导区的原始镜像，或能说明
`0x10000088` 实际读写内容及上下文的跟踪资料。取得后应先复现
未修改原厂整包的头部摘要，再验证菜单认证与编程流程。
