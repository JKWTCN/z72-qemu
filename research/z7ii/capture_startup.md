# 采集任务的地址坐标与启动绑定

主引擎的文件偏移和运行地址必须分开记录：代码运行地址为
`0x10020000 + 文件偏移`，函数指针另有 Thumb 位。此前
[采样事件记录](sensor_frames.md)中的部分地址遗漏了 `0x20000`，
据此搜索得出的“没有调用者、没有静态指针、必须存在瞬态重定位”
结论撤回。静态调用边与运行记录分别验证，不能用前者代替后者。

## 静态绑定

`analyze/capture_startup.py` 校验原始 C 1.70 master 身份，解码调用
指令并核对实际目标、方法表、任务回调字面量及队列判定指令。
输出同时携带文件偏移与运行地址，避免再次混用。

| 用途 | 文件偏移 | 运行地址 |
| --- | --- | --- |
| 模块初始化包装 | `0x40f650` | `0x1042f650` |
| 创建任务及同步对象 | `0x3acef0` | `0x103ccef0` |
| 建立服务依赖 | `0x3acfd2` | `0x103ccfd2` |
| 任务事件分发 | `0x3ac9ca` | `0x103cc9ca` |
| 模式配置处理 | `0x3abbc8` | `0x103cbbc8` |
| 设备打开处理 | `0x3ac408` | `0x103cc408` |
| 工作处理 | `0x3abd98` | `0x103cbd98` |
| 请求入口 | `0x3b01dc` | `0x103d01dc` |

模块方法表的复制源为文件 `0x23de910`，运行源地址 `0x123fe910`，
RAM 地址 `0xb186497c`。首方法为 `0x1042f651`；包装器按参数
低字节分派，参数 2 直接调用任务创建，参数 3 直接调用服务绑定。
公共分发器 `0x1020194c` 从 getter 数组取得方法表后调用首方法，
调用点 `0x1020196c`。这条路径不需要假设额外的重定位机制。

任务创建路径在 `0x103ccf62` 读取字面量 `0x103cd134`，值为
`0x103cc9cb`，并在 `0x103ccf68` 调用任务创建包装器
`0x103606b6`；任务对象是 `0xb238e654`。回调有明确的静态来源。

事件分发器按移位后的符号位判定事件，相关映射为：

| 事件位 / 掩码 | 处理入口 |
| --- | --- |
| 18 / `0x40000` | 设备打开 `0x103cc408` |
| 13 / `0x2000` | 工作 `0x103cbd98` |
| 17 / `0x20000` | 模式配置 `0x103cbbc8` |

请求入口 `0x103d01dc` 的 `0x20000` 投递不能解释成直接唤醒工作
处理器。设备打开另有通知路径：`0x103cd162` 对通知
`0x041b0080` 的分支在 `0x103cd248` 保存上下文，投递 `0x40000`。
此通知在 `0x10269f66..0x10269f6c` 经已注册回调发送。
该链的实际到达条件仍需观察。

队列空检查 `0x1034faa2` 和计数 getter `0x1034fb26` 都读取队列
对象的 `+8`，不是两个链接字段。探针现同时采样任务 `+0x40`、
`+0x60` 两组队列的链接与计数，不能再仅凭四个链接字判断队列状态。

## 运行观察与边界

`tools/sensor_frame_probe.py --trace-capture-startup` 在复位后为上述
入口设置一次性观察点，直到原始同步等待。每个入口只记录首次命中，
随后移除观察点继续运行；不统计调用次数，也不写入运行时寄存器或
RAM。记录保留调用者、参数、驱动状态和两组队列的元素计数。
正常同步脉冲和后续采样沿用既有探针路径；启动追踪模式跳过额外的
菜单往返，以便把观察限定在初始化与稳态。普通模式的虚拟计数等待
现增加宿主时间上限，避免计数停止时无限等待。

完整交互台输入的运行已命中初始化参数 2、任务创建、服务绑定
参数 3、事件 `0x20000` 的模式配置处理，以及请求入口
`0x103d01dc`（调用者 `0x10322a89`）。随后到达同步等待并自然进入
拍摄前台，图形不支持命令数与失败请求数均为零。同步等待之前未命中
设备打开和工作处理，这一有界阴性结果不能覆盖同步等待之后。
稳态捕获状态为 `(2, 0)`，驱动状态/分类为 `(1, 2)`，两组队列计数
均为零。完整身份与观察值见[验证记录](../../artifacts/capture_startup_shutter/report.json)。

同一运行用交互台的触点驱动方法逐项驱动外部快门 G14/G15，通过
原厂控制器扫描、串行传输及主引擎解码，得到以下开关字：

| 输入 | 主引擎首开关字 |
| --- | --- |
| 释放 | `0x200` |
| 全按 | `0x0c000200` |
| 半按 | `0x08000200` |
| 半按与全按同时保持 | `0x0c000200` |
| 释放全按、保持独立半按 | `0x08000200` |
| 最后释放半按 | `0x200` |

交互台现在提供半按、全按按钮及 `F`、空格快捷键。输入沿复用既有
模拟时间排队和超时释放机制，完整按压先闭合半按触点，释放先断开
全按触点。四项针对性检查覆盖短点击的沿保持、两个控件交叠、释放
全部取消待发输入，以及既有扩展器路由。运行验证直接调用交互台触点
驱动方法，未覆盖浏览器或 HTTP；这些结果也不表示快门已经产出照片。

这项修正恢复了可追踪的生产者路径，尚未证明 LCD 实时像素或拍照
完成。后续应沿 `0x041b0080` 的发送条件、设备上下文与打开完成回调
追踪实际硬件依赖；不能再把“未注册”视为已经证实的唯一阻塞点。
