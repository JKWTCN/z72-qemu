# PTP 内层服务、校验上下文与确认边界

分析固件确认：普通 PTP 表中的 `0x94FD–0x94FF` 还会进入独立服务表，
不依赖 `0x92F0` 的诊断配置 `0x4D6`。本轮验证了地址读取门槛，以及

以[确认页分析](menu_confirmation.md)为最新时序结论。

## 两层命令与状态

外层五个 32 位参数依次为内层命令和四个参数，不足补零。
参数布局由原始回调核对，实机工具直接使用 USB PTP。

| 外层操作 | 准备回调 | 执行回调 |
| --- | --- | --- |
| `0x94FD` | `0x107722E4` | `0x107722EA` |
| `0x94FE` | `0x10772300` | `0x10772306` |
| `0x94FF` | `0x1077230C` | `0x10772312` |

准备及执行分别进入 `0x104C6B14`、`0x104C6B9C`。表访问器
`0x104C6A4C` 返回 `0x119E405C`，步长 28 字节。原始查找与缓存函数
`0x104C6CC4` 对 175 项逐项检查通过。旧的 161 项统计只覆盖普通
外层操作表，不是整个服务接口的命令总数。

内层 `F001`、`F002` 分别为进入和退出服务。状态判定器经
`0x104798DE` 注册，读取 `0xB188BC80`。状态关闭时，地址读取以
外层 `0xA004` 拒绝。局部执行由主机显式设置该状态，未执行完整的
进入、退出流程，不能作为实机服务进入成功的证据。

## 地址读取与对象缓冲

`F032` 的准备与执行回调分别为 `0x104B010A`、`0x104B020C`，
参数一为地址、参数二为长度。准备函数检查长度非零，并经
`0x104B0098` 检查首尾地址。普通请求与
`0x10000000–0x13FFFFFF` 相交时被拒绝，另有若干工作区限制。

有界执行和 QEMU 均确认：B8 地址 `0x10000088`、master 起点和
零长度请求没有进入数据提交；允许的合成 RAM 请求则保持地址、长度
和等待参数 5000，进入数据交接。范围拒绝时外层仍为 `0x2001`，
首个响应参数才是 `0x201D`，只检查外层状态会误报成功。

传输函数 `0x1063C46E` 及分段函数 `0x104B014A` 在入口由观察环境
捕获，响应也由主机捕获。没有执行真实 USB 端点发送。

`F021` 固定读取对象 `0x11`，对应物理区域首址 `0x132C0000`。
其执行函数使用对象记录 `+8` 的已初始化缓冲指针，并非直接使用
区域物理地址。本轮显式提供合成缓冲后核对提交参数；该对象不覆盖
引导区，不能把它当成任意 Flash 导出接口。

## 校验上下文是另一条候选来源

原厂整包校验上下文在 `0xB2B422C8`，大小 `0x34`：

| 偏移 | 内容 |
| --- | --- |
| `+0x00`、`+0x04` | 解码主体指针、长度 |
| `+0x08` | 转换回调 `0x1039C635` |
| `+0x0C` | 八字节材料，地址 `0xB2B422D4` |
| `+0x14` | 设置后为 `0x44B`，变换后为 `0xB4FBFFFF` |
| `+0x18` | `Z_7_2` 与零填充，共八字节 |
| `+0x20` | 原包头的 20 字节期望摘要 |

原始设置函数先复制 B8；`0x103AFE82` 调用实际转换回调，将上下文
`+0x0C` 原地变为 K8，再追加到主体并计算 SHA-1。两种合成摘要的
对照分别返回 1 和 0，上下文都保留同样的 K8。`F032` 均允许读取
这处完整的 52 字节。`0x103AED1C` 会清空上下文，不能假设材料跨重启
或后续检查一直保留。

该链条已在 QEMU 交叉验证：先执行原始启动至 `0x1002D6EC`，之后
由调试器安排局部调用。设置、转换、SHA-1 和服务分派执行原始指令；
引导内容、主体、期望摘要、数字字符标志和断言日志为明确的合成环境。
传输只到提交入口，未执行菜单调用者，也未取得真实材料或执行编程。

## 菜单时序的已知部分与未验证部分

| 阶段 | 已确认的服务侧行为 |
| --- | --- |
| `0x10767048` | 资格与状态检查，未进入整包摘要 |
| `0x10767070`、`0x10767092` | 文件检查与版本列表，与整包认证分别处理 |
| `0x10767108` | 执行请求，经 `0x103F67A4` 进入控制器 |

| `0x103F6938` | 整包分支调用 `0x1039C638`，返回认证结果 |
| 认证结果为 0 | 同一执行调用继续进入更新准备 `0x1039C8FE` |

返回失败，结果 0 时进入更新准备。探针在准备入口明确拒绝，没有
执行准备体或编程；它没有执行原始认证或最终确认对话框。

官方[更新操作说明](https://download.nikonimglib.com/archive3/jFBMN00KI4Ix03x9LuU85FxJko41/Z-series_FirmUp_Win_En.pdf)
将对话框选择 Yes 与随后开始更新相连，但没有说明内部 SHA-1 的时点。
当时的两个有名服务观察点不足以确认菜单路径，不能据局部服务调用
证明认证位于最终 Yes 以前。后续已找到并执行原始菜单对象和事件表，
确认已追踪路径在执行选项后才到达认证事件投递入口，见
[确认页分析](menu_confirmation.md)。仍未找到认证后的额外可靠取消点。
因此**不提供“点击最终 Yes、等待校验、再取消”的实机操作**。
“只校验、取消、读取 RAM”目前尚不是已成立的操作流程。

## 固定 RAM 观察工具

完整 WSL 命令、基线对照、确认页选否和结果判读见
[实机 PTP 观察流程](../../docs/z72-ptp-observation.zh-CN.md)。

[读取工具](../../tools/ptp_checksum_context_probe.py)只进行机型查询、
进入服务、固定 52 字节读取和退出服务，没有菜单输入、更新请求、
参数写入或编程。默认仅打印离线计划；显式 `--execute` 才连接相机。
工具通过 PyUSB 直接访问 USB PTP 接口，不加载外部传输模块。
用户已在 WSL 实机完成身份查询与两组固定 RAM 读取；观察结果见下节。
这验证了固定读取通路，没有验证真实材料或菜单认证时点。

该工具只观察既有上下文，不触发校验。在没有新的时序证据前，
实机观察只能停在最终 Yes 以前：

1. 同次开机中先获取基线快照，工具自动退出服务。
2. 菜单只到明确的最终 Yes/No 对话框，选择 No 后退出。
   不选择最终 Yes，不进入更新进度，不用断电取消。
3. 保持同次开机再读取快照。USB 重连不能作为上下文保留的保证；
   如果相机重启，两次快照不能用于确认上述时序。
4. 只有上下文绑定和原厂整包摘要都匹配，工具才输出有效材料。
   全零、未绑定、旧包上下文或摘要不匹配均不算取得 K8。
   两次都无有效材料不能区分“尚未检查”与“随后已清空”。

这只是确认页以前的观察方案，不能称为已经完成“只校验、取消”。
如出现更新进度，已超出方案范围，不以强制断电终止更新。

离线计划和固定读取形式如下。实机读取要求传输依赖已就绪；本地
输入必须是原始 C 1.70 master 与原厂整包。第二次使用新目录，
例如 `.local/ptp-after-no`：

```text

python -B tools/ptp_checksum_context_probe.py --execute --master <C1.70-master> --package <original-package> --destination .local/ptp-baseline
```

输出目录保存私有 `context.bin` 和不含材料字节的 `report.json`。
仅摘要通过时另存 `verified-material.json`，其中 `boot_key` 是 B8，
`appended_key` 是 K8。这些本地输出不纳入公开清单。工具锁定
Z7 II / V1.70，不向其他机型或版本套用这个 RAM 地址。

## 服务切换与实机全零结果的后续分析（2026-10-24）

用户反馈的两组实验均为 Z7 II / V1.70，两次基线和选否后的快照
均为 52 字节全零，SHA-256 为
`7955cb2de90dd9efc6df9fdbf5f5d10c114f4135a9a6b52db1003be749e32f7a`。
用户确认到达最终 Yes/No 页、选择 No，当前和目标版本均为 1.70，
期间持续开机、没有关机或重启；运行读取脚本后屏幕似乎闪动。
这些是用户提供的实机观察，不是模拟环境生成的结论。

### 同步处理与异步模式请求

服务表中 F001 的执行处理函数为 `0x1047994C`，F002 为
`0x10479A66`；两者的准备项均为 `0x104798DE`。
F001 先核对五个参数和当前服务状态，调用 `0x10502EFA(0)`，
然后初始化对象、调用 `0x1047990C(0)`，成功才设置服务标志。
F002 经 `0x104799F6` 做多项子系统清理，在服务已开启时调用
`0x10502EFA(1)` 和 `0x1047990C(1)`，最后清除服务标志及 `+8` 状态。
因此不能把进入、退出服务视为一次普通的 RAM 标志写入。

`0x1047990C` 经 `0x10383C26` 把模式和回调保存至状态区
`0xB18A7B7C`，投递 `0x40` 任务事件，并等待响应。
任务分派 `0x103838A2` 在该事件下调用已注册接口的 `+0x1C` 项。
初始化链 `0x1020230A → 0x10383BBC` 注册由 `0x10206CA4`
返回的接口表，故此项绑定 `0x10206E04`。桥接函数再向另一个
已注册的接收器转发类型 3 的请求，包含模式值与完成回调。
该轮最终接收器尚未绑定，不能从桥接之前的指令排除其副作用。
后续已定位注册接收器并扩展执行至队列及回包，见下节。

`0x10502EFA` 的两个分支也可能请求运行模式转换并等待响应：
参数 0 到 `0x1050322A`，参数 1 到 `0x105031B8`。
这为屏幕闪动提供了一条可疑调用链，但尚未执行最终显示接收器，
不能把闪动直接归因于其中某个函数，也不能将闪动等同于重启。

### 上下文保留的覆盖边界

[局部对照程序](../../tools/ptp_service_transition_probe.py)与
[结果](../../artifacts/ptp_service/transitions.json)记录了六种原始
处理分支：进入成功、已进入、模式管理拒绝、任务完成失败，以及
服务开启和关闭时退出。预先放入非零合成上下文，监视其原始写入，
这六种分支均未改写它。另执行原始任务分派和桥接函数，模式 0、1
均向合成接收器转发类型 3 请求，保留上下文。

这些局部对照显式替代了模式管理、子系统清理和任务完成；桥接的
最终模式接收器也为合成边界。它们只排除已执行指令直接清零的解释，
**不证明完整服务切换会保留上下文**，也没有执行 USB 重连或菜单 No。

对整个 master 的半字对齐 Thumb BL/B.W 编码进行候选扫描，
`0x103AED1C` 的唯一直接分支来源仍为 `0x1039C66E`，即整包认证
开始处。启动初始化表也包含覆盖上下文的清零记录。该扫描包括可能
落在数据中的编码，不涵盖间接调用、动态构造的地址或大范围清零，
所以不能作为“其他路径都不会清零”的证明。持续开机的反馈使启动
清零不足以解释本轮结果。

### 当前结论与后续定位点

目前确认固定 PTP 读取可在实机完成、两组读回一致。尚不能区分：

## 注册接收器、会话关闭与界面返回的补充分析

用户补充：拔插 USB 似乎会强制回到拍摄界面；执行读取脚本时屏幕
闪动，还会听到类似界面返回的声音。这里保留用户对画面和声音的
观察，不把它写成已验证的重启、校验完成或某个具体函数的显示效果。
该现象增加了前后快照的混杂因素：不能把它们当成仅由菜单 No
隔开的两次无扰动观察。

### 接收器注册和消息往返

原始初始化循环 `0x1020555A` 经 `0x1022D638` 获取 18 项接口表
`0x1197FFB0`。索引 15 的记录 `0x119800A0` 给出注册函数
`0x10206CBA`、回包派发 `0x10206CC4` 和转换接口 getter
`0x10432724`。循环用 `0x102054FE` 作为接收器，并将记录地址作为
回调参数。这绑定了上一节止于合成接收器的间接调用。

该接收器使用原始转换函数 `0x10432728`；类型 3 请求经
`0x104328BA` 变为长度 8 的消息，内容为命令 9 和模式 0 或 1。
`0x10205698` 将它按接口 15、通道 1 提交队列。
这只确认消息编码和排队，尚未执行队列后端的实际模式动作。

对照环境在传输边界提供命令 10 的合成回复。原始解码
`0x10432770 → 0x104328DE` 将其变为类型 `0x12`，再经
`0x10206CC4 → 0x1038368C` 投递 `0x80` 事件。
任务分派再次执行后，经原始完成回调 `0x104798F2` 写入状态：
模式 0 对应 `0x03010003`，模式 1 对应 `0x03010004`。
回复标志 0 对应完成结果 1，标志 1 对应完成结果 0；随后清除待完成
回调，并发出服务等待事件。这是合成回复的原始解释，不是实机成功证据。

### CloseSession 也是观察过程的一部分

USB 实现会在固定读取结束后关闭自己的标准 PTP 会话。普通
`0x1003` 执行回调 `0x10479890` 发布通知后，调用
`0x10478BF2(1)`。该控制器清理会话标识、处理排队工作、触发多个
子系统清理和通知，并再次调用服务清理 `0x104799F6`。
所以完整读取涉及 OpenSession、F001、F032、F002、CloseSession，
不能只检查 F001/F002 来解释屏幕或声音变化。

其中 `0x103BB74E → 0x10329FDE → 0x103D1B5C` 会发送资源 3、
操作 `0x28`、长度 12 的从引擎请求，参数字节为 1，并更新本地状态。
局部执行覆盖了这条发送前路径；从引擎请求接收器、其界面行为及
其他清理端点仍为边界。因此这里尚不能声称已证明返回拍摄画面的原因。

### OpenSession 的原始通知与内部工作事件

标准 OpenSession `0x1002` 的回调为 `0x10479838`。它设置会话标识后，
发布 `0x040F0080` 通知，携带操作码与会话参数。
原始启用函数 `0x105109E8(1)` 经 `0x105464AC → 0x10463548`
注册处理器 `0x1050C3DE`；原始通知分派 `0x104C0F4E` 可以到达它。

处理器经 `0x1050C302` 查表 `0x1206251C`。其中 OpenSession 行
`0x12062540` 的八个模式槽均绑定 `0x1050C6C4`。
在合成的非忙状态下，通知先排入内部事件 50，再由原始队列消费函数
`0x10510AD0` 调用该操作处理器。处理器继续投递内部事件 9；
同一消费函数经原始状态映射和函数表进入 `0x1050B7AC`。

新增离线对照实际执行了上述注册、通知分派与两次队列消费。
在该输入下，事件 9 发布 `0x04090004`，四个参数字为 `[0, 0, 0, 1]`，
并请求将参数 `0x2300` 设为零。整个已执行链条保留非零合成校验
上下文。分配、排队、等待及参数存储为显式环境边界；通知在
OpenSession 回调返回后重放，不能当作真实并发时序。

这条路径独立于后续 F001/F032/F002，因此不能再只用服务进入/退出
解释 Python 运行时的界面变化。另一个原始绑定表 `0x119DB944`
将 `0x04090004` 经 `0x107363F2 → 0x10735D3C → 0x1073880A`
转换为界面事件 `0x04030026`。该下游尚未加入本轮执行；
新增对照中对应监听器为空，实际菜单退出及声音来源仍未证明。

### 更新服务的第五项并非已找到的 No 回调

相邻更新服务函数 `0x10767136` 循环等待结果，每次调用
`0x105212AA` 的超时参数为 300。合成结果位 1 返回成功 1，
结果位 2 返回失败 3、原因 6；日志为更新成功或失败。
这识别了一个执行后的结果等待入口，不能把它误认为最终确认页的
取消处理。该轮尚未定位原始最终 Yes/No 回调；后续定位及原始分派执行见
[确认页分析](menu_confirmation.md)。

每组使用非零合成上下文并检查读回及原始写观察，已执行路径均保留

外围清理及等待端点明确由环境提供，没有连接相机或执行更新。

USB 生命周期仍未覆盖，见[确认页分析](menu_confirmation.md)。
