# 播放停止请求的委托链与观察时间

本页接续[播放键停止路径](body_shutter.md)。地址为 C 1.70 master
运行地址，文件偏移减去 `0x10020000`。探针以原厂按键触发操作 18，
不改写固件状态或替换完成回调。

## 已完成的准备与实际工作提交

[依赖观察](../../artifacts/playback_stop_dependencies/report.json)确认：

| 位置 | 实测 |
| --- | --- |
| 停止队列 `0xb23ef3c8` | 停止前后元素计数均为 0，空队列判断返回 1 |
| `0x10322e84` | 参数操作 `0x1b0b` 返回 1 |
| `0x103c5342` | 收到回调 `0x10321a4d` |
| `0x10321a4c` | 准备通知 `0x042f0027` 实际到达 |
| `0x1023333e` 返回点 | 返回 0，进入后续工作提交 |
| `0x10398726` | 实际收到停止命令 |

`0x103c5342` 调用 `0x102f0f30` 后固定返回 1；后者直接通过传入
回调发送 `0x042f0027`。这一返回值不能独立解释为准备失败。
驱动随后还收到 `0x04190041`、`0x041b0041`，说明相关回调并非全部
静默。回调入口重复记录有八次上限，不能把达到上限后的空白当作
后续没有通知。

## 处理任务继续委托，而非未被唤醒

`0x10398726` 把命令字节 `0x11` 写入 `0xb1868310`，复制四字参数
到 `0xb23ed1a0`，并向任务 `0xb23ecc80` 投递标志 `0x10000`。
该任务在 `0x10398162` 创建，分发入口为 `0x10397b5d`。

[委托观察](../../artifacts/playback_stop_delegate/report.json)实际命中
`0x10397260`：参数为 `(1,1,0,1)`，处理阶段改为 `0x12`，随后调用
`0x1026e204`。后者先调用 `0x102e9fc2`，再清事件位，进入
`0x102ea05a`。任务已执行这些代码，不能把等待归因于未注册或未唤醒。

`0x102ea05a` 在控制字段 `0xb1868690` 非零时，等待对象
`0xb1868718` 的位 `0x400`，超时参数为 `3000`。原始指令还显示：
该对象的正常完成路径在 `0x102e9600..0x102e961c` 和
`0x102e9676..0x102e9692` 清除控制字段、迁移本地状态并置位事件。
这些静态路径尚未逐项增加运行命中证据，不能据此声称已找到缺失中断。

## 相机时间改变了短窗口结论

探针现在记录 `0x04266008` 的 64 位计数和 `0x04266010` 公告频率，
并报告计数差除以频率的观察时长。该数值用于比较固件的执行时间，
不是对真实机身频率或所有内核时间单位的验证。

[短窗口](../../artifacts/playback_stop_event_wait/report.json)中，宿主
30 秒只推进约 **0.893 个计数器秒**。因此“这段窗口尚未返回”不足以
证明长期挂起，也不能独立证明超时已发生。此前的短窗口记录保留为
有界观察，不能扩大其结论。

[长窗口](../../artifacts/playback_stop_timeout_window/report.json)运行
180 个宿主秒，推进 **5.483 个计数器秒**，得到以下续行证据。
时间为相对按键前快照的计数差／48 MHz，保留近似值：

| 计数器秒 | 实际到达 |
| --- | --- |
| 0.045 | `0x102ea06e` 等待事件 `0x400`，`r3=3000` |
| 2.692 | `0x1026e242`，前一等待调用已返回，`r0=1` |
| 2.692 | `0x1026e254`、`0x1039722c`，委托返回并进入后续处理 |
| 3.041 | 驱动收到 `0x041a000d` |
| 3.045 | 操作 18 完成生产者 `0x103e6c0a` 执行，结果字段 `r4=1` |
| 3.045 | 界面分发 `0x1020e228` 收到 `0x05040021`，结果参数 `r2=1` |

事件等待包装器 `0x10361192` 将底层返回零映射为 1，其他值映射为 0。
本次等待返回为 1，故不能把最终操作失败直接归因于这第一个等待超时。
验证文件名中的 `timeout_window` 表示扩大时间窗口的实验目的，不表示
已经证明超时返回。

长窗口结束时，驱动状态已从 11 转到 0，处理阶段从 `0x12` 进到
`0x13`，委托状态为 1；操作 18 的一次性回调槽被清零。但捕获状态为
`(4,0)`，状态列表新增 `0x3f`，门控仍为 1。这里实际发生的是延后续行
并以失败结果完成，并非停止成功，也不是永久停在驱动状态 11。
输入几何和格式字仍为零，没有有效取景像素或照片文件证据。

## 两个等待都有正常确认，失败要追溯到更早的局部操作

[后续结果观察](../../artifacts/playback_stop_result/report.json)推进约
5.192 个计数器秒，进一步确认：

| 相对计数器秒 | 原厂执行证据 |
| --- | --- |
| 2.67625 | `0x102e961c` 实际调用事件置位，`r0=0xb1868718`、`r1=0x400` |
| 2.67632 | 委托任务实际接收 `0x40`，到达 `0x1026c91a` |
| 3.02576 | 委托等待 `0x1026c344(0x400,3500,0x11)` 返回 1 |
| 3.02577 | `0x1026c9c4` 通过回调 `0x10394763` 发出 `0x04200107`，参数为 0 |

本次没有命中等待失败广播 `0x1026c37c`。两个等待的成功不能等同于
整项停止操作成功：首个确认点的局部累计字段 `r4` 已是 `0x20`。
原厂即使带着局部错误，也可以继续发出完成确认。

停止委托在两个等待之间还调用 `0x102d986e`：它先等待对象
`0xb18a764c` 位 4，参数 100；随后按调用参数选择清位 `0x20`、
控制请求 `0x107`、等待位 `0x20`，或清位 `0x10`、控制请求
`0x101`、等待位 `0x10`。两条后续等待的参数均为 150。
原始指令在这两个局部等待失败时分别累计 `0x80`、`0x100`，之后
调用 `0x102d8592` 并合并结果。下文记录了这两个局部等待的实际
失败返回，不能把后面委托等待的成功套用于它们。

驱动通知 `0x041a000d` 的生产点为 `0x1022e7e8`：它整理下层结果的
首字节及种类字节后调用捕获驱动。接收方 `0x103212b0` 会按这两个
字节决定错误处理和后续状态请求，不能仅从通知号认定为成功。

同次探针通过分别选择 master 和 slave 核心采样各自的输入寄存器，
按键前与结束时，两者的格式字及三个几何字均为零。这排除了本次
快照中“副处理器已有非零几何、只读了主处理器”的解释；仍未证明
所有中间时刻均为零，也不能仅凭格式零判断格式无效。

[诊断观察](../../artifacts/playback_stop_diagnostic/report.json)随后实际
命中 `0x1026c25e`：`r4=0x180`，广播 `0x04200181`，三元参数为
`(9,11,0x180)`，接收入口 `0x10394d07`。它来自当前局部调用的错误
分支，另两个诊断入口未命中。下游 `0x041a000d` 的两个结果字节
实测为 `(1,1)`。由此将状态 `0x3f` 定位到局部同步操作的错误累计，
而不是两个已经成功的停止确认等待。

重新核对 `0x102d6b6a` 的移位测试也纠正了早期位号：`0x102d6b6e`
左移 24 检查的是组 2 **位 7**，它经减计数器置对象位 4；
`0x102d6bc4` 左移 21 检查的是组 2 **位 10**，它直接置对象位
`0x20`。组 2 位 18 直接置对象位 `0x10`。不能把移位数当成位号。

探针新增可选 `--local-stop-events`，仅在相应局部等待入口通过
既有外部同步输入线送一次边沿，且要求该线的掩码已使能。报告显式
标明此实验输入与所用位号；默认不送这些边沿。它用于验证事件与
等待的因果关系，不改写对象状态，也不代表已恢复真实硬件的自动
事件生产合同。

[局部等待观察](../../artifacts/playback_stop_local_waits/report.json)直接
确认调用 `0x102d986e` 的参数为 1：先等待对象 `0xb18a764c` 的位 4，
参数 100，返回 0；再实际提交控制请求 `0x107`，等待同对象位
`0x20`，参数 150，也返回 0。对应两段计数差约为 0.101、0.151 秒。
结合错误广播的 `0x180`，两项局部等待失败已获得逐项运行证据；
它们与后续两个返回成功的停止确认等待是四次不同的调用。

## 外部事件对照使停止操作成功，但未提供像素

[外部事件对照](../../artifacts/playback_stop_external_events/report.json)
保持相同固件与设备配置，仅开启上述探针选项，在两个局部等待前
分别向同步组 2 位 7、位 10 送边沿。两次输入时原厂掩码均为
`0x27feb7`，对应位已使能。

| 结果 | 原厂事件基线 | 外部边沿对照 |
| --- | --- | --- |
| 对象位 4 的局部等待 | 返回 0 | 返回 1 |
| 对象位 `0x20` 的局部等待 | 返回 0 | 返回 1 |
| 当前错误广播 `(9,11,0x180)` | 实际出现 | 观察窗口未出现 |
| 驱动 `0x041a000d` 的结果字节 | `(1,1)` | `(0,1)` |
| 操作 18 完成生产者 `r4` | 1 | 0 |
| 界面完成结果 `r2` | 1 | 0 |
| 最终状态列表 | `0x3f` | 空 |
| 最终驱动状态 | 0 | 12 |

本次对照推进约 3.823 个计数器秒，没有写入图像缓冲或清除错误列表。
操作 18 的成功结果说明这两条事件足以改变本次停止链的结果，不能
再把 `0x3f` 的消失一概等同于已有真实像素流。但这些输入由探针在
已知等待入口定向产生，尚不是设备自动响应模型；不得将本报告当作
默认配置已经修复、成功进入播放应用或实现取景、拍照的证据。

结束时主、副输入几何仍为零，快门门控仍为 1。后续工作应恢复帧相位
及控制请求 `0x107` 对应的设备完成条件，再验证这些事件对正常启动、
停止和重启的作用，而不是把定向边沿无条件改成周期广播。
