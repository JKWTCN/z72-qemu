# 初始化之后的状态与模式请求

以下为 C 1.70 master 运行地址，文件偏移等于地址减去 `0x10020000`。
使用原厂三份映像、实验驻留参数、带卡覆盖层及显示完成源。
`tools/device_registration_probe.py --capture-operations --watch-release`
只观察原厂执行和写入，不改写固件或完成状态。

## 状态 4 的实际到达

[状态切换观察](../../artifacts/capture_state4_transition/report.json)直接命中：

| 入口 | 实测 |
| --- | --- |
| `0x1020dad2` | 收到初始化成功后的事件 1，模式参数 0、附加参数 1 |
| `0x1020dc5c` | 当前状态 2，选择状态 4 分支 |
| `0x102470ae` | 对象 `0xb1819604`；父级当前状态 4、前一状态 2 |
| `0x102470d6` | 状态 4 对象向父级报告事件 1、模式参数 0、附加参数 1 |
| `0x1020dc72` | 父级实际执行状态 4 的就绪分支 |

这补齐了[父级分发](body_shutter.md)此前仅静态恢复的主状态路径。
状态 1 专用辅助路径没有执行，并未阻止主状态机进入状态 4。
状态字写入观察最多记录八次，在更新前一状态之后达到上限；
该写入列表的末值不是最终状态，状态 4 有独立入口与字段采样证据。

## 操作 16、17 已完成，槽位保留不表示挂起

[请求与回调观察](../../artifacts/capture_mode_requests/report.json)从复位记录
两条完整链：

| 阶段 | 操作 16 | 操作 17 |
| --- | --- | --- |
| API | `0x103f25bc` | `0x103f25d4` |
| 提交标志 | `0x1` | `0x2` |
| 捕获任务入口 | `0x103ef366` | `0x103ef376` |
| 下级模式请求 | `0x10323676` | `0x1032375a` |
| 完成回调 | `0x10632f56` | `0x10632fae` |
| 实际通知 | `0x04100010` | `0x04100011` |
| 回传标志 | `0x1` | `0x2` |

回传首字是标志，不能把非零值解释为错误结果。两个回调进一步将
载荷交给应用字事件 `0x4a/0x4b`，并唤醒应用更新。

运行结束时槽 `0xb23f7024/0xb23f7028` 分别保留
`0x10632f57/0x10632faf`。生产者 `0x103e910c`（操作 16）和
`0x103e90f0`（操作 17）调用的是 `0x102282ac`，即查看槽位，
随后经 `0x102282b4` 调用；它们不使用取走并清零的 `0x1022829c`。
因此这些槽与初始化操作 14 的一次性回调具有不同的生命周期。

[门控置位后的独立观察](../../artifacts/capture_mode_requests_after_gate/report.json)
在门控从 0 写成 1 后重新布置两项操作的入口与回调观察点，并观察
两个回调槽的写入。到 60 秒结束，未出现新的请求、回调或槽写入，
原先登记值保持不变。结合前面已命中的完成回调与生产者指令，
不能据此把当前边界命名为操作 16、17 等待硬件完成。

## 输入格式零值有明确写入来源

同一复位观察在同步握手前命中 `0x102097fa`，调用返回地址
`0x10238fcb`，格式结构为 `0xb2b36b88`。十四项打包输入全部为零；
在实际存储指令 `0x10209848`，`r0=0`、目标 `r2=0x20068500`。
所以稳态格式字为零并不意味着格式设置函数从未执行，也不能单凭
零值认定格式无效。稳态观察到某配置表为空，同样不证明启动期间
该表从未提供临时配置。

几何设置 `0x1020905a` 在这次复位到稳态的窗口仍未命中。格式
初始化、模式请求完成与有效像素传输是不同条件；当前没有证明
输入几何与采集缓冲已建立，LCD 有效实时像素及照片写入仍未实现。
后续需要沿实际通道的数据和缓冲生产者继续，避免把已完成的请求
或保留的通知回调误当作阻塞。

## 几何配置请求的具体选择条件

`--watch-input-config` 从复位观察配置分发与两条几何设置路径，
每入口最多八次命中；观察到的入口会从 `unseen` 中排除，另报告
每项命中次数。[60 秒观察](../../artifacts/input_geometry_requests/report.json)
只记录到一次配置分发 `0x1023abaa`：

| 字段 | 实测 |
| --- | --- |
| `r0` 请求掩码 | `0x1` |
| `r1` | 0 |
| `r2` 指针表 | `0xb51ddfb0` |
| 指针表 `+0x18` 的几何描述符 | 0 |
| 返回地址 | `0x1022fcf1` |

分发器在 `0x1023ad0a..0x1023ad1a` 检查掩码位 `0x100`，选中后
才取指针表 `+0x18`，调用 `0x1023c8ae`；后者会调用几何构造
`0x10239c34` 与条件构造 `0x10239bcc`，最终包装器 `0x1020c2c8`
进入寄存器设置 `0x1020905a`。另一更新分发器 `0x1023aed8`
在 `0x1023afd0..0x1023afda` 使用相同掩码位及槽位。

本次所有几何入口及更新分发器均未命中，配置分发只命中一次，
未达到八次上限。因此这次并非“已选择几何配置，但描述符为空”——
观察到的请求本身未选择几何位，不能仅填充空槽就认定已修复生产者。

调用者 `0x1022fca6` 先清零栈上的八字指针表，再以掩码 1 调用
`0x1023ad8e`，由包装器进入分发器；它没有提交完整几何参数。
这把稳态的输入几何零值进一步定位到上游请求范围，尚未解释所有
有效取景请求应在何种条件下产生。

[加长冷启动观察](../../artifacts/capture_long_boot/report.json)将无按键
窗口扩到 180 个宿主秒，末次计数为 `191883788`，公告频率为
48 MHz，即自计数器起点约 3.998 秒。配置分发仍只命中一次，参数
仍为掩码 1；全部七个更新或几何入口均未命中，且未触及八次记录
上限。最终捕获状态 `(2,0)`、应用模式 `(4,2)`、门控 1，主处理器
格式和三个几何字均为零。这扩大了有界证据，仍不能代表任意更长
相机时间之后都不会请求几何配置。

## 所需掩码存在，但完整配置工作尚未执行

在自动输入握手和限次计时修复后的构建上，
[120 宿主秒冷启动观察](../../artifacts/input_configuration_producers/report.json)
增加了配置构造、完整准备、掩码判定及队列工作入口。只提供既有启动
同步输入，未提供按断点注入的 GPIO 握手或播放停止事件。

| 原厂字段或入口 | 实测 |
| --- | --- |
| 配置块 `0xb1887d70+0x5c` | `0x1` |
| 配置块 `+0x60` | `0x2eb` |
| 分发 `0x1023abaa` | 一次，掩码 1，与上述两个字段同时采样 |
| 构造 `0x10231c70` | 未命中 |
| 准备 `0x10232040` / 判定 `0x102320ee` | 未命中 |
| 队列工作 `0x10233cf6` | 未命中 |
| 更新、几何构造及设置入口 | 全部未命中 |

末次计数 `151372432 / 48000000`，约 3.154 个相机计数器秒。
主状态 `(4,2)`、捕获状态 `(2,0)`；自动握手的待处理字段与适配器
活动字段均为零。观察上限未耗尽任何配置入口的八次记录额度。

原厂 `0x1022fc26` 按内部模式选择 `+0x60` 所需配置掩码：模式 0
选择 `0x2eb`；`0x102358de` 的返回结果还可清除位 `0x80`。
初始化 `0x1022fca6` 登记这一掩码，却只把位 1 写入 `+0x5c`
并提交。完整准备 `0x10232040` 调用构造器之后，读取两个字段，
以 `r5 = field_60 & ~field_5c` 计算尚需配置的项，再按上下文分类
过滤位 4；掩码非零时才调用分发包装 `0x1023ad8e`。
这说明已配置字段是提交记录，不能单凭它断言硬件已完成。

`0x2eb` **不包含**几何位 `0x100`，差集 `0x2ea` 也不包含它。
因此既不能通过补齐几何描述符修复这次请求，也不能认定全部取景
通道都必须经过 `0x20069500`。完整准备的两个直接调用点
`0x10233cbe/0x10233d3a` 分别位于上下文处理与队列工作路径；
下一步需要确认上游上下文和工作请求的来源，而非强制该掩码或
把未请求的尺寸配置当作唯一原因。
