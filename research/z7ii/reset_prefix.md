# Z7 II C 1.70 原厂复位启动前段

本记录基于主从固件分析和 QEMU 10.2.4 原地址主板执行。代码位置为 EG 成员
文件偏移，执行地址为 `0x10020000 + 偏移`。原始输入未修改。

此前实验从选定例程进入，使用合成 MMU 设置。本实验直接从两份 EG 的偏移 0
进入，保留镜像内 `0x10000` 的完整 16 KiB 页表。原厂代码自行关闭及开启 MMU、
设置 TTBR、域访问、向量地址，读取 MPIDR 并设置六个 CPU 模式栈。
调试连接只用于逐步执行和读取状态，正常场景不写寄存器或内存。

| 项目 | master | slave |
| --- | --- | --- |
| 偏移 0 分支目标 | `0xBC88` | `0xBCD4` |
| 首次外设写入指令偏移 | `0xBDA4` | `0xBDF0` |
| 停止时 SVC 栈顶 | `0xB2B88000` | `0xC18F8000` |
| 首次写入地址 / 值 | `0x04264000` / `0x21` | 相同 |

两个角色均连续执行 72 条原厂 ARM 指令后，在 `STR r1, [r0]` 执行前停止。
检查每条指令的下一 PC 和 ARM 状态，在 UND、ABT、FIQ、IRQ、SYS、SVC 六个栈
设置完成时核对模式和 SP。最后核对 `r0`、`r1`，并逐字节确认整张页表未被改写。
该前段检查的代码、页表、栈顶下方和首个外设地址均由原厂一级 section 恒等映射；
这只是软件映射证据，不确认整个 SoC 的物理内存容量。

负对照使用另外的实例，将 RAM 中代码地址 `0x10000000` 对应的页表项清零。
原厂 MMU 开启后，master 在预期下一位置 `0xBD1C`、slave 在 `0xBD68` 前发生
取指异常，PC 为 `0x0000000C`，模式为 ABT。此时尚未设置 VBAR，所以使用低向量。
这验证正向路径依赖原厂页表，不能仅靠预加载镜像执行。负对照修改仅限实例 RAM。

```sh
python tools/boot_probe.py --master /path/to/eg1840_mas_01700.bin --slave /path/to/eg1840_sla_01700.bin --qemu .build/build/qemu-system-arm --destination .local/boot-run
```

该工具仅支持原地址主板，不支持 `virt`。它先校验两份完整固件的长度、SHA-256、
CRC 和结构，再创建输出目录。运行目录保存完整 PC/CPSR/SP 轨迹、启动参数及日志。
精简结果见 [验证记录](../../artifacts/boot_validation/report.json)。

2026-10-10：master/slave 正向路径和无效页表负对照全部通过。每个角色仍使用独立
单 CPU 和通用加载器预加载；CPU 型号与 RAM 容量为实验选择。完整相机加载器、
外设、次核释放、RTOS 和菜单尚未执行，不能把这次结果称为相机正常启动。

下一启动边界是该外设的两个写入（第二个为 `0x04264020` / `0x153B0902`），
随后是临时栈 `0x04008F00` 以及 `0x2B8`、master `0xD700` / slave `0xD740`、
`0x394` 三个调用。应先恢复这些路径的寄存器访问及等待条件，再实现对应外设。

后续阶段已增加四个配置字和临时栈，并将连续执行推进到 `0x394` 前。
本工具仍保留首次写入前的停止边界；扩展实验见
[早期配置](early_configuration.md)。
