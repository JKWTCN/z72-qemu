# 启动后的五秒时限

分析固件并观察原厂组合运行，拍摄状态栏之后的清屏由应用软件计时器
触发。它不是本次图形上传窗口的访问异常，也不能仅凭消息编号认定为
温度检查失败。

`0x102a71f8` 初始化应用控制服务，把 `AppC_Tim` 对象
`0xb1f80168` 注册到事件槽 0，关联目标 `0xb1818bd0` 和消息
`0x03000003`。应用控制上下文位于 `0xb1819aa0`：偏移 `0x10`
保存算出的秒数，偏移 `0x14` 保存策略标志。
`0x102a74ca` 在标志与掩码 6 的交集非零时选用五秒时限；
`0x102a7bd0` 将秒数乘以 1000 后启动计时器。

本次原厂运行中的状态为：

| 字段 | 观察值 |
| --- | --- |
| 应用控制策略标志 | `2` |
| 算出的时限 | `5` 秒 |
| 计时器最后一次启动参数 | `5000` 毫秒 |
| 事件槽 | `0` |
| 目标上下文 / 消息 | `0xb1818bd0` / `0x03000003` |
| 控制器电池通信状态 | `9` |

在 `0x102a7c48` 观察到槽 0 投递该消息，随后同一消息对象
`0xb1f7fdf4` 进入系统分发器。`0x1020ccb8` 将请求值设为 3，
经 `0x1020cc82` 调用模式请求入口 `0x102467be`，后续才发生已记录的
模式 3 → 1 → 8 切换。本次观察在同一实例复位后追踪计时器投递，
没有覆盖策略标志、改写完成回调或修改固件指令。

## 策略标志的输入

分析 `0x1020f32c..0x1020f36a` 可确认，参数 `0x1902` 非零时，
策略更新入口 `0x102a7688` 会设置标志 2；参数 `0x1901` 对应另一项
限制标志。本次参数缓存中的 `0x1902` 为 1，与策略标志 2 一致。
这条分支来自固件分析；本次直接捕获的是计时器投递及模式请求。

控制器的 `0x2001fa79` 为 9，整理记录 `0x20016040` 的分类字段为
`0xff`、状态字段为 9，与此前确认的电池串口传输失败路径一致。
该状态经供电记录转换使参数 `0x1902` 置位，具体传输与内容校验边界见
[控制器串口](controller_uart.md)。当前实验没有接入完整电池串口对端，
需要继续实现并验证收发时序、回复内容和后续查询，不能把忽略五秒时限
当作修复，也不能用覆盖供电状态替代外设实现。

`tools/graphics_boot_probe.py` 的报告增加 `idle_timer` 字段，记录上述
上下文、策略、目标消息及最后启动参数。最后启动参数不是剩余时间，
也不能证明计时器当前仍在运行。该读取已在原厂运行状态上检查，记录见
[启动时限验证](../../artifacts/startup_idle_timer_validation/report.json)。
稳定启动、菜单显示及菜单交互仍待验证。

后续[实验电池串行对端](battery_serial.md)已使供电通信状态保持为 2，
解除上述五秒策略，计算时限恢复为 30 秒。新的持续观察仍出现模式 3
切换到模式 1，此时策略标志为零，需要单独追踪其来源。
