# 控制器系统复位域

组合机器的控制器使用独立 CPU 和地址空间。原先未连接其
`SYSRESETREQ` 输出，控制器写系统复位请求时，默认处理会复位整个组合机器。
原厂唤醒输入实验中，G7 由高变低、再由低变高后均观察到 QMP
`RESET`，原因是 `guest-reset`。控制器返回 `0x080002b4`，主引擎的
应用上下文和初始化标志也被清空。这使已完成的引擎初始化重新开始。

现在把该输出连接到控制器自己的复位容器。请求通过底半部回调执行，
避免在寄存器写入过程中直接复位正在运行的 CPU。容器覆盖控制器 CPU、
中断控制器、系统计时器、配置窗口、GPIO、DMA、串行接口、随机数、
模拟量和计时外设，以及它们的中断合并器。多窗口设备只加入一次。
备份时钟窗口、控制器 SRAM 和固件存储不加入该容器。
宿主请求的整机复位继续使用机器原有的复位路径。

`tests/test_controller_embedded.py` 在显式串行连接和板级自动连接两个场景中，
用合成指令写入 `AIRCR=0x05fa0004`，验证：

- 控制器恢复自己的复位向量和栈指针。
- DMA、计时器、中断使能和系统计时控制清零。
- 控制器 SRAM 和备份寄存器内容保留。
- 四个引擎 CPU 的寄存器及引擎串行配置保留。
- 后续宿主整机复位仍恢复控制器向量、DMA 和板级连接状态。

原厂唤醒实验使用临时采样存储尾标、周期字段 81、空寄存器目标、
实验控制器驻留数据和显式 GPIO 输入，指令计时设置为
`shift=0,sleep=off`。修复后两次输入边沿仍使控制器返回复位向量，
但不再发布整机 `RESET`，五个应用的初始化状态和采样就绪状态保留。
最终系统模式仍为 0、待更新位图为 11，尚未完成前台切换或菜单显示。

这些实验输入不是有效机身参数或已确认的开关配置；复位域修复不代表
完整启动已实现。备份时钟域的精确电源行为和整机迁移尚未验证。
验证记录见 [复位域观察](../../artifacts/controller_reset_validation/report.json)。
