# 引导材料的存储窗口与 NOR 访问路径

2026-10-24 继续追踪 `0x10000088–0x1000008F` 的初始化来源。
新增证据表明：固件将包含该地址的映射窗口按 x16 NOR Flash 接口处理，
具有设备识别、CFI 查询、编程及擦除例程，并会临时修改页表权限。
这将来源调查从一般 RAM 写入缩小到映射存储器及更早的引导阶段。
尚未定位真正写入八字节 B8 的程序，也没有取得实际 B8 或 K8。
十二个历史版本的映射、初始化表与设置函数执行复核见
[历史更新包检查](update_history.md)；早期版本仍未补上真实输入。

分析对象仍为原始 Z7 II C 1.70 master/slave，身份和动态检查见
[结果元数据](../../artifacts/boot_material_access/report.json)。
下文 `0xB2BBxxxx` 为运行地址；其他注明的代码位置为 master 成员偏移。

## 默认权限及写入对照

原始页表将 `0x10000088` 恒等映射，描述符为 `0x1000C426`。
普通 section 的 AP 值为 5，domain 为 1。启动代码设置的 DACR 为
`0x55555555`，对应 client 域；在所观察的 MMU 配置下，普通 CPU 写入
受到权限限制。域与权限检查关系参见
[Arm 短描述符 MMU fault 说明](https://support.arm.com/documentation/ddi0406/c/System-Level-Architecture/Virtual-Memory-System-Architecture--VMSA-/VMSA-memory-aborts/MMU-faults)。

已用原始启动指令和原始 `STR r1,[r0]` 做两组隔离对照：

| 状态 | master / slave 结果 |
| --- | --- |
| MMU 尚未开启 | 向实验窗口写入固定合成值成功，并触发写监视点 |
| 原始 MMU 设置完成 | 写入触发 section permission fault，目标保持原值 |

master 的存储指令偏移为 `0xBDA4`，slave 为 `0xBDF0`。
后者的异常入口分别是 `0x10100010`、`0x10034110`；观测到的 DFAR 为
`0x10000088`，DFSR 为 `0x81D`。这些是实验板原始代码的运行结果，
不是对真实机身寄存器状态的转储。两项对照只改变独立实例中的寄存器，
输入镜像及页表均未修改。

## RAM 中的 NOR 驱动

启动复制记录把 master 偏移 `0x2428D80` 开始的 `0x105C` 字节放到
`0xB2BB0000`。其中存在以下路径：

| 运行地址 | 已确认行为 |
| --- | --- |
| `0xB2BB0158` | 读取设备标识及 CFI 几何信息，并缓存初始化状态 |
| `0xB2BB04E0` | 临时放开权限、初始化、检查编程参数、恢复权限 |
| `0xB2BB0682` | 遍历 12 字节控制记录 |
| `0xB2BB0686` | `STRH` 输出记录指定的地址和半字值 |
| `0xB2BB0692` | 进入可写访问状态 |
| `0xB2BB06AC` | 恢复先前访问状态 |
| `0xB2BB06CC` | 改写活动 TTBR0 页表的 section 属性，执行维护操作 |

`0xB2BB06CC` 从活动页表的 `+0x400` 开始处理 64 项，对应
`0x10000000–0x13FFFFFF`。进入访问状态时保留各项物理基址，低属性
改成 `0x432`；首项从 `0x1000C426` 变成 `0x10000432`。退出时用保存
的属性恢复。因此，默认只读映射不能作为不存在存储编程路径的证明。

监视到的设备识别与查询序列如下；地址是 CPU 字节地址：

| 地址 | 半字值 | 作用 |
| --- | --- | --- |
| `0x10000AAA` | `0xAA` | 识别序列第一步 |
| `0x10000554` | `0x55` | 识别序列第二步 |
| `0x10000AAA` | `0x90` | 进入设备识别 |
| `0x10000AAA` | `0xF0` | 恢复读取 |
| `0x100000AA` | `0x98` | 进入 CFI 查询 |
| `0x10000AAA` | `0xF0` | 恢复读取 |

地址除以半字宽度后，分别对应标准 NOR 字地址 `0x555`、`0x2AA`
和 `0x55`。序列与
[Spansion NOR 数据手册的命令定义](https://community.infineon.com/gfawx74859/attachments/gfawx74859/nor-flash/5446/1/S29AL016J_Rev06.pdf)
一致；此处仅据此识别协议，未确定实际器件型号或容量。
代码还从 `0x1000004E` 读出设备大小指数，与 x16 CFI 的 `0x27`
字偏移相符。这些观察支持将该窗口视为 NOR 存储访问窗口。

本次没有把查询命令写入当成 B8 数据初始化。六次控制写入都在 B8
范围之外，而且识别与查询模式中的读取值不能直接当成正常存储内容。

## 编程请求的上层入口

master 偏移 `0x3513B8` 将目的地址、源指针和半字数量放到请求块
`0xB1D50118`。工作循环在偏移 `0x351234` 取出三项参数，通过
`0x30B7A8` 的跳板进入 `0xB2BB04E0`。这提供了继续追踪实际存储
写入者的明确入口，但目前没有证据显示某个已分析请求以 B8 为目的。

已识别的直接调用点是 `0x287D40`、`0x744D7E`、`0x746084`。
第一处把字节长度转换为半字数量并带重试；另外两处先请求编号
`0x152` 的擦除操作，再编程。不能将这些通用存储操作命名为 B8
生成器，也不能由控制命令中的常量推导引导材料。

## 动态复现边界

[探针](../../tools/boot_material_access_probe.py)先让原始启动代码复制
RAM 例程、复制页表并执行页表切换，再以三个零参数进入
`0xB2BB04E0`。原始包装器执行六次查询控制写入后，因目的地址无效
返回 2，未进入数据编程分支；活动页表完整恢复。期间 B8 的实验零值
没有改变。此调用由调试器安排，不是自然菜单更新流程。

实验板未模拟真实 NOR 的命令状态机；识别及 CFI 数据来自普通实验
存储，不能用于判定真实器件身份、几何信息、正常阵列内容或编程成功。
QEMU 启动时的零值也不是真实 B8，增加该设备模型本身不会生成密钥。

```text
python tools/boot_material_access_probe.py --master /path/to/eg1840_mas_01700.bin --slave /path/to/eg1840_sla_01700.bin --qemu /path/to/qemu-system-arm --destination .local/boot-material-access
```

模拟器需要能在执行环境中运行。本次复用已编译二进制，SHA-256 为
`be664ded625e66304b2d98f157cf30bd8ac0f1aca2fbfa43f1546b02f30b13c2`；
本次检查使用指定的 Windows Python，经本地进程适配启动 WSL 中的
现有二进制，没有重新编译项目。报告只保存地址、命令、计数和哈希。

## 初始化来源的当前判断

已确认的整包校验调用点仍从 `0x10000088` 取得八字节输入；
`0x10000080` 另被读取四字节用于参数设置。更新 master 从
`0x10020000` 开始，前面留出 `0x20000` 字节。结合 NOR 访问路径，
应优先核对低端存储内容和更早的引导代码，而不是把实验 RAM 零填充
或 CFI 查询当成来源。这是调查方向的推断，尚不是引导材料持久化
布局或生产写入流程的完整证明。

下一条证据链是请求块 `0xB1D50118` 的上游：恢复其区域描述符和
调用参数，确认能否出现覆盖偏移 `0x88` 的实际编程请求；同时保留
更早阶段写入、地址重映射及其他存储主设备的可能性。若最终定位到
包外引导程序，仍需取得该程序或相应存储内容，才能计算并验证 K8。

## 区域表与区域 0 的编程接口

进一步追踪得到 33 项区域描述符和 81 项对象记录。二者在原始启动
复制数据中分别位于 `0xB185E5C4` 和 `0xB185EB70`，步长为 44 与
28 字节。成员偏移 `0x2286E4` 计算区域记录地址；`0x2286F6` 检查
对象编号小于 `0x51`，并检查记录内编号相符。区域地址计算函数本身
没有提供区域数上界；这里的 33 项依据已恢复的对象引用范围确定。

| 区域编号 | 首选地址 | 备用地址 | 区域跨度 |
| --- | --- | --- | --- |
| 0 | `0x10000000` | 无 | `0x20000` |
| 1 | `0x10000000` | 无 | `0x20000` |
| 2 | `0x10020000` | 无 | `0x2940000` |
| 9 | `0x12A40000` | 无 | `0x20000` |

0 和 1 是仅有的覆盖 B8 地址的描述符；区域 2 从 master 起点开始。
描述符证明固件把低端 `0x20000` 字节单独管理，但表中没有存放该
区域的实际内容，也没有提供 B8 的生成算法或生产写入记录。

成员偏移 `0x39F6CC` 是通用对象写入入口。它拒绝对象编号 1 和 2，
但允许对象 0，并检查输入长度不超过对应区域容量。对象 0 的请求经
`0x39F6B2`、`0x287F9A`、`0x287E98`、`0x287D2E` 到达上一节的
编程队列；数据取自传入的缓冲区，不在这条路径中构造 B8。

[区域探针](../../tools/boot_region_probe.py)执行了原始记录查找、
请求构造与重试路径，结果见[区域检查元数据](../../artifacts/boot_region/report.json)：

- 对象 0、长度 256 的合成请求被转交给目的地址 `0x10000000`，
  长度和源指针保持不变。这一范围包含 B8。
- 主机端编程队列固定返回拒绝；原始外层与内层重试最终形成三次
  擦除请求、九次相同编程请求，最后返回失败。擦除请求只在主机端
  应答，没有执行设备擦除；编程数据没有写入任何真实或模拟 Flash。
- 对象 1、对象 2，以及对象 0 超过 `0x20000` 的请求均未进入队列。
- 原始读取接口 `0x39F7D4` 可把对象 0 的前 256 字节复制到指定
  缓冲区。该检查读取的是显式设置的合成内容，不是真实 B8，也没有
  验证该读取接口能从相机外部到达。

## 已识别应用调用者的约束

在成员前 `0x780000` 字节中，按 Thumb BL 与无条件 B.W 解码，找到
14 条到 `0x39F6CC` 的直接边。继续追踪这些边的参数后，尚未找到
区域 0 的实际请求来源。其中两个看似可变的入口已进一步收窄：

- 启动路径 `0xE27C6` 从 `0xE1A4E(0x4E)` 返回的固定描述符取得
  对象编号，实际为 `0x44`，不对应引导区。
- `0x37A540` 的已识别直接调用者 `0x492FF8` 从六项表中选择对象，
  该表为 `0x49–0x4E`；它覆盖资源区域，不会选出对象 0。

通用写接口的其他已识别应用分支涉及参数及资源对象；仅凭某处寄存器
传参不能认定它能在自然流程中接收到 0。这一调用分析不覆盖任意计算
目标的间接调用、其他代码窗口、其他处理器或更早的加载程序，不能用
直接引用未命中证明初始化代码一定不在分发包内。

当前已找到低端存储的明确描述符和能写入它的通用接口，仍缺真正产生
或提供 B8 内容的调用者。后续应检查对象 0 的间接调用及更早的引导
输入；不能把合成写入请求、可写区域定义或程序重试当成来源已恢复。

```text
python tools/boot_region_probe.py --master /path/to/eg1840_mas_01700.bin --output .local/boot-region/report.json
```

该检查只需本地原始 master 及 Unicorn、NumPy、Capstone，不需要
编译或运行整机。主机替代边界为锁、拒绝编程的队列、合成擦除应答和
批量复制；原始接口、范围检查及重试代码仍由固件执行。

## 扩展引用与附加成员复核

后续将五个已知写接口的引用检查扩展到完整 master，并按各自运行
地址另外检查四段启动复制区。检查包括 ARM B/BL/立即数 BLX、
Thumb 宽分支、条件分支和短分支，以及精确地址字、PC 相对地址和
限定窗口内的 MOVW/MOVT 地址构造。此检查会覆盖数据区中的指令
候选，不等于确认整个扫描区域都可执行，也不穷尽任意计算目标。
范围与地址记录见[引用复核元数据](../../artifacts/boot_region/reference_audit.json)。

通用对象写入入口仍只有原先的 14 条直接边。另找到先前窄范围分支
检查未计入的 `0x38496E` 短跳转，它进入 `0x3848CC`，但在跳转前
明确装入对象 `0x45`。因此该分支没有补上区域 0 的调用来源。
没有找到这五个接口的精确地址字或上述限定构造形式的新引用；该结果
不能排除经过多步计算、运行时注册或其他未覆盖机制的调用。

对 EX、TPJ、VR 三个原始成员，另逐一代入其中连续八字节值，按
B8 和 K8 两种解释检查原版整包摘要。共检查 1,420,279 个窗口、
2,840,558 次摘要比较，未匹配。结果见
[附加成员值检查](../../artifacts/boot_region/auxiliary_values.json)。
这只排除了该种连续存储解释，不能排除运行期构造、非连续编码、
通信输入或单独保存的机身配置；其他处理器的同数值地址也不能直接
视为主引擎 B8 的物理地址。

截至这些复核，尚未定位 B8 的真实初始化程序。现有材料没有提供
原始 `0x10000000–0x1001FFFF` 内容或更早加载器，已识别的应用路径
也未提供实际区域 0 输入。继续验证需要能覆盖这一缺口的原始引导
镜像，或记录 B8 实际写入／读取上下文的实机跟踪。八字节候选匹配、
区域可写或实验读取成功，都不能单独证明初始化来源已经恢复。
