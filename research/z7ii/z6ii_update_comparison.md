# Z6 II / Z7 II C 1.70 更新结构对照

分析日期：2026-10-22。分析固件对比两款机型的原厂 C 1.70 整包、
主引擎成员及更新解析例程。身份、代码窗口摘要和执行结果保存在
[对照数据](z6ii_update_comparison.json)。原始更新文件未修改。

## 样本与成员

| 项目 | Z6 II | Z7 II |
| --- | --- | --- |
| 原始文件 | `Z6_2_0170.bin` | `Z7_2_0170.bin` |
| 原始长度 | 49,002,888 | 48,494,024 |
| 型号标识 | `1850` | `1840` |
| master 长度 | 38,750,138 | 38,239,098 |
| slave 长度 | 8,832,194 | 8,834,370 |
| EG 版本记录 | `Ver.01.70.02` | `Ver.01.70.02` |

两包都是 EX、TPJ、master、VR、slave 五成员，目录头长 `0xD0`。
10 个成员 CRC 与 2 个容器 CRC 均通过；TPJ 完全相同。其他四类成员
内容不同，未做互换验证。本次没有为 Z6 II 增加模拟器启动支持，也没有
验证头部 SHA-1。

## 相同的变换与不同的参数

以下代码偏移属于各自 master 成员；运行时地址为 `0x10020000 + 偏移`。
表地址和 RAM 地址已经是运行时地址。

| 项目 | Z6 II | Z7 II |
| --- | --- | --- |
| 整包检查入口 | `0x37EA40` | `0x37C638` |
| 摘要检查 | `0x392286` | `0x38FE82` |
| 字节变换 | `0x39EA3C` | `0x39C310` |
| 原始引导材料 B8 的读取地址 | `0x10000088` | `0x10000088` |
| 传入的 32 位种子参数 | `0x44C` | `0x44B` |
| 机型串 | `Z_6_2` | `Z_7_2` |
| 种子折叠后的表索引 | 72 | 79 |
| 机型折叠后的表索引 | 20 | 120 |
| 第一张 256 字节表 | `0x12078C96` | `0x12068276` |
| 第二张 256 字节表 | `0x12078D96` | `0x12068376` |
| 外层三张表的起点 | `0x11990A44` | `0x119800D0` |
| 摘要上下文 RAM | `0xC2B2B608` | `0xB2B422C8` |

三张外层表的连续 `0x300` 字节、两张摘要变换表，以及从装入乘数
`0x260` 到函数返回的 `0x22` 字节循环均逐字节一致；哈希见对照数据。
代入各自的种子和机型串后，两款的 S8 序列不同。Z6 II 原始字节变换
例程对三组合成输入的执行结果与恢复的累加公式一致；字符分类由实验
环境提供，未使用真实 B8。

本次确认了共享查表内容和变换实现，尚未确认 seed 候选集合的跨机型
适用性。`0x44C/0x44B` 是已知的 32 位算法参数，不是
未知的 8 字节 B8，也不是最终 K8。关系仍是 `K8 = B8 XOR S8`；
S8 不同不能单独证明最终 K8 不同，因为 B8 尚未取得。

## 更新路径选择条件

| 作用 | Z6 II master 偏移 | Z7 II master 偏移 |
| --- | --- | --- |
| 类别 2/4 的共用文件检查 | `0x37E016` | `0x37BC0E` |
| 包目录解析器 | `0x38F744` | `0x38D340` |
| 读取包格式标志 | `0x38F992` | `0x38D58E` |
| 保存扫描记录 | `0x37F8DC` | `0x37D4D4` |
| 将记录载入更新状态 | `0x37FEAC` | `0x37DAA4` |
| 根据类别读取状态 `+0x68` | `0x37FF28` | `0x37DB20` |
| 根据返回值分派检查 | `0x3D7970` | `0x3D6938` |
| 非整包处理入口 | `0x37E886` | `0x37C47E` |

两机型类别 2/4 都先调用共用文件检查，再从文件偏移 `0x20` 进入
目录解析器。解析器成功处理编码目录后，把自己的上下文 `+8` 写为
常量 1；成员数则是另一处的 16 位字段。扫描记录 `+0x1C4` 在对应
分支保存这个格式标志，记录选择随后把它复制到更新状态 `+0x68`。
分派器对非零值调用整包检查，对零调用非整包处理。

这补足了此前缺少的调用者与写入者证据：`+0x68` 不能称为“成员数”，
也不能由其为零直接推导出“裸 master 可以安装”。非整包处理还服务于
其他更新类别，其存在不能代替 EG 文件的前置分类和目录检查。

## 原始目录解析例程的局部执行

两份原始解析器均从传入文件的 `0x20` 开始执行。实验环境只代替文件
定位和读取、内存复制和清零、缓存维护及 ASCII 大写转换；解码、字节序
转换、目录遍历与接受/拒绝分支执行原始代码。

| 机型与输入 | 返回值 | 结果 |
| --- | ---: | --- |
| Z6 II 原厂整包 | 1 | 目录接受，格式标志 1，成员数 5 |
| Z6 II 原厂裸 master | 0 | 目录拒绝 |
| Z6 II 原厂裸 slave | 0 | 目录拒绝 |
| Z7 II 原厂整包 | 1 | 目录接受，格式标志 1，成员数 5 |
| Z7 II 原厂裸 master | 0 | 目录拒绝 |
| Z7 II 原厂裸 slave | 0 | 目录拒绝 |

该结果支持“这两份 C 1.70 的原厂裸 EG 不能直接通过类别 2/4 的共用
包目录解析器”。实验未执行文件名扫描、完整型号资格
检查、SHA-1、成员 CRC 检查或存储编程；不是相机完整安装实测，也不
扩大为对所有版本、文件格式及更新入口的断言。上述 CRC 通过结果来自
独立的包结构检查，不来自此局部执行。

## 立即数组合候选检查

2026-10-24 对两款 C 1.70 的 master、slave 共四个引擎成员进行有限
候选检查。输入先绑定原厂文件 SHA-256，再检查解码后的目录、成员
CRC 与容器 CRC。可复跑脚本为 `tools/seed_immediate_probe.py`，
结果见[候选检查记录](../../artifacts/seed_immediate_candidates/report.json)。

检查提取 ARM 无条件及 Thumb-2 部分 MOV/MVN 立即数形式，以及 MOVW 后
32 字节内、同一寄存器且中途未被覆盖的 MOVT 组合。遇到跳转或调用
即停止该寄存器的组合。随后将同一指令模式、起点相距不超过 128
字节的两个值，分别按两种字节序和两种字序组成 8 字节候选。
这些只是候选，未要求它们实际写入引导窗口；数据区中的指令形状
也可能被纳入。

| 候选来源 | 新增不同候选数 |
| --- | ---: |
| Z7 II master | 406,157 |
| Z7 II slave | 1,198 |
| Z6 II master | 76,448 |
| Z6 II slave | 100 |
| 合计 | 483,903 |

候选在四个成员之间去重，因此后扫描成员的新增数不代表其构造代码
更少。每个候选分别按原始 B8 和最终 K8 解释，针对两款机型各自的
完整解码主体、S8 和原厂头摘要检查，均未匹配。主体哈希预先计算，
每个候选只追加 8 字节；没有更改原厂输入或输出更新包。

本次还确认 Z7 II master 偏移 `0x37A8BA..0x37A8C8` 从
`0x10000080` 读取四个字节并复制到栈上，供后续参数调用使用；
`0x37C694..0x37C69C` 将 `0x10000088` 交给摘要上下文初始化，
`0x38ED3E..0x38ED4C` 从该指针复制八字节。上述都是读取路径，
尚未确认初始化写入者。

边界：未覆盖 Thumb 16 位立即数、条件 ARM 指令、一般算术构造、
逐字节写入、跨越上述距离的组合、引擎成员以外的程序或运行时输入。
没有命中不能证明分发包不含构造代码，也不能证明两机型共享或不共享
B8；本次不涉及原厂认证接受、菜单安装、存储写入或复位持久性。

复跑需安装 NumPy、Capstone，并提供本地原厂输入：

```text
python -B tools/seed_immediate_probe.py --master <z72-master> --z72 <z72-package> --z62 <z62-package> --report <report.json>
```

报告仅保存身份摘要、计数、搜索范围和匹配状态，不保存固件或候选
密钥字节。

## Z5 C 1.50 与扩展候选检查

2026-10-24 增加 Z5 C 1.50 原厂整包交叉样本，文件长 36,011,790
字节，包含 EX、TPT、EG、VR 四个成员。目录、四个成员 CRC 和容器
CRC 均通过。文件身份与检查结果见
[Z5 交叉检查记录](../../artifacts/z5_seed_comparison/report.json)。

| 参数 | Z5 C 1.50 |
| --- | --- |
| 引擎成员 | `eg1650_015001.bi`，34,603,578 字节 |
| 原始 B8 读取地址 | `0x10000088` |
| 32 位算法参数 | `0x448` |
| 机型串 | `Z_5` |
| 两张表的折叠索引 | 76、55 |
| 字节变换表地址 | `0x11D010E4`、`0x11D011E4` |
| 整包检查成员偏移 | `0x1B6E10` |
| 附加材料设置成员偏移 | `0x1BDD96` |
| SHA-1 检查成员偏移 | `0x1BEEDA` |
| 字节变换成员偏移 | `0x1BDCA8` |

两张表与 Z7 II 相同，但机型参数不同。Z5 仍然读取引导窗口，没有
在这处调用中直接提供原始 B8。不能由地址与查表内容相同推定 B8
相同。原始解码例程 `0x1BC0DA` 的 1,024 字节局部执行确认：索引
为零时保留开头 32 字节空格标记，只解码其后的内容。本次用于摘要
比较的主体均重新从原厂包取得，包含标记及完整尾部。

扩展检查结果如下，均未匹配：

- Z5 解码主体的 36,011,751 个连续八字节窗口，分别按 B8、K8
  解释，针对 Z5 自身与 Z7 II 各检查 72,023,502 次。
- 加入 Thumb 16 位立即数，检查连续八个字节值或四个半字值，跨度
  不超过 256 字节：Z6 II/Z7 II 四引擎去重后 1,698,343 个候选；
  Z5 引擎另检查 1,524,205 个候选。两批独立计数，可能相交。
- 从部分立即数指令起点做最长 48 条的直线常量传播，处理移位、
  异或、加减、字面量读取与连续内存写入，遇分支或调用停止：
  Z6 II/Z7 II 共 3,443 个候选，Z5 另有 2,738 个。合成样例已验证
  运算后写入形成的 B8 能被识别。
- 合并三个机型提取出的 13,106 个不同立即数值，检查全部有序双字
  组合、两种字节序及 B8/K8 两种解释，不限制指令距离。针对每个
  原厂包比较 687,068,944 次，三款合计 2,061,206,832 次。

另检查 Z7 II C 1.10、1.61 的原始调用者：分别在成员偏移
`0x2AC45A`、`0x37B7B4` 读取同一引导地址，并传入 `0x44B`。
这确认早期版本也存在该读取路径，未确认其初始化来源。

以上扩大了有限候选范围，没有穷尽任意算术、分支路径或整个 64 位
空间，也没有确认引导窗口写入者；没有恢复实际 K8。

## 引导窗口映射与字面量写入补充

2026-10-24 进一步分析 Z7 II 启动映射。成员偏移 `0xBCF0` 从
`0xBFCC` 取出 `0x10030000`，随后在 `0xBCF4` 写入 TTBR0。
以该表作短描述符转换时，虚拟地址 `0x10000088` 的一级表项位于
成员偏移 `0x10400`，值为 `0x1000C426`；它描述一个非超级节的
1 MiB 节，得到物理地址 `0x10000088`。这项静态计算以 TTBCR
选择 TTBR0、该表实际生效且没有其他转换阶段为前提，不是运行时
寄存器观测，也不能确定后备存储类型或数据初始化来源。页表解释
参考 [Arm 短描述符转换说明](https://developer.arm.com/community/arm-community-blogs/b/tools-software-ides-blog/posts/developing-jython-scripts-for-ds-5-translation-table-decoder)。

主引擎启动表的 20 条复制、清零记录均不覆盖
`0x10000000–0x1001FFFF`。这只排除了该表对引导前缀的初始化，
不能排除其他代码、DMA 或更早的启动阶段。

为覆盖旧 ARM 常见的构造形式，常量传播检查增加了 PC 相对字面量
加载起点，以及内存访问后的地址自增更新。五个引擎成员仍按每个
起点最多 48 条指令、遇跳转或调用停止的边界检查；跨成员去重后
得到 15,461 个不同的八字节写入候选。分别按 B8、K8 解释，对
Z5、Z6 II、Z7 II 原厂摘要检查，均未匹配。合成样例确认了分离
字面量、异或、地址自增写入及最终 B8 摘要匹配的完整检查链。

此范围内没有识别出直接写入 `0x10000088–0x1000008F` 的位置。
结果及搜索边界见[引导材料来源检查](../../artifacts/boot_material_origin/report.json)。
尚未获得初始化程序或独立引导区样本，不能由这些有限的未命中结果
推出分发包中一定不存在 B8 构造代码。

## 尚未解决的问题

B8 的初始化来源和实际内容仍未确认。两机型都从同一引导地址取值，
不能据此认定内容相同，也不能排除由其他代码构造。下一步应追踪该窗口
的初始化写入者；若取得定义明确的 Z6 II seed 候选库，再对各自机型参数
进行候选验证，最终以原厂头部摘要匹配为准。当前不需要增加解码算法，
也不应直接把 Z6 II 的参数替换进 Z7 II 的安装检查。
