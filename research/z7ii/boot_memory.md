# 启动内存操作和完成等待

本阶段继续分析 C 1.70 原厂内存初始化设置及等待函数，实现有界清零的实验解释。
偏移为 EG 文件偏移，运行地址为 `0x10020000 + offset`。

## 已观察的设置与模型解释

master `0xC234` / slave `0xC280` 写入零源、两个低 16 位为 `0x4000` 的参数、
向上取整的 16 KiB 块数和目的地址，再向 `0x20070010` 写入 1。
两份设置函数、等待函数的对应字节一致，参数范围见
[前一阶段](boot_continuation.md)。本模型据此采用零填充解释，并清理完整取整块数。
实际硬件操作、块尾处理及完成时间尚无硬件验证；这三项属于实验假设。

| 角色 | 起始地址 | 请求字节数 | 模型清零字节数 | 不含末地址的结束位置 |
| --- | --- | --- | --- | --- |
| master | `0xB18AEDC0` | `0x12AF750` | `0x12B0000` | `0xB2B5EDC0` |
| slave | `0xC1017D80` | `0x8B71D4` | `0x8B8000` | `0xC18CFD80` |

补充 master `0xB1900000..0xB2000000` 的 7 MiB RAM，将清零范围内原有空洞接通。
这也是实验 RAM 容量选择，不代表完整硬件内存地图。

执行命令前检查零源、16 KiB 参数、非零且小于 `0x4000` 的块数、字对齐和整个
目的范围。主、从机器的可写范围分别限于 `0xB1800000..0xB2C00000` 和
`0xC1000000..0xC1A00000`。配置不匹配时产生错误并保持 RAM 不变，不向外设或
固件窗口执行写入。这不是通用 DMA 引擎；其他格式和操作尚未实现。

## 完成、应答和原厂错误处理

新增精确状态字 `0x20070008`，总配置字数为 373。成功清零后同步发布位 0，
无效设置或 `memory-init-error=on` 发布错误位 `0x10`。状态采用写一清零，软件
不能通过写入制造完成位。设备状态格式为版本 6，拒绝旧布局；完整迁移仍未验证。

master `0xC2A0` / slave `0xC2EC` 的原厂等待逻辑先检查错误，再检查完成，
没有软件超时。完成路径写回 1，返回零；错误路径写回 `0x10`，返回 `0xFFFFFFFF`。
在成功路径中，原厂启动代码随后跳至 master `0x416C60` / slave `0x1474A8`。

错误返回使启动调用者把 r0 置零并调用 `0x2B4`。该地址的原厂指令为致命自循环，
不会返回。负对照实际单步三次，确认 PC 均保持该地址；错误场景没有到达下一入口。
这不同于先前平台配置封装中被后续调用覆盖的中间错误。

## 验证

```sh
python tools/memory_boot_probe.py --master /path/to/eg1840_mas_01700.bin --slave /path/to/eg1840_sla_01700.bin --qemu .build/build/qemu-system-arm --destination .local/memory-run
```

2026-10-10，五个场景通过：两角色原厂路径、两角色强制内存错误、slave 选择位置位。
通过普通 RAM 预加载，将整个模型操作范围填为 `0xA5`，两侧各放置四字节保护字。
成功路径逐字节检查 19,595,264 / 9,142,272 字节均为零；错误路径逐字节检查填充
保留。两侧保护字、三段原厂复制、原厂页表和 SVC 栈均符合预期。
本地物理 RAM 快照用于比较，固件和快照均不纳入公开源码。

主板合成检查覆盖有效清零、范围／对齐／计数／参数／源错误、状态应答和复位。
两种主板、22 项 Python 检查、270 项渲染器 ASan/UBSan 检查通过；
启动衔接、结构及显示回归通过。证据见
[验证报告](../../artifacts/memory_boot_validation/report.json)。

成功场景从原厂复位入口连续执行至下一入口之前，没有修改指令、重新指定 PC 或
替换原厂页表。下一入口本身、RTOS、双 EXPEED 协作、LCD 与菜单仍未执行和验证。
