# 菜单固件更新路径与实验更新存储

分析固件定位了原厂菜单固件更新的静态结构:入口服务、卡上更新文件的
命名规则、包完整性检查库,以及服务在缺少存储卡时的检查行为。本页
同时记录实验室的阶段性实现:更新存储、菜单门控的安装流程与重启后
加载,并明确哪些环节是实验代替品。以下文件偏移均为 master EG
(`eg1840_mas_01700`)的成员内偏移,运行时地址为
`0x10020000 + 文件偏移`。

## 固件管理服务

master 固件内有一个按名称注册的服务表,文件偏移 `0x90BB50` 一带可见
`Key`、`ChangeLV`、`ChangeCaptureMode` 等名称,每项名称后跟随一个
`0xB181xxxx` 的运行时对象指针;`FWUpdate` 名称位于文件偏移
`0x90BC70`,对应对象指针 `0xB181A3DC`。记录间距不完全一致,表项
边界未逐项复原;`FWUpdate` 即菜单固件更新使用的服务名。

服务的实现与日志字符串位于文件偏移 `0x7470xx..0x747340`,字符串池
紧随代码。日志前缀 `CFirmwareManagementService_` 暴露了两个方法阶段:

| 方法 | 字符串(文件偏移) | 含义 |
| --- | --- | --- |
| `GetProprietyCheck` | `:Failed, %d`(`0x7471A8`) | 检查失败 |
| 同上 | `No update file.`(`0x7471E0`) | 卡上没有更新文件 |
| 同上 | `There is many update files.` | 更新文件不唯一 |
| 同上 | `There is no update files targeted.` | 没有适配本机的目标 |
| 同上 | `ExMCU update file exist.` | 外部微控制器更新在场 |
| 同上 | `BobyVR update file exist.` | 机身引导更新在场 |
| 同上 | `Lens firmware update file exist.` | 镜头固件更新在场 |
| `Execute` | `:RequestFailed %xh.`(`0x7472B8`) | 执行请求失败 |
| 同上 | `FW update succeeded.`(`0x7472F0`) | 更新成功 |
| 同上 | `FW update failed.` / `:ExecuteFailed.` | 更新失败 |

服务同时发出通知 `ID_NOTIFY_EVENT_FWUP_RESULT:%d.`(`0x7472C0`
附近),即更新结果以通知事件回报给界面层。方法名与字符串只能证明
检查与执行两个阶段的划分和卡上目标种类的枚举,不能证明菜单项到
服务的调用时序;该时序尚未在运行中验证。

## 卡上更新文件命名

文件偏移 `0x2086838` 起是 `B:\` 与 `firmware\` 两个路径字符串,
随后是成组的更新文件名模板,`?` 为版本通配:

`????.BIN`、`NKLD????.BIN`、`WR1_????.BIN`、`_D_WT????.BIN`、
`_TPFW????.BIN`、`Z7_2_????.BIN`、`????_???.BIN`、`WRR10_??.BIN`、
`_WT?_????.BIN`、`_TPJ01??.BIN`、`WR??????.BIN`、`LF??????.BIN`、
`ML??????.BIN`、`MA??????.BIN`、`TC??????.BIN`、`RG??????.BIN`。

`Z7_2_????.BIN` 与原始更新包名 `Z7_2_0170.bin` 一致,是整机更新包
的卡上文件名;`MA??????.BIN`、`ML??????.BIN` 等对应单成员文件。
模板表说明服务在 `B:\firmware\` 目录下按这些名字扫描候选,这与
`GetProprietyCheck` 的多文件判定字符串互相印证。字符串表没有直接
代码引用(引用经由运行时重定位或寄存器基址构造),扫描调用点尚未
定位。

## 包完整性检查库

文件偏移 `0x38F11C` 与 `0x38FFA4` 有两处断言文件名
`FirmwareChkLib.c`,其前部为 Thumb 代码,代码池内出现
`0x5A827999`(`0x38F0xx` 一带)——SHA-1 轮常数。结合本地更新包
分析(整包在外层 CRC-16 之外还有 SHA-1 完整性检查)可知该库是
检查实现的一部分;库的函数边界、摘要输入范围与真实签名材料未
复原,本仓库也不包含任何校验或构造工具。

卡子系统本身在固件内有完整服务(`CCardService`、`CARDSRV` 任务与
`eSyscCommandId_CardMount*` 命令族,文件偏移 `0x2085CB0` 一带);
实验室尚未建模存储卡设备、文件系统与挂载命令,这是原厂更新路径
在本环境停下的第一个外部依赖。

## 版本记录

两份 EG 成员文件偏移 `0x20` 均为十二字节版本记录(如
`Ver.01.70.02`),详见[容器与成员记录](container.md)。菜单固件
版本页显示的字符串来源未逐段跟踪;实验更新存储直接读取该记录
作为已安装镜像的版本描述。

## 整包摘要检查(K8 签名)

菜单更新在读入文件后、写入之前执行一个整文件摘要检查。分析固件
恢复了完整算法(文件偏移均为 master EG 成员内偏移,运行时地址为
`0x10020000 + 偏移`):

- 检查入口 `0x37C638`:读取整个更新文件,包体起点为缓冲区 `+0x20`,
  包体长度为文件长减 `0x20`,调用 `0x38D2C2` 三表异或解码;起始
  索引为零时跳过文件前 `0x20` 明文头与 `0x20..0x40` 的标记块,从
  `0x40` 起以表索引 `0x20` 解码。文件选择器 `0x37DB20` 对类别 2
  (独立 EG 成员文件)与类别 4(整包)都返回非零,两类文件共用该
  检查。
- 摘要期望值是文件头前 20 字节;校验上下文位于 RAM `0xB2B422C8`
  (`0x34` 字节:`+0` 包体指针、`+4` 长度、`+8` 变换回调、`+0xC`
  8 字节附加输入、`+0x14` 种子、`+0x18` 机型串、`+0x20` 期望
  SHA-1)。`0x38FE82` 把种子取反字节反转,经回调变换 8 字节附加
  输入后追加到包体末尾,长度加 8,计算 SHA-1 与期望值比对。
- 变换回调 `0x37C634 → 0x39C310`:种子四字节异或折叠为一张 256 字节
  表的索引;机型串 `Z_7_2` 按数字折叠为另一张表的索引;流字节为
  `表1[折叠] + 表2[索引] × (0x260 + i)`。种子 `0x44B`,两张表与
  三张解码表都位于本镜像内(运行时 `0x12068276`、`0x12068376`、
  `0x119800D0`)。
- 即 `SHA1(标记块 + 解码包体 + (K8 ⊕ 派生流)) == 文件头[0:20]`,
  其中 K8 是引擎地址 `0x10000088` 处的 8 字节引导区材料。对
  Z7 II C1.70 的实测:原厂固件运行到菜单就绪后 `0x10000000..0x10020000`
  窗口保持全零,五个成员与解码流的全部 8 字节窗口(约九千五百万个)
  经中态加速逐一检验,无一满足该摘要——K8 不随更新文件分发,属于
  机身引导区内容。实验室因此把 K8 作为独立的本地输入(与固件镜像
  同等地位),`analyze/upgrade_signature.py` 实现上述检查的验证与
  摘要重算:修改固件后重新计算摘要并以同样的方式打包,即可通过同
  一校验。该模块不向磁盘写出解码固件。

### K8 获取路径的排除记录(2026-10-20)

对照公开研究与补充实验,把可行路径收敛如下:

- 公开研究交叉验证了同一摘要公式(头部 20 字节 == 解码体 ∥ K8),
  并指出:较新的 EXPEED 7 机身把 8 字节种子作为字面量放在镜像内
  SHA-1 初始向量前 24 字节处,因此可以直接搜出;而 EXPEED 6 机身
  (含本机)的种子由加载器代码中的立即数构造——即种子写在引导
  加载器里,由加载器写入引擎引导窗口,不随本机固件包分发。
- 补充暴力排除:以两处 SHA-1 初始向量邻域(±128 字节)、原始包
  头、解码流头部与 master 头部共 1341 个候选种子,对
  线性/二次两种流形式、`0x260`/`0xD3` 两种乘数与全部
  `(基准,乘数)` 字节组合(每种子 262,144 种)复核头部摘要,全部
  不命中;第二处初始向量经查属于无线局域网驱动,与更新校验无关。
- 主机端尼康软件目录扫描:仅镜头数据组件与参数库,无加载器镜像;
  `NKLD01.lns`/`NKLD02.lns` 为镜头档案文件,与加载器更新文件只是
  名称相近。
- 剩余可行路径:取得本家族的加载器更新文件(相机存储卡上的
  `NKLD????.BIN`,种子应在其按 `0x10000000` 映射的 `+0x88` 处或
  由其立即数构造);或读取真机引导窗口。随包的机身 VR 成员经完整
  逆向确认为机身防抖控制器的页式闪存映像(见
  [机身 VR 成员](body_vr_member.md)),与引导区无关,已从 K8 路径
  中排除。任一途径成功后,`--boot-key` 直接接入,验证代码不变。


## 刷入后的整机复位重启

菜单更新在原厂路径的末端由固件写入机身存储并复位重启。实验室以
`nikon-z72-boot-store` 设备补上这一段:每个引擎一个启动存储,每次
整机复位把存储的镜像集(固件镜像与 `path@address` 辅助文件)重新
复制进代码窗口,并把两个核心的程序计数器重置到镜像入口,模拟
"机身从存储启动"。控制台的安装流程因此变为:

1. 菜单前台门控与签名验证如上;
2. 镜像与清单提交到持久更新存储;
3. 待装镜像写入运行中机器的启动存储(`qom-set` 的 `image` 属性即
   编程步骤);
4. QMP `system_reset` 整机复位,板卡重载存储镜像,两个引擎从镜像
   入口重新启动,控制台按首次启动的同一步骤(观察同步等待、供给
   同步边沿与帧同步)放行,机器从刷入镜像回到拍摄前台——全过程
   不重启主机进程。

`/update/remove` 回退走同一复位路径(编程回原厂镜像再复位)。
运行中镜像的版本记录(`0x10020020` 的 12 字节)由状态接口从机器
内读出,作为"机器确实从刷入镜像启动"的机内侧证据。

## 实验更新存储与菜单门控安装

存储卡、文件系统、包校验与机身闪存写入均未建模,因此控制台以
实验更新存储代替原厂更新的落盘环节:

- `analyze/update_store.py` 定义候选接受与存储。候选 master 必须保持
  可执行启动结构:长度在主控存储窗口内、成员 CRC 余数为零、版本
  记录格式正确、复位分支与初始化表记录数不变、通信窗口零记录与
  引导前缀(首 MMIO 存储及其页表恒等映射)不变。原厂镜像与本地
  重建镜像(含尾部追加代码、重算 CRC)都通过;截断、CRC 破坏、
  版本记录畸形、启动布局改变都被拒绝。**原厂研究探针锁定的
  显示窗口摘要在此不适用**——更新本来就可能改写这些字节。
- 安装把镜像与清单(`master.bin` + `manifest.json`,记录 SHA-256、
  长度、版本、时间)原子写入持久目录;清单是提交点,无清单的
  镜像视为残留。每次启动重新校验存储镜像与清单一致,不一致则
  回退原厂镜像并显示存储错误,不静默掩盖。
- 安装入口 `tools/web_console.py` 的 `/update/install` 要求前台为
  菜单应用(应用索引 1):菜单未打开时拒绝,浏览器面板同样只在
  菜单打开时启用按钮。安装先完成整文件摘要验证,再编程运行中
  机器的启动存储并整机复位,机器从存储镜像重新启动;
  `/update/remove` 以同一复位路径回退原厂。
- 待安装更新文件由控制台启动参数 `--update-image` 提供(带签名的
  卡片式更新文件),`--boot-key` 提供 8 字节引导区密钥材料;两者
  都是本地研究输入,本仓库不提供制作、解码或重打包工具;更新存储
  目录由 `--update-store` 指定。

该流程在"菜单内的固件更新"这一语义上还原了操作路径(打开菜单、
执行更新、复位加载),整文件摘要校验已按上文恢复的算法实现;仍由
主机侧代替的环节是卡扫描与文件读取(无存储卡模型),签名通过后
的编程与复位由启动存储设备在机内完成。菜单项目前不要求到达原厂
"固件版本"条目,只要求菜单应用为前台。固件内 `FWUpdate` 服务的
运行时激活、版本页显示与通知回报仍属未验证边界。

## 验证

- 固件无关检查:`checks/test_update_store.py`(合成结构镜像上的
  接受/拒绝与存储生命周期)、`checks/test_upgrade_signature.py`
  (合成表镜像上的摘要算法、往返打包、错误密钥/篡改/缺标记拒绝)
  与 `checks/test_web_console.py` 的更新用例(签名验证入暂存、菜单
  门控、安装、回退、状态上报与机内版本记录)。
- 原厂镜像端到端:`tools/console_update_check.py` 经控制台 HTTP
  路径驱动完整循环——原厂启动、菜单外安装被拒、单击开菜单、
  验签安装、整机复位后以更新镜像回到拍摄前台(并核对机内版本
  记录)、再经主机侧重启保持、复位路径回退原厂。
  记录见[菜单更新验证](../../artifacts/menu_update_validation/report.json)。
