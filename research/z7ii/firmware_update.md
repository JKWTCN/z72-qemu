# 菜单固件更新路径与实验更新存储

分析固件定位了原厂菜单固件更新的静态结构:入口服务、卡上更新文件的
命名规则、包完整性检查库,以及服务在缺少存储卡时的检查行为。本页
同时记录实验室的阶段性实现:更新存储、菜单门控的安装流程与重启后
加载,并明确哪些环节是实验代替品。以下文件偏移均为 master EG
(`eg1840_mas_01700`)的成员内偏移,运行时地址为
`0x10020000 + 文件偏移`。

## 固件管理服务

master 固件内有一个按名称注册的服务表,文件偏移 `0x90BB50` 一带可见
`Key`、`ChangeLV`、`ChangeCaptureMode` 等名称,每项名称后跟随一个
`0xB181xxxx` 的运行时对象指针;`FWUpdate` 名称位于文件偏移
`0x90BC70`,对应对象指针 `0xB181A3DC`。记录间距不完全一致,表项
边界未逐项复原;`FWUpdate` 即菜单固件更新使用的服务名。

服务的实现与日志字符串位于文件偏移 `0x7470xx..0x747340`,字符串池
紧随代码。日志前缀 `CFirmwareManagementService_` 暴露了两个方法阶段:

| 方法 | 字符串(文件偏移) | 含义 |
| --- | --- | --- |
| `GetProprietyCheck` | `:Failed, %d`(`0x7471A8`) | 检查失败 |
| 同上 | `No update file.`(`0x7471E0`) | 卡上没有更新文件 |
| 同上 | `There is many update files.` | 更新文件不唯一 |
| 同上 | `There is no update files targeted.` | 没有适配本机的目标 |
| 同上 | `ExMCU update file exist.` | 外部微控制器更新在场 |
| 同上 | `BobyVR update file exist.` | 机身防抖更新在场 |
| 同上 | `Lens firmware update file exist.` | 镜头固件更新在场 |
| `Execute` | `:RequestFailed %xh.`(`0x7472B8`) | 执行请求失败 |
| 同上 | `FW update succeeded.`(`0x7472F0`) | 更新成功 |
| 同上 | `FW update failed.` / `:ExecuteFailed.` | 更新失败 |

服务同时发出通知 `ID_NOTIFY_EVENT_FWUP_RESULT:%d.`(`0x7472C0`
附近),即更新结果以通知事件回报给界面层。方法名与字符串只能证明
检查与执行两个阶段的划分和卡上目标种类的枚举,不能证明菜单项到
服务的调用时序;该时序尚未在运行中验证。

已进一步定位并局部执行资格检查分段 `0x747048`。它调用
`0x3D645A`，后者依次检查 `0x37AA82`、`0x37AAA6`；状态快照由
原始函数 `0x3D9A2A` 读取，长度为 `0x50`。成功时服务返回 1、
原因字段为 0；两类条件失败均返回 3、原因字段为 1。下表使用快照
内偏移，不预先给尚未追踪来源的枚举赋予电量百分比或硬件型号含义：

| 检查 | 已执行确认的条件 |
| --- | --- |
| 第一段 | `word[0] != 0`，且 `byte[4]` 既不是 0，也不是 5 |
| 第二段 | `byte[8]`、`byte[0x20]`、`byte[0x38]` 均不等于 1 |
| 等级选择 | `byte[7] == 1` 时取 `byte[0x23]`，等于 2 时取 `byte[0x3B]`，否则取 `byte[0x0B]` |
| 等级条件 | 选择结果必须小于 2 |

这里执行的是原始服务函数及其状态判断，快照内容为合成输入；锁操作
和诊断日志由执行环境代替。11 组输入确认上述分支，但未证明运行中
菜单会生成这些状态，也未验证更新资格的其余分段或安装执行阶段。

另一个服务段 `0x747092` 调用 `0x3D636A` 生成版本列表，只在条目数
等于 1 且类别为 2、4 或 8 时返回成功。通过前述整包扫描后，在合成
已安装版本参数下实际得到 5 个条目，类别顺序为 `4, 9, 2, 3, 17`；
该服务段返回 3、原因字段为 4。这里的条目数不能直接当作卡上的
更新包数量，也不能将这个局部返回值视为整机包被相机拒绝的证明。
菜单何时选择这一服务段、何时进入整机更新路径仍需进一步验证。

## 卡上更新文件命名

文件偏移 `0x19603D0` 起的记录包含类别、模板指针及可选条件函数。
普通扫描入口 `0x37C360` 遍历 11 项，依次包括 `EX1840??.BIN`、
`EG1840??.BIN`、`Z7_2_???.BIN` 等。类别 4 的模板实际只有三个 `?`，
位于 `0x208680C`；此前记为四个 `?` 的说法不正确。

目录搜索 `0x37C236` 对目录记录起始处的短名逐字节匹配，`?` 匹配一个
非零字符，普通字符经大写转换后比较。找到记录后，`0x37C218` 从
记录 `+0x0E` 的宽字符长名生成打开路径。因此，模拟记录中的短名
`Z7_2_0~1.BIN` 能匹配模板，随后按长名打开 `Z7_2_0170.BIN`。
这个短名是明确构造的目录输入；实际卡上的别名由文件系统决定，不能
仅凭模板判断完整长文件名不受支持。

原始初始化数据中 `0xB1887D00`、`0xB1887D04` 的两个根指针分别
指向 `A:\`、`B:\`。已执行确认：选择字段低四位为 0 时使用 A，
为 2 时使用 B；位 `0x10` 允许在目录打开失败后尝试另一个根。
目录成功打开但未找到匹配文件时，这个函数直接返回，不执行同样回退。
探针从原始初始化数据恢复这两个指针，选择字段及目录内容为合成输入。
上述目录搜索入口没有使用位于 `0x2086840` 的 `firmware\` 字符串。
原始候选枚举循环则通过 `0x37D372` 使用初始化数据中的相对目录表：
目录索引 0 对应 `firmware\`，索引 1 对应空前缀。探针已执行两种
路径构造；目录记录本身由执行环境提供，存储卡上的真实目录设备
仍未建模。

## 存储卡栈的结构

分析固件把"卡"拆成四层,每层的证据与剩余未知如下:

- **卡服务**(master):请求保存在 `0xB1D53D8C`(操作、槽位、结果)。
  查询操作的处理函数在文件偏移 `0x463048`:请求区 `+4` 的槽位字节为
  0 时走本地驱动路径 `0x462A0E`,为 1 时经 `0x1038866` 向从引擎发
  资源 8、操作 1 的委托(整机运行的 -821 回复即来自该路径,见
  [前台等待分析](message_wait.md));其他槽位值返回错误 6。
- **槽位驱动表**:指针 `0xB18105BC`,初始化数据为零,由卡服务模块
  初始化(文件偏移 `0x59E866` 一带,模块号 0xD0)在运行时注册。
  `tools/card_slot_probe.py` 以写观察点捕获了这次注册:表位于
  `0x108ABB28`,每槽 0x38 字节,槽 0/1 的函数指针各指向
  `0x481571`/`0x481715`(构造)、`0x73E770` 一带(槽操作薄包装,
  再调 `0x462676`、`0x462240` 等工作函数)与 `0x4626A4`/
  `0x462154`(配置谓词 `+0x28`)。配置谓词链最终读取
  `0xB1808B50 + 槽位` 的使能字节——这是卡设备的第一道门:该字节
  为零时驱动直接报告未配置,SD 寄存器访问不会发生。观察记录见
  [卡槽驱动表观察](../../artifacts/card_slot_table/report.json)。
- **SD 驱动**:文件偏移 `0x215D9E4` 起 `CSdDriver_Setup`,其后
  `SD0_Mount_Retry`、`SD0_Wait_Tran_State`、`SD0_Read_Sector`、
  `SD0_Write_Sector`、`SD0_Card_Init`、`SD0_Send_Command00/06/11`、
  `SD0_Send_ACommand41`、`SD0_Err_Recovery`、`SD0_Set_Bus_Power`
  及成套的 `SD1_*` 命令级函数名;`0x769A94` 起另有
  `CSdUhs2Driver_ReadSector/WriteSector` 与 `XQD High Speed Memory
  Card` 字符串。命令编号(CMD0/6/11、ACMD41)说明驱动直接构造 SD
  协议命令;UHS-II(CMD11 电压切换)与 XQD 描述与双卡槽机型一致。
  相邻的 `SDIODEV`/`GSPI` 字符串属于 Wi-Fi 模块驱动,不是存储卡。
- **文件系统层**:master 内含 `MSDOS5.0FAT12/FAT16/FAT32` 与
  `NIKON5.0` 格式化模板及 `eSyscCommandId_CardFirstMountReqested/
  CardMountComplete/CardMountError` 挂载命令——固件自带 FAT
  12/16/32 的解析与格式化,未发现 exFAT 字符串。更新扫描调用的
  目录/文件函数(`0x47D2E6`/`0x47D3DA`/`0x4B3C00` 等)就在这一层。

为恢复 SD 主控制器的寄存器窗口，新增了两件工具:
`tools/card_slot_probe.py --ram-dump` 把整机运行时 RAM(代码窗
64MB 与 `0xB1800000` 起 72MB)经 memsave 导出;`tools/
card_worker_probe.py` 把快照载入有界执行环境,以原始指令执行
卡工作链并记录外设访问，包括已映射窗口中的读写。缺失内存立即停止，
未提供有效转储的低地址窗口保持未映射；探针不把缺失设备当成返回零。
当前结果见[卡工作链执行](../../artifacts/card_worker_execution/report.json)。

挂载边界已推进到文件系统层:`sd_native_probe --slot-query --list-directory`
经主机建模的文件系统任务分派(入口 `0x59DD08`,62 个操作码经 TBB
分发,请求块固定于 `0xB1D1B0C0`)完成槽查询后,卷表 `0xB2B464C0`
显示卷 0 已识别并绑定模块(挂载态 2),原厂目录打开返回原始
"未挂载"状态(0x80000403)而非崩溃。操作 4 分派成功;部分操作会经
`0x59DF2A` 向更深的任务转发——挂载操作与该嵌套任务链是文件系统
挂载验证的剩余段。该运行使用合成 FAT16 卡(512MiB、64KiB 簇,
原厂更新包以短名 `Z7_2_0~1.BIN` 存于根目录)。记录见
[挂载边界验证](../../artifacts/sd_native_mount_boundary/report.json)。

挂载操作的进一步定位:文件系统工作入口的内层分发(0x59CDE2 的
第二张 TBB)已逐操作解码——op 2/3 走 `0x424A88`/`0x424ADC`
(紧邻卷表引用区),op 4 走 `0x4513BE`(槽查询已走通)。直接向
固定请求块写操作码再调用工作入口的实验显示:op 3 干净返回状态
0x80002010,op 2 被请求复制机制改写(0x59DF2A 把 0xD0 字节请求
复制进转发块,合成操作码不生效)——挂载请求必须由原厂发送端
(卡服务的挂载路径)构造投递,这是下一 increment 的入口。
实验记录见[挂载尝试](../../artifacts/sd_native_mount_attempts/report.json)。

发送端扫描把管道完全打通:15 个原厂请求发送端(0x59DF2A 的
调用者)在有界环境里以客户端身份逐一执行,其中三个完成真实
投递——工作端收到 op 53/54 并返回真实状态 0x80001002 族
("卷未挂载")。两个 RTOS 边界补上了建模:对象句柄查询
0x80470400(经 0x32FF4C,需向输出参数写对象指针)与挂载执行体
直调。关键发现:挂载初始化(op 2 执行体 0x424A88)在槽查询
流程中**已经完成**——再次直调只返回"already active"(路径仅
6 条指令),卷状态 2 正是初始化后的产物;op 3(0x424ADC)是
卸载。2→4 的转换在事件驱动的卷扫描链里(0x39F290 一带的事件
旗标族),这是文件系统挂载验证的最后一段。扫描记录见
[挂载发送端扫描](../../artifacts/sd_native_mount_senders/report.json)。

早期按卷号直调 `0x447D04` 的实验包含卡序列号副本补写，属于
额外状态夹具；其状态字不能单独证明常规挂载或目录读取成功。
[历史挂载记录](../../artifacts/sd_native_fat_mount/report.json)保留该
边界。后续常规槽位查询与目录验证不使用此补写，也不调用这些
挂载扫描选项，证据见下节。

### 原始目录访问与更新文件名选择

`0x4631F2` 把逻辑槽位 0 映射为 `A:`，槽位 1 映射为 `B:`。
SD 卡的目录路径因此是 `B:\`。原始卷查找按 `0x88` 字节步长
遍历 `0xB2B464C0` 的两个记录；`+0x38` 是就绪字段，`+0x3A`
是文件系统种类，不能把两者混作挂载状态。常规槽位查询后的实测
记录为卷 0 名称 `B:`、就绪 1、种类 2；卷 1 未启用。

原始 `0x47D2E6` 打开 `B:\` 返回 0；`0x47D3DA` 读取真实 FAT
目录条目并返回文件名与长度，遇到零目录项时经 `0x47D3D6`
返回 `0x80000030`，这是本路径的正常结束值；关闭 `0x47D3F8`
返回 0。不再尝试参数未确认的其他目录发送端。

在含原厂整包和独立文本文件的 SDHC 镜像上，原始更新文件查找
`0x37C236` 从真实目录选择 `Z7_2_0~1.BIN`，长度 48,494,024
字节。该名称是 `Z7_2_0170.BIN` 的短文件名；`0x37C218` 在长名
字段为空时保留短名。扫描明确将 `0xB1887D10` 低位选择值设置为
2，以选择 SD 的 B 盘；这是有界输入夹具，不是菜单自动产生的状态。
只有文本文件的对照镜像在相同调用下返回 0，未选中升级文件。
见[卡目录与原始更新查找](../../artifacts/native_update_card_directory/report.json)、
[无升级文件对照](../../artifacts/native_update_card_no_candidate/report.json)。

该验证使用常规槽位查询、实际 FAT 目录读取和原始文件名匹配，
没有由主机提供目录条目或预设匹配结果。它证明文件名选择，不证明
整包认证。经 `0x4B3C04` 打开文件会提交另一条异步文件服务请求，
目前未收到该请求的回应，见
[文件服务边界](../../artifacts/native_file_service_boundary/report.json)。
文件字节读取、整包摘要检查和完整菜单更新仍待接通。
进一步的只读跟踪确认，`0x59C4AC` 经槽位映射回调 `0x462D92`
将 B 盘路由到逻辑槽位 1，随后走异步分支 `0x59D556`。
文件系统操作 9 在这里转为处理器间资源 9、操作 13、长度 28 字节的
消息，经 `0x368666` 提交。原始发送函数返回 1，共享队列
`0xB7CF0000` 的写入索引为 1、消费索引为 0。
该快照环境只执行发送端，没有运行另一端的消息消费者；因此提交成功
不会产生等待的文件系统完成事件。这是有界执行环境的缺口，不能据此
认定整机通信失败，也不能认定原厂整包已被校验拒绝。
接下来需要在双引擎执行中跟踪资源 9 的接收、文件操作和回应分派，
再验证返回字节来自同一张卡。记录见
[文件服务消息边界](../../artifacts/native_file_message_boundary/report.json)。
本组输入身份、已通过条件及未完成边界汇总于
[卡上更新文件验证](../../artifacts/native_update_card_validation/report.json)。

静态模块描述表位于运行时地址 `0xB1808AC4`，步长 `0x18`，包含
CF、SD、XQD 三项。表内函数指针是带 Thumb 位的运行时地址，必须先
清除低位，再减去 `0x10020000` 才得到 master 成员偏移：

| SD 描述项 | 运行时入口 | 成员偏移 |
| --- | --- | --- |
| 操作 0 | `0x10481C70` | `0x461C70` |
| 操作 1 | `0x10481E30` | `0x461E30` |
| 操作 2 | `0x10481F06` | `0x461F06` |
| 操作 3 | `0x10482016` | `0x462016` |
| 共享函数 | `0x104A14FE` | `0x4814FE` |

此前把 SD 指针当成成员偏移的记录多加了 `0x20000`，指向了其他
函数。因此撤回卡驱动依赖辅助 CPU 的 `0xB7C8` 表及必须先执行
ex1840 固件的结论；现有证据没有建立这种依赖。

`0xB1D28008` 是私有句柄表：起始为 16 位计数，`+4` 有三个指针，
`+0x10` 起是三个步长 `0x20` 的对象。它不是供模块描述记录直接
写入的注册表。探针保留快照中的空表，让原始打开函数创建对象；本次
操作 1 执行后，计数变为 1，第一个对象指针为 `0xB1D28018`。

逻辑槽位与模块内控制器索引必须分别传递。原始映射函数 `0x463212`
对逻辑槽位 1 返回 0，因此 SD 打开操作的前两个参数应为 `(1, 0)`。
此前 `(1, 1)` 测试访问了未使用的第二个在场描述符，并在 `0x8`
读取失败；该失败不能用于判断实际 SD 通道的初始化条件。

原始板级初始化 `0x47D8E4` 通过 `0x38047C` 查询已有对象表，
把 ID `0x149` 的 `0xB1801774` 写入总线句柄 `0xB18019A0`，
把 ID `0x5B` 的 `0xB1803884` 写入通道 0 在场描述符
`0xB18019F4`。有界执行中仅将事件清除 `0x3410D2` 建模为返回零，
对象查询和指针写入均由原始指令完成，没有构造替代描述符。
该初始化返回 0；随后以 `(1, 0)` 打开时无缺失内存访问，返回
`0xFFFFFCCB`（有符号值 -821）。总线检查 `0x4F87F4` 观察到
对象 `0xB1801774` 的 `+0x14` 启用字段仍为零。尚未证明该错误码
仅由这一字段决定，也没有完成卡协议初始化。低地址转储文件长度
为零，不能据此认定实际窗口内容全为零。

下一步应追踪总线对象启用和控制器初始化。现阶段卡服务的 RTOS
调用语义、板级上下文和控制器窗口仍未补全。探针的通用 RTOS 响应
仍为合成值，报告明确标记这些边界；寄存器访问或入口返回值本身也
不能证明卡已挂载或原厂更新能够执行。

### SD 总线与主控制器窗口

板级启动 `0x47E21C` 调用总线启用 `0x4F811E`。后者通过
`0x4F7212` 读取 `0x2B200058` 的位 16..21，最多等待 500 次，
值为 `0x11` 时才把总线对象的 `+0x14` 置为 1。随后原始总线
检查 `0x4F87F4` 还要求 `0x2B000010` 位 10 为 1，并要求
`0x2A900098` 低四位为 2。这里的位 10 是原始状态字的位置；
`0x4F67FE` 将它右移两位后返回，调用者再检查结果位 8。

补入上述三个明确标记的合成就绪条件后，原始代码访问
`0x2A800000` 起的端点配置，并向偏移 `0x10`、`0x14` 分别写入
`0x2A810000`、`0x2A820000`。随后在第一个窗口访问中断使能
`+0x34`、中断信号使能 `+0x38`、主机控制 `+0x28`、时钟
`+0x2C` 和超时/软件复位 `+0x2E`。向 `+0x2E` 写入半字
`0x010E` 后反复读取，单纯 RAM 无法完成复位。这些访问与
SDHCI 寄存器布局一致，不能再用全零存储代替主控制器。

模拟器新增可选 `nikon-z72-boot-config.sd-host=on`：在
`0x2A810000` 接入上游 `generic-sdhci`，其 DMA 地址空间连接到
所属引擎；`0x2A800000` 起 8 KiB 暂为配置读回存储，复位清零。
配置偏移 `0x64` 位 2 对应原始通道 0 时钟等待 `0x4807E2`，
模型将该只读位接到 SDHCI 内部时钟稳定状态；写入不能制造就绪。
该选项同时提供上述链路条件，其中时钟状态按请求字
`0x2B000004` 位 2 的反值同步产生。第二个 BAR 尚未实现。
卡镜像可通过 `-drive if=none,id=card,file=...,format=raw,snapshot=on`
与 `-device sd-card,drive=card` 接到 SD 总线；单引擎实验避免双引擎
同名总线选择歧义。双引擎可显式指定
`bus=/z72-sd-master/sd-bus` 或 `bus=/z72-sd-slave/sd-bus`。
配置读回不等于完整 PCIe 枚举，也没有实现所有端点功能。

原始总线初始化把 `0x4F7A18` 注册到向量 243；该处理函数通过
`0x4F703E` 读取 `0x2B200024` 位 28，并调用总线对象 `+4`
登记的回调。板级启动在 `0x47E3A8` 登记 `0x47E1F2`，后者
读取并确认 SDHCI `+0x30`，保存状态并设置事件标志。模型据此把
SDHCI 中断连接为 PCIe INTA 和 GIC 输入 243：状态位跟随源电平，
仅写 PCIe 确认字不能隐藏仍然有效的源。独立检查覆盖命令完成时
拉高、GIC 输入、确认期间保持，以及清除 SDHCI 状态后的撤销。

`tools/sd_native_probe.py` 将快照内原始卡代码的上述总线/主机窗口
读写转发到正在运行的 QEMU 设备。逻辑 SD 槽位 1 的使能字节
`0xB1808B51` 由探针明确置为 1，完整启动探针不写这个状态。
命令完成等待由设备真实中断状态提供，等待时推进 1 ms 设备时钟；
这是有界事件投递模型，没有运行原厂中断任务或内核调度。ADMA2-32
描述符先从快照执行环境复制到 QEMU RAM，设备完成后把实际 DMA
结果复制回来，报告记录长度和摘要，不用预设扇区数据代替设备读取。
其他服务或其他事件等待调用点立即停止，不返回通用成功值。

此前跳到地址 0 的原因已定位到执行环境：SVC 回调中的 PC 已指向
下一条指令，再加 4 会跳过返回地址恢复。修正后原始返回栈保持平衡，
固件无关的压栈、SVC、出栈回归检查通过；不再把该现象归因于固件。

在带 FAT 目录的 512 MiB 合成卡上，原始打开操作 `0x461E30`
返回 0，并完成 CMD17 与 512 字节 DMA。读回摘要与镜像首扇区一致。
原始 `0x461D5A..0x461D70` 检查首扇区偏移 `0x1FE/0x1FF`
是否为 `55 AA`：仅把偏移 `0x1FE` 改为 `54` 的对照仍完成读取，
但打开返回 `-830`。已确认两份镜像只有该字节不同，说明这是卡打开
阶段的拒绝条件，不是更新包摘要条件。
见[原始卡打开](../../artifacts/sd_native_host/report.json)与
[签名字节对照](../../artifacts/sd_native_bad_signature/report.json)。

`--slot-query` 继续到 `0x462A0E` 的文件系统附加路径。`0x59E95A`
经 `0x59E866` 提交独立工作任务请求，再从 `0x3410DA` 等待回应。
该等待尚未建模，探针在此停止；不能把初始为零的回应字段当成
工作任务已经成功。见[文件系统边界](../../artifacts/sd_native_slot_query/report.json)。

带卡的完整双引擎启动已到达拍摄前台，观察结束时槽位使能仍为
`[0, 0]`，端点 BAR 和 SDHCI 时钟仍为零。因此有界卡打开成功
尚未接通原厂完整启动中的卡挂载或菜单更新。
见[整机启动观察](../../artifacts/sd_runtime_startup/report.json)。

## 原始目录与成员检查探针

`tools/native_update_probe.py` 接收本地 C 1.70 master、原厂整包及可选
候选整包，执行目录解析 `0x38D340`，并从分类函数 `0x37BC0E` 执行
到 `0x37C100` 的版本列表构造入口。包解码、目录匹配、大小判断及
成员信息读取使用原始指令；文件读取、内存原语、缓存操作及 ASCII
字符标志由执行环境提供。运行中镜像描述符采用给定 stock master，
平台标签为零，容量为合成的 `0x04000000`，其余运行时 RAM 初始为零。
这不是从机身捕获的状态。探针另外提供明确的组件版本查询响应与参数
存储接口，继续执行原始版本格式化及分类返回路径；原厂包与候选均
返回 1，版本条目数为 5。组件响应为全零的合成描述符，未验证真实
组件通信或版本兼容性。

已执行结果见[原始更新检查记录](../../artifacts/native_update_checks/report.json)：

| 输入或环境变化 | 目录解析 | 成员检查阶段 |
| --- | --- | --- |
| 原厂整包、显示条件候选整包 | 返回 1 | 成员掩码 `0x1F`，到达列表构造入口 |
| 裸 master、截断到 64 字节的整包 | 返回 0 | 返回 12 |
| 容量恰等于原厂 master 长度 | 返回 1 | 返回 11；master 要求长度严格小于容量 |

最后两项说明目录和成员信息检查并不验证整包摘要或成员 CRC。
候选通过这一阶段，不能证明通过后续完整性检查或允许菜单升级。
探针报告同时记录资格检查的输入分支和执行入口，不包含固件内容。

报告另有 10 组目录输入、4 组扫描输入、8 组枚举输入和 12 组收集
输入。扫描从 `0x37C360` 出发，
实际经过模板遍历、目录搜索、长名转换、文件打开、目录解析、成员检查
与版本列表构造，再返回调用者。原厂包与候选返回 0，类别为 4；将
裸 master 作为同名整包提供，或让文件打开失败，均返回 3。文件系统
和组件通信接口由执行环境提供，未进入整包摘要或写入阶段。

### 选择记录到整包校验的局部执行

探针从目录收集入口 `0x37D984` 出发执行原始候选枚举循环
`0x37D71C`，由它完成文件匹配、路径构造、类别检查 `0x37D5BC`、
版本比较和记录构造 `0x37D4D4`。整机包被归入逻辑槽位 13，记录内
文件类别为 4；这两个值由原始循环产生。
槽位、文件类别与版本条目类别是不同字段，不能因数值相同就认定含义
相同。执行环境随后调用记录选择 `0x37DAA4` 和调度函数 `0x3D6938`；
编码包标志经记录 `+0x1C4` 传到运行时状态 `+0x68`，值为 1，
因此进入整包检查 `0x37C638`。

9 组枚举输入确认：原厂包及候选可以生成记录，裸 master、截断包、
其他机型文件名和空目录不能生成对应整机包记录；A 卡的根目录及
`firmware\` 子目录、B 卡的 `firmware\` 子目录均能按配置构造路径。
相同主体使用两个匹配文件名时，匹配数为 2，槽位 13 保留后枚举的
同版本条目。这个结果限于该循环，不能推断完整更新流程允许多个包。

### 原始目录收集入口的执行与接受条件

目录收集入口 `0x37D984` 已由原始指令执行。它先检查调用模式：仅
0、2、3、4、6、7、8、9、`0x0C`、`0x0D`、`0x0E`、`0x10`、`0x12`
被接受，其他值不改任何状态直接返回 0。接受后 `0x37D216` 清空
记录数组与版本摘要，前置段 `0x37D940` 分配记录向量（`0x6A40`
字节）和目录索引向量（`0xC8` 字节），分配失败即释放并返回 0。
主循环对两个目录索引各执行一次：`0x37D278` 按选择字段低四位选根
（0/1 取 A，2 取 B，3 在卡状态函数报告无卡时回落 A）、拼接相对
目录并经 `0x4B3EF0` 检查存在性，目录不存在则跳过该索引。存在的
目录经 `0x4B3E92` 枚举，回调 `0x37D6B5` 以原始代码把每条 `0x220`
字节记录复制进记录向量并登记目录索引，收集上限 50 条。枚举返回
`0x043A0080`/`0x043A0084` 之外的状态时整个收集中止返回 0，即使
前一个目录已成功。两个目录都成功后才进入枚举循环 `0x37D71C`，
最后 `0x37D922` 释放两块缓冲。

12 组收集输入确认上述接受条件：`firmware\` 与根目录单独或同时在场
均构造出正确路径，目录索引随收集来源记为 0 或 1，枚举循环用它重建
打开路径；两个目录都不存在时返回 0；任一目录枚举出错即中止，后
目录出错时已收集的记录也不进入枚举循环；调用模式 1、5 被直接
拒绝；模式 2 通过收集门、汇总头由 19 变为 1，但不产生整机包记录
——模式字节写入运行时状态 `+2` 后由枚举循环读取；选择字段低四位
为 2 时从 B 根收集。目录记录、已安装版本与卡状态仍为合成输入；
菜单调度及真实存储卡设备尚未执行。

整包检查保留原始上下文设置、八字节变换、摘要比较、CRC 结果判断及
成员指针生成。大块解码、SHA-1 运算、CRC 和内存移动使用执行环境
的运算原语，计时器及状态回调也由执行环境提供。另以原始指令执行
3 组解码边界、3 组八字节变换、10 组 SHA-1 比较和 5 种长度的 CRC，
核对这些原语。模拟字符表的数字标志已改为原始变换要求的 `0x20`；
此前前段扫描检查不使用这一数字变换分支，不能用它证明摘要变换正确。

校验完成后，原始调度器将结果写入运行时地址 `0xB1887D22` 的
16 位字段，并对事件对象 `0xB1887D24` 发出掩码 `0x20`，随后返回。
探针验证了成功及失败分支的状态和事件，并由模拟 RTOS 接口接收。
这属于更新任务内部同步；界面层 `ID_NOTIFY_EVENT_FWUP_RESULT`
的回报与后续存储写入仍未执行。

为验证原厂检查分支，在内存中使用明确的合成八字节引导材料，并仅对
测试变体重算外层摘要，没有生成可供相机安装的文件。执行结果如下：

| 测试输入与合成材料 | 原始整包检查返回 | CRC 阶段 |
| --- | --- | --- |
| 原厂包或已构造候选保持原摘要 | 3 | 未进入 |
| 原厂包主体配匹配的合成摘要 | 0 | 已进入并通过 |
| 候选主体配匹配的合成摘要 | 0 | 已进入并通过 |
| 摘要按一种材料生成，检查时使用另一种 | 3 | 未进入 |
| CRC 损坏，但重算匹配的合成摘要 | 3 | 已进入并失败 |

上述原厂包的失败是合成材料环境中的结果，不能推断其在相机上失败。
两个返回 0 的结果说明这组原始控制逻辑在输入一致时可以通过，也
不能证明合成材料是实际 B8。真实 B8 仍未知，原始分发包的摘要接受、
完整菜单更新、存储写入及重启验证均未完成。

## 三版本交叉的收集层接受矩阵

以 `--extra-package` 提供本地 C 1.10-01、C 1.61 原厂整包后，探针对
三份整包 × 三种合成已装 master 版本（01.70、01.61、01.10）执行
目录收集，共 9 组。全部组合都构建了整机包记录：返回 1、匹配数 1、
类别 4、编码包标志 1，包括 1.70 装机收到 1.61 或 1.10 包的降级
组合与同版本重装组合。逐字节比较进一步确认：同一整包在三种已装
版本下生成的记录完全相同，记录内容只含整包自身的成员名、版本、
长度与时间戳，不含任何已装版本差值。

也就是说，目录收集与枚举层不按版本方向把关；降级与重装在这里
与升级同样得到记录。已装版本参数在这一层仍被读取（缺少即失败），
但读取结果不改变整机包记录。若原厂流程在任何环节拒绝降级，该
判断只可能位于更深层——整包摘要检查、执行阶段或菜单服务——均
未验证。矩阵只覆盖收集层，不构成"相机接受任意版本"的结论。

## 纯菜单更新的边界与所需模型

当前控制台的更新安装由主机侧驱动：菜单应用为前台是门控条件，
摘要检查、更新存储编程与整机复位都由控制台完成。把更新改为
"纯菜单操作"——用户只用机身按键导航到固件版本项并确认，其余由
机器内的原厂代码完成——需要补齐以下三段，每段的现状与缺口如下：

| 环节 | 已具备 | 缺口 |
| --- | --- | --- |
| 菜单导航 | 按键经控制器扩展器到达引擎，菜单应用可前台，画面随按键变化；`tools/menu_fwupdate_probe.py` 每标签一次全新开机、双服务入口观察点扫完六个标签 × 24 项 × 双确认 | 两个服务入口均未命中：按键到达标签与高亮层，条目级菜单派发未发生（与菜单资源仅头桩一致）；剩余边界是条目派发数据而非按键可达性 |
| 存储卡 | 卡服务、文件系统层与 SD 驱动均在 master 内（见上文卡栈结构），目录收集会按 `firmware\` 与根目录找文件 | 卡查询经资源 8 返回 -821；槽位驱动表已运行时捕获（`tools/card_slot_probe.py`）、槽使能字节 `0xB1808B50+槽位` 已定位，但 SD 主控寄存器窗口仍未定位（使能之后的挂载路径未能在整机内执行），需要 SD 主控设备与含更新文件的卡内容 |
| 机身编程 | 原厂更新任务把完整已解码整包写入 `0x52000000` 暂存窗口（有界执行证据）；启动存储复位时校验并收获该窗口（见上文原厂编程窗口与复位收获） | 无——编程环节已由暂存窗口加复位收获建模，`tools/update_window_probe.py` 已验证 |

按实验室的一贯做法（控制器扩展器、图形设备、启动存储均为替代
真实硬件的实验设备），三段中剩两段是设备模型：SD 主控是其中
最深的一段，也是纯菜单路径与当前控制台路径的本质差别；菜单
导航是行为验证而非设备。版本矩阵说明三份原厂包都能通过收集层，
可作为将来卡设备与菜单导航验证的输入。

### 菜单扫页的实测边界

`menu_fwupdate_probe` 以**每标签页一次全新开机**的方式扫完六个
标签(避开"退出键关闭菜单后无法重开"的既有边界):开机到拍摄
前台、单击菜单键打开菜单后,右键移动到目标标签,向下 24 次逐项
走列表,再连按两次确认(覆盖需要确认页的条目)。两个服务入口
(资格检查 `0x747048` 与版本列表 `0x747092`)都设了观察点。

结果:六个标签全部完成扫描,两个服务入口均未被执行。结合
单机版的观察——菜单打开、标签切换、下移走项都真实改变画面,
确认键会重绘(条目页)、退出键关闭菜单——按键链路已到达
标签与高亮层,但**条目级的菜单派发没有发生**。这与本机菜单
资源仅加载头桩(resource header only)相符:菜单画面可绘制,
而条目选择到服务请求所需的数据未就位。纯菜单更新的剩余边界
因此从"按键可达性"收窄为"菜单条目派发",需要完整菜单资源
或对条目处理路径的进一步分析。历史记录见
[菜单更新导航验证](../../artifacts/menu_fwupdate_navigation/report.json)。

## 包完整性检查库

文件偏移 `0x38F11C` 与 `0x38FFA4` 有两处断言文件名
`FirmwareChkLib.c`,其前部为 Thumb 代码,代码池内出现
`0x5A827999`(`0x38F0xx` 一带)——SHA-1 轮常数。结合本地更新包
分析(整包在外层 CRC-16 之外还有 SHA-1 完整性检查)可知该库是
检查实现的一部分。摘要输入范围与附加材料的变换见下文;
摘要检查、容器检查与成员启动结构检查分别实现。

卡子系统本身在固件内有完整服务(`CCardService`、`CARDSRV` 任务与
`eSyscCommandId_CardMount*` 命令族,文件偏移 `0x2085CB0` 一带);
实验室尚未建模存储卡设备、文件系统与挂载命令,这是原厂更新路径
在本环境停下的第一个外部依赖。

## 整包摘要与 K8 的区别

分析固件确认 C 1.70 的整包路径在写入前执行 SHA-1 检查。下列
偏移均属于 master 成员,运行时地址为 `0x10020000 + 偏移`:

| 成员偏移 | 已确认的行为 |
| --- | --- |
| `0x37C638` | 读取整包、解码包体、设置摘要上下文并检查结果 |
| `0x37C694..0x37C69C` | 传入引导窗口地址 `0x10000088`、种子 `0x44B` 与机型串 `Z_7_2` |
| `0x38ED3E` | 从传入地址复制 8 字节到上下文 `+0x0C` |
| `0x38FE82` | 变换这 8 字节、追加到包体、计算 SHA-1 并比较头部 20 字节 |
| `0x37C634` | 转入字节变换函数 `0x39C310` |
| `0x39C376..0x39C382` | 每轮先累加当前增量,再增加增量并异或当前字节 |

定义 `B8` 为引导窗口的原始 8 字节,`K8` 为最终追加给摘要的
8 字节。两者的关系是 `K8 = B8 XOR S8`。因此常见表达式
`SHA1(解码后的固件主体 || K8)` 中的 K8 应指最终附加字节,
不应直接等同于地址 `0x10000088` 中的原始内容。这里的主体包括
32 字节空格标记、成员目录、全部成员、容器 CRC 与尾部填充;
不包括原文件头的 `0x20` 字节。

变换种子先取反并反转字节序,四字节异或折叠后索引第一张表;
机型串逐字符折叠后索引第二张表。两表运行时地址分别为
`0x12068276` 和 `0x12068376`。设取出的表值为 `a`、`m`,
字节序号 `i = 0..7`,则:

```text
S8[i] = (a + m * ((i + 1) * 0x260 + i * (i + 1) / 2)) mod 256
SHA1(解码主体 || (B8 XOR S8)) == 文件头[0:20]
```

`analyze/upgrade_signature.py` 的 `--boot-key` 调用方输入约定仍是
原始 `B8`,函数内部完成变换。旧实现把序列误写为
`a + m * (0x260 + i)`;它只在第一个字节一致。已修正并以独立的
寄存器累加测试及三组合成输入的固件原指令执行结果核对。只做
“构造后再检查”的往返测试不足以发现这种共同的算法偏差。
此前依赖旧公式的候选材料排除记录不能作为最终结论,本页撤回
“已排除所有分发成员窗口”的断言。本次没有提供 B8,因此没有
验证三个原厂包的 SHA-1 头部摘要,也没有确认其跨版本是否相同。

公开项目另外提出 E6 的 seed 可能由指令立即数构造。当前读取
`0x10000088` 的证据不能确定该窗口的初始化来源,不能据此排除
从更新代码恢复候选材料的可能。公开源码的支持范围与验证边界见
[公开资料对照](public_update_evidence.md)。

### 烧录是否需要 K8

- **正常安装未修改的原厂整包**:不需要另外提供 K8。整包已携带
  期望摘要,相机在内部读取自己的引导材料完成检查。
- **修改主体后仍按整包形式提交**:按已确认的 C 1.70 检查需要正确的
  最终 K8,或者能派生它的 B8 与对应变换参数,才能重算匹配摘要。
  解码成功、成员 CRC 正确或容器 CRC 正确都不能代替这一检查。
- **模拟器直接加载本地成员**:加载、身份检查和 CRC 校验本身不需要
  K8。控制台的单成员安装也是实验室本地流程。
- **向 Z7 II 相机提交独立成员**:固件内有 `0x37C47E` 的独立处理路径,
  其中没有上述整包 SHA-1 调用;但类别 2/4 先经过 `0x37BC0E` 的
  包目录检查。与 Z6 II C 1.70 对照后确认,`+0x68` 对应已解析的
  包格式标志,不是成员数。两机型原始目录例程均接受原厂整包并
  拒绝各自的原厂裸 master/slave。因此不能把非整包处理入口当成
  裸 EG 安装支持。该结果仍限于局部执行,见[双机型对照](z6ii_update_comparison.md)。

### 三版本容器对照

本地 C 1.10-01、C 1.61、C 1.70 样本的结构与身份记录见
[版本对照数据](update_versions.json)。本次只在内存中检查包体,
没有写出成员文件或改动原始固件。

| 更新包 | 原始字节数 | master 版本记录 | master 字节数 | slave 字节数 |
| --- | ---: | --- | ---: | ---: |
| `Z7_2_0110_01.bin` | 47,640,392 | `Ver.01.10.e0` | 37,437,242 | 8,782,594 |
| `Z7_2_0161.bin` | 48,381,064 | `Ver.01.61.00` | 38,126,522 | 8,833,986 |
| `Z7_2_0170.bin` | 48,494,024 | `Ver.01.70.02` | 38,239,098 | 8,834,370 |

三版的 32 字节空格标记、五成员目录与 `0xD0` 头长一致。目录内
都是 EX、TPJ、master、VR、slave,未列出单独的引导区成员;
这不能证明包体内不存在任何特定 8 字节值。15 个成员 CRC 和
3 个容器 CRC 均通过。容器 CRC 在最后成员后立即出现,其后
14 字节为零。TPJ 三版逐字节相同;EX 与 VR 在后两版相同。
C 1.10 的版本记录含小写字母 `e`,不能据此当作无效固件;
现有安装器仍只支持 C 1.70 的已验证启动结构,并未新增旧版启动支持。

`analyze/update_container.py` 校验已解码包体的目录边界、连续成员范围、
名称唯一性、保留字段、各成员 CRC 与容器尾部,仅返回元数据或内存中
选定的 master。控制台先完成整包摘要检查,再检查容器并选择唯一的
master,避免把目录当作可执行镜像。其他成员只校验,不安装。

## 刷入后的整机复位重启

菜单更新在原厂路径的末端由固件写入机身存储并复位重启。实验室以
`nikon-z72-boot-store` 设备补上这一段:每个引擎一个启动存储,每次
整机复位把存储的镜像集(固件镜像与 `path@address` 辅助文件)重新
复制进代码窗口,并把两个核心的程序计数器重置到镜像入口,模拟
"机身从存储启动"。控制台的安装流程因此变为:

1. 菜单前台门控与摘要检查如上;
2. 镜像与清单提交到持久更新存储;
3. 待装镜像写入运行中机器的启动存储(`qom-set` 的 `image` 属性即
   编程步骤);
4. QMP `system_reset` 整机复位,板卡重载存储镜像,两个引擎从镜像
   入口重新启动,控制台按首次启动的同一步骤(观察同步等待、供给
   同步边沿与帧同步)放行,机器从刷入镜像回到拍摄前台——全过程
   不重启主机进程。

`/update/remove` 回退走同一复位路径(编程回原厂镜像再复位)。
运行中镜像的版本记录(`0x10020020` 的 12 字节)由状态接口从机器
内读出,作为"机器确实从刷入镜像启动"的机内侧证据。

### 原厂编程窗口与复位收获

有界执行补上了编程环节的原厂侧证据:整包检查通过后,原厂更新
任务把**完整已解码整包流**(48,493,992 字节:32 字节摘要区、
空格标记、目录、全部成员与容器尾)写入 `0x52000000` 起的缓冲池
窗口——更新状态里的窗口指针即指向该地址。写入后调度器返回 0
并发成功事件;这一步在探针里由原厂指令完成,大块解码/复制原语
由执行环境提供(与整包检查同一组原语)。

据此把机身存储的实验室模型延伸为"编程窗口 + 复位收获":

- 缓冲池从 `0x54900000` 扩到 `0x54F00000`,使 48.5MB 的完整
  暂存流容纳在同一后备存储内(`0x30000000` 总线别名保持一致)。
- `nikon-z72-boot-store` 新增复位收获:每次整机复位先按主机侧
  同一套规则(空格标记、大端目录、连续成员、零保留字段、单一
  `eg1840_mas_` 成员、逐成员 CRC 余数为零、容器 CRC 为零)校验
  窗口内容;校验通过则把 master 成员复制进代码窗口代替文件镜像
  本次启动,不通过则照常从启动存储文件启动。窗口内容是普通
  RAM,复位不清除,因此"机身存储"语义 = 窗口里的最后一次成功
  编程;`harvest-update` 属性可关闭。
- `tools/update_window_probe.py` 以预载窗口代替原厂调度器的写入
  (原厂写入由上节有界执行单独覆盖),验证:预载 C 1.61 已解码
  整包后整机复位,代码窗口与运行版本记录变为 `Ver.01.61.00`,
  第二次复位仍从窗口启动;预载损坏一个字节的副本则被 CRC 拒绝,
  机器继续以 C 1.70 master 启动。历史记录见
  [更新窗口收获验证](../../artifacts/update_window_harvest/report.json)。

边界:只有 master 引擎收获(从引擎镜像与本窗口不在同一地址空间,
混版本机器不要求到达拍摄前台);EX/TPJ/VR/SLAVE 成员只随容器校验,
不安装——与控制台更新存储的取舍一致。复位收获在启动存储文件复制
之前执行;预载窗口用文件型 loader 时,loader 在复位时先恢复窗口
内容再被收获,顺序无害。

## 实验更新存储与菜单门控安装

存储卡、文件系统与机身闪存控制器尚未建模,包校验在主机侧完成,
控制台以实验更新存储代替原厂更新的落盘环节:

- `analyze/update_store.py` 定义候选接受与存储。候选 master 必须保持
  可执行启动结构:长度在主控存储窗口内、成员 CRC 余数为零、版本
  记录格式正确、复位分支与初始化表记录数不变、通信窗口零记录与
  引导前缀(首 MMIO 存储及其页表恒等映射)不变。原厂镜像与本地
  重建镜像(含尾部追加代码、重算 CRC)都通过;截断、CRC 破坏、
  版本记录畸形、启动布局改变都被拒绝。**原厂研究探针锁定的
  显示窗口摘要在此不适用**——更新本来就可能改写这些字节。
- 安装把镜像与清单(`master.bin` + `manifest.json`,记录 SHA-256、
  长度、版本、时间)原子写入持久目录;清单是提交点,无清单的
  镜像视为残留。每次启动重新校验存储镜像与清单一致,不一致则
  回退原厂镜像并显示存储错误,不静默掩盖。
- 安装入口 `tools/web_console.py` 的 `/update/install` 要求前台为
  菜单应用(应用索引 1):菜单未打开时拒绝,浏览器面板同样只在
  菜单打开时启用按钮。整包输入先完成摘要、容器及成员检查,再编程运行中
  机器的启动存储并整机复位,机器从存储镜像重新启动;
  `/update/remove` 以同一复位路径回退原厂。
- 待安装更新文件由控制台启动参数 `--update-image` 提供(整包或
  实验室本地 master 成员文件),整包另需 `--boot-key` 提供 8 字节
  原始引导区材料。它们都是本地研究输入;本仓库没有导出成员文件
  的命令行工具。更新存储目录由 `--update-store` 指定。

该流程在"菜单内的固件更新"这一语义上还原了操作路径(打开菜单、
执行更新、复位加载),整文件摘要校验已按上文恢复的算法实现;仍由
主机侧代替的环节是卡扫描与文件读取(无存储卡模型),检查通过后
的编程与复位由启动存储设备在机内完成。菜单项目前不要求到达原厂
"固件版本"条目,只要求菜单应用为前台。固件内 `FWUpdate` 服务的
运行时激活、版本页显示与通知回报仍属未验证边界。

## 验证

### 显示条件候选的菜单更新检查（2026-10-22）

对 C 1.70 生成直方图与水平仪显示条件候选：两处显示判断钩子、九个
可见性掩码及尾部追加的 68 字节代码发生修改。master 长度为
38,239,166 字节，整包长度为 48,494,092 字节。成员和容器 CRC 均
通过，但构造脚本保留了原始外层摘要；整包在缺少 B8 时不能完成
控制台摘要检查。本次没有确认原厂整包升级资格或相机安装。

实验 master 路径经 HTTP 检查了菜单外拒绝、菜单打开、菜单内安装、
整机复位及返回拍摄前台。复位后进一步核对机内两处显示钩子、掩码
源数据以及追加代码和 CRC，四个区域均与候选一致。候选版本记录
仍为 `Ver.01.70.02`，因此不能仅凭版本号确认已加载修改内容。
完整身份与检查结果见[显示候选菜单更新记录](../../artifacts/patched_menu_update_validation/report.json)。

该检查同时发现并修正了启动器的镜像覆盖问题：启动存储与带文件的
通用加载器同时拥有相同的代码窗口时，通用加载器注册的镜像会在复位
时恢复，覆盖启动存储刚写入的候选。`tools/dual_boot_probe.py` 现在
对已配置启动存储的引擎只设置加载器入口地址，由启动存储负责镜像
装载。未配置启动存储的探针仍使用原有文件加载路径。

本次使用已有模拟器二进制，没有编译项目。通过的是控制台菜单门控
的实验更新存储流程；未执行原厂存储卡扫描、完整更新服务和机身闪存
编程，也没有验证直方图与水平仪同屏的实际显示效果。
