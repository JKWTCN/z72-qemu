# 菜单固件更新路径与实验更新存储

分析固件定位了原厂菜单固件更新的静态结构:入口服务、卡上更新文件的
命名规则、包完整性检查库,以及服务在缺少存储卡时的检查行为。本页
同时记录实验室的阶段性实现:更新存储、菜单门控的安装流程与重启后
加载,并明确哪些环节是实验代替品。以下文件偏移均为 master EG
(`eg1840_mas_01700`)的成员内偏移,运行时地址为
`0x10020000 + 文件偏移`。

## 固件管理服务

master 固件内有一个按名称注册的服务表,文件偏移 `0x90BB50` 一带可见
`Key`、`ChangeLV`、`ChangeCaptureMode` 等名称,每项名称后跟随一个
`0xB181xxxx` 的运行时对象指针;`FWUpdate` 名称位于文件偏移
`0x90BC70`,对应对象指针 `0xB181A3DC`。记录间距不完全一致,表项
边界未逐项复原;`FWUpdate` 即菜单固件更新使用的服务名。

服务的实现与日志字符串位于文件偏移 `0x7470xx..0x747340`,字符串池
紧随代码。日志前缀 `CFirmwareManagementService_` 暴露了两个方法阶段:

| 方法 | 字符串(文件偏移) | 含义 |
| --- | --- | --- |
| `GetProprietyCheck` | `:Failed, %d`(`0x7471A8`) | 检查失败 |
| 同上 | `No update file.`(`0x7471E0`) | 卡上没有更新文件 |
| 同上 | `There is many update files.` | 更新文件不唯一 |
| 同上 | `There is no update files targeted.` | 没有适配本机的目标 |
| 同上 | `ExMCU update file exist.` | 外部微控制器更新在场 |
| 同上 | `BobyVR update file exist.` | 机身防抖更新在场 |
| 同上 | `Lens firmware update file exist.` | 镜头固件更新在场 |
| `Execute` | `:RequestFailed %xh.`(`0x7472B8`) | 执行请求失败 |
| 同上 | `FW update succeeded.`(`0x7472F0`) | 更新成功 |
| 同上 | `FW update failed.` / `:ExecuteFailed.` | 更新失败 |

服务同时发出通知 `ID_NOTIFY_EVENT_FWUP_RESULT:%d.`(`0x7472C0`
附近),即更新结果以通知事件回报给界面层。方法名与字符串只能证明
检查与执行两个阶段的划分和卡上目标种类的枚举,不能证明菜单项到
服务的调用时序;该时序尚未在运行中验证。

已进一步定位并局部执行资格检查分段 `0x747048`。它调用
`0x3D645A`，后者依次检查 `0x37AA82`、`0x37AAA6`；状态快照由
原始函数 `0x3D9A2A` 读取，长度为 `0x50`。成功时服务返回 1、
原因字段为 0；两类条件失败均返回 3、原因字段为 1。下表使用快照
内偏移，不预先给尚未追踪来源的枚举赋予电量百分比或硬件型号含义：

| 检查 | 已执行确认的条件 |
| --- | --- |
| 第一段 | `word[0] != 0`，且 `byte[4]` 既不是 0，也不是 5 |
| 第二段 | `byte[8]`、`byte[0x20]`、`byte[0x38]` 均不等于 1 |
| 等级选择 | `byte[7] == 1` 时取 `byte[0x23]`，等于 2 时取 `byte[0x3B]`，否则取 `byte[0x0B]` |
| 等级条件 | 选择结果必须小于 2 |

这里执行的是原始服务函数及其状态判断，快照内容为合成输入；锁操作
和诊断日志由执行环境代替。11 组输入确认上述分支，但未证明运行中
菜单会生成这些状态，也未验证更新资格的其余分段或安装执行阶段。

另一个服务段 `0x747092` 调用 `0x3D636A` 生成版本列表，只在条目数
等于 1 且类别为 2、4 或 8 时返回成功。通过前述整包扫描后，在合成
已安装版本参数下实际得到 5 个条目，类别顺序为 `4, 9, 2, 3, 17`；
该服务段返回 3、原因字段为 4。这里的条目数不能直接当作卡上的
更新包数量，也不能将这个局部返回值视为整机包被相机拒绝的证明。
菜单何时选择这一服务段、何时进入整机更新路径仍需进一步验证。

## 卡上更新文件命名

文件偏移 `0x19603D0` 起的记录包含类别、模板指针及可选条件函数。
普通扫描入口 `0x37C360` 遍历 11 项，依次包括 `EX1840??.BIN`、
`EG1840??.BIN`、`Z7_2_???.BIN` 等。类别 4 的模板实际只有三个 `?`，
位于 `0x208680C`；此前记为四个 `?` 的说法不正确。

目录搜索 `0x37C236` 对目录记录起始处的短名逐字节匹配，`?` 匹配一个
非零字符，普通字符经大写转换后比较。找到记录后，`0x37C218` 从
记录 `+0x0E` 的宽字符长名生成打开路径。因此，模拟记录中的短名
`Z7_2_0~1.BIN` 能匹配模板，随后按长名打开 `Z7_2_0170.BIN`。
这个短名是明确构造的目录输入；实际卡上的别名由文件系统决定，不能
仅凭模板判断完整长文件名不受支持。

原始初始化数据中 `0xB1887D00`、`0xB1887D04` 的两个根指针分别
指向 `A:\`、`B:\`。已执行确认：选择字段低四位为 0 时使用 A，
为 2 时使用 B；位 `0x10` 允许在目录打开失败后尝试另一个根。
目录成功打开但未找到匹配文件时，这个函数直接返回，不执行同样回退。
探针从原始初始化数据恢复这两个指针，选择字段及目录内容为合成输入。
上述目录搜索入口没有使用位于 `0x2086840` 的 `firmware\` 字符串。
原始候选枚举循环则通过 `0x37D372` 使用初始化数据中的相对目录表：
目录索引 0 对应 `firmware\`，索引 1 对应空前缀。探针已执行两种
路径构造；目录记录本身由执行环境提供，存储卡上的真实目录设备
仍未建模。

## 原始目录与成员检查探针

`tools/native_update_probe.py` 接收本地 C 1.70 master、原厂整包及可选
候选整包，执行目录解析 `0x38D340`，并从分类函数 `0x37BC0E` 执行
到 `0x37C100` 的版本列表构造入口。包解码、目录匹配、大小判断及
成员信息读取使用原始指令；文件读取、内存原语、缓存操作及 ASCII
字符标志由执行环境提供。运行中镜像描述符采用给定 stock master，
平台标签为零，容量为合成的 `0x04000000`，其余运行时 RAM 初始为零。
这不是从机身捕获的状态。探针另外提供明确的组件版本查询响应与参数
存储接口，继续执行原始版本格式化及分类返回路径；原厂包与候选均
返回 1，版本条目数为 5。组件响应为全零的合成描述符，未验证真实
组件通信或版本兼容性。

已执行结果见[原始更新检查记录](../../artifacts/native_update_checks/report.json)：

| 输入或环境变化 | 目录解析 | 成员检查阶段 |
| --- | --- | --- |
| 原厂整包、显示条件候选整包 | 返回 1 | 成员掩码 `0x1F`，到达列表构造入口 |
| 裸 master、截断到 64 字节的整包 | 返回 0 | 返回 12 |
| 容量恰等于原厂 master 长度 | 返回 1 | 返回 11；master 要求长度严格小于容量 |
| EX 成员长度从 `0x80002` 改为 `0x80003` | 返回 1 | 返回 11 |
| 仅改变外层摘要 | 返回 1 | 仍到达列表构造入口 |
| 仅改变最后一个成员 CRC | 返回 1 | 仍到达列表构造入口 |

最后两项说明目录和成员信息检查并不验证整包摘要或成员 CRC。
候选通过这一阶段，不能证明通过后续完整性检查或允许菜单升级。
探针报告同时记录资格检查的输入分支和执行入口，不包含固件内容。

报告另有 10 组目录输入、4 组扫描输入、8 组枚举输入和 12 组收集
输入。扫描从 `0x37C360` 出发，
实际经过模板遍历、目录搜索、长名转换、文件打开、目录解析、成员检查
与版本列表构造，再返回调用者。原厂包与候选返回 0，类别为 4；将
裸 master 作为同名整包提供，或让文件打开失败，均返回 3。文件系统
和组件通信接口由执行环境提供，未进入整包摘要或写入阶段。

### 选择记录到整包校验的局部执行

探针从目录收集入口 `0x37D984` 出发执行原始候选枚举循环
`0x37D71C`，由它完成文件匹配、路径构造、类别检查 `0x37D5BC`、
版本比较和记录构造 `0x37D4D4`。整机包被归入逻辑槽位 13，记录内
文件类别为 4；这两个值由原始循环产生。
槽位、文件类别与版本条目类别是不同字段，不能因数值相同就认定含义
相同。执行环境随后调用记录选择 `0x37DAA4` 和调度函数 `0x3D6938`；
编码包标志经记录 `+0x1C4` 传到运行时状态 `+0x68`，值为 1，
因此进入整包检查 `0x37C638`。

9 组枚举输入确认：原厂包及候选可以生成记录，裸 master、截断包、
其他机型文件名和空目录不能生成对应整机包记录；A 卡的根目录及
`firmware\` 子目录、B 卡的 `firmware\` 子目录均能按配置构造路径。
相同主体使用两个匹配文件名时，匹配数为 2，槽位 13 保留后枚举的
同版本条目。这个结果限于该循环，不能推断完整更新流程允许多个包。

### 原始目录收集入口的执行与接受条件

目录收集入口 `0x37D984` 已由原始指令执行。它先检查调用模式：仅
0、2、3、4、6、7、8、9、`0x0C`、`0x0D`、`0x0E`、`0x10`、`0x12`
被接受，其他值不改任何状态直接返回 0。接受后 `0x37D216` 清空
记录数组与版本摘要，前置段 `0x37D940` 分配记录向量（`0x6A40`
字节）和目录索引向量（`0xC8` 字节），分配失败即释放并返回 0。
主循环对两个目录索引各执行一次：`0x37D278` 按选择字段低四位选根
（0/1 取 A，2 取 B，3 在卡状态函数报告无卡时回落 A）、拼接相对
目录并经 `0x4B3EF0` 检查存在性，目录不存在则跳过该索引。存在的
目录经 `0x4B3E92` 枚举，回调 `0x37D6B5` 以原始代码把每条 `0x220`
字节记录复制进记录向量并登记目录索引，收集上限 50 条。枚举返回
`0x043A0080`/`0x043A0084` 之外的状态时整个收集中止返回 0，即使
前一个目录已成功。两个目录都成功后才进入枚举循环 `0x37D71C`，
最后 `0x37D922` 释放两块缓冲。

12 组收集输入确认上述接受条件：`firmware\` 与根目录单独或同时在场
均构造出正确路径，目录索引随收集来源记为 0 或 1，枚举循环用它重建
打开路径；两个目录都不存在时返回 0；任一目录枚举出错即中止，后
目录出错时已收集的记录也不进入枚举循环；调用模式 1、5 被直接
拒绝；模式 2 通过收集门、汇总头由 19 变为 1，但不产生整机包记录
——模式字节写入运行时状态 `+2` 后由枚举循环读取；选择字段低四位
为 2 时从 B 根收集。目录记录、已安装版本与卡状态仍为合成输入；
菜单调度及真实存储卡设备尚未执行。

整包检查保留原始上下文设置、八字节变换、摘要比较、CRC 结果判断及
成员指针生成。大块解码、SHA-1 运算、CRC 和内存移动使用执行环境
的运算原语，计时器及状态回调也由执行环境提供。另以原始指令执行
3 组解码边界、3 组八字节变换、10 组 SHA-1 比较和 5 种长度的 CRC，
核对这些原语。模拟字符表的数字标志已改为原始变换要求的 `0x20`；
此前前段扫描检查不使用这一数字变换分支，不能用它证明摘要变换正确。

校验完成后，原始调度器将结果写入运行时地址 `0xB1887D22` 的
16 位字段，并对事件对象 `0xB1887D24` 发出掩码 `0x20`，随后返回。
探针验证了成功及失败分支的状态和事件，并由模拟 RTOS 接口接收。
这属于更新任务内部同步；界面层 `ID_NOTIFY_EVENT_FWUP_RESULT`
的回报与后续存储写入仍未执行。

为验证原厂检查分支，在内存中使用明确的合成八字节引导材料，并仅对
测试变体重算外层摘要，没有生成可供相机安装的文件。执行结果如下：

| 测试输入与合成材料 | 原始整包检查返回 | CRC 阶段 |
| --- | --- | --- |
| 原厂包或已构造候选保持原摘要 | 3 | 未进入 |
| 原厂包主体配匹配的合成摘要 | 0 | 已进入并通过 |
| 候选主体配匹配的合成摘要 | 0 | 已进入并通过 |
| 摘要按一种材料生成，检查时使用另一种 | 3 | 未进入 |
| CRC 损坏，但重算匹配的合成摘要 | 3 | 已进入并失败 |

上述原厂包的失败是合成材料环境中的结果，不能推断其在相机上失败。
两个返回 0 的结果说明这组原始控制逻辑在输入一致时可以通过，也
不能证明合成材料是实际 B8。真实 B8 仍未知，原始分发包的摘要接受、
完整菜单更新、存储写入及重启验证均未完成。

复现命令如下，输出路径应尚不存在；候选整包参数可省略：

```text
python tools/native_update_probe.py --master <stock-master> --stock-package <stock-package> --candidate <candidate-package> --report <new-report.json>
```

## 三版本交叉的收集层接受矩阵

以 `--extra-package` 提供本地 C 1.10-01、C 1.61 原厂整包后，探针对
三份整包 × 三种合成已装 master 版本（01.70、01.61、01.10）执行
目录收集，共 9 组。全部组合都构建了整机包记录：返回 1、匹配数 1、
类别 4、编码包标志 1，包括 1.70 装机收到 1.61 或 1.10 包的降级
组合与同版本重装组合。逐字节比较进一步确认：同一整包在三种已装
版本下生成的记录完全相同，记录内容只含整包自身的成员名、版本、
长度与时间戳，不含任何已装版本差值。

也就是说，目录收集与枚举层不按版本方向把关；降级与重装在这里
与升级同样得到记录。已装版本参数在这一层仍被读取（缺少即失败），
但读取结果不改变整机包记录。若原厂流程在任何环节拒绝降级，该
判断只可能位于更深层——整包摘要检查、执行阶段或菜单服务——均
未验证。矩阵只覆盖收集层，不构成"相机接受任意版本"的结论。

## 纯菜单更新的边界与所需模型

当前控制台的更新安装由主机侧驱动：菜单应用为前台是门控条件，
摘要检查、更新存储编程与整机复位都由控制台完成。把更新改为
"纯菜单操作"——用户只用机身按键导航到固件版本项并确认，其余由
机器内的原厂代码完成——需要补齐以下三段，每段的现状与缺口如下：

| 环节 | 已具备 | 缺口 |
| --- | --- | --- |
| 菜单导航 | 按键经控制器扩展器到达引擎，菜单应用可前台，画面随按键变化 | 多步导航到设置菜单固件版本项、菜单项到 `FWUpdate` 服务的请求时序未验证 |
| 存储卡 | 卡服务与查询代码在机内执行，目录收集会按 `firmware\` 与根目录找文件 | 卡查询经资源 8 返回 -821；需要可被原厂卡栈挂载的卡设备（含更新文件的卡内容），文件系统解析由原厂代码完成 |
| 机身编程 | 复位后从启动存储加载镜像已实现 | 原厂执行阶段的闪存控制器写入未建模，当前由启动存储设备代替 |

按实验室的一贯做法（控制器扩展器、图形设备、启动存储均为替代
真实硬件的实验设备），上述缺口分别对应三个设备模型；卡设备是
其中最深的一段，也是纯菜单路径与当前控制台路径的本质差别。版本
矩阵说明三份原厂包都能通过收集层，可作为将来卡设备与菜单导航
验证的输入。

## 包完整性检查库

文件偏移 `0x38F11C` 与 `0x38FFA4` 有两处断言文件名
`FirmwareChkLib.c`,其前部为 Thumb 代码,代码池内出现
`0x5A827999`(`0x38F0xx` 一带)——SHA-1 轮常数。结合本地更新包
分析(整包在外层 CRC-16 之外还有 SHA-1 完整性检查)可知该库是
检查实现的一部分。摘要输入范围与附加材料的变换见下文;
摘要检查、容器检查与成员启动结构检查分别实现。

卡子系统本身在固件内有完整服务(`CCardService`、`CARDSRV` 任务与
`eSyscCommandId_CardMount*` 命令族,文件偏移 `0x2085CB0` 一带);
实验室尚未建模存储卡设备、文件系统与挂载命令,这是原厂更新路径
在本环境停下的第一个外部依赖。

## 版本记录

两份 EG 成员文件偏移 `0x20` 均为十二字节版本记录(如
`Ver.01.70.02`),详见[容器与成员记录](container.md)。菜单固件
版本页显示的字符串来源未逐段跟踪;实验更新存储直接读取该记录
作为已安装镜像的版本描述。

## 整包摘要与 K8 的区别

分析固件确认 C 1.70 的整包路径在写入前执行 SHA-1 检查。下列
偏移均属于 master 成员,运行时地址为 `0x10020000 + 偏移`:

| 成员偏移 | 已确认的行为 |
| --- | --- |
| `0x37C638` | 读取整包、解码包体、设置摘要上下文并检查结果 |
| `0x37C694..0x37C69C` | 传入引导窗口地址 `0x10000088`、种子 `0x44B` 与机型串 `Z_7_2` |
| `0x38ED3E` | 从传入地址复制 8 字节到上下文 `+0x0C` |
| `0x38FE82` | 变换这 8 字节、追加到包体、计算 SHA-1 并比较头部 20 字节 |
| `0x37C634` | 转入字节变换函数 `0x39C310` |
| `0x39C376..0x39C382` | 每轮先累加当前增量,再增加增量并异或当前字节 |

定义 `B8` 为引导窗口的原始 8 字节,`K8` 为最终追加给摘要的
8 字节。两者的关系是 `K8 = B8 XOR S8`。因此常见表达式
`SHA1(解码后的固件主体 || K8)` 中的 K8 应指最终附加字节,
不应直接等同于地址 `0x10000088` 中的原始内容。这里的主体包括
32 字节空格标记、成员目录、全部成员、容器 CRC 与尾部填充;
不包括原文件头的 `0x20` 字节。

变换种子先取反并反转字节序,四字节异或折叠后索引第一张表;
机型串逐字符折叠后索引第二张表。两表运行时地址分别为
`0x12068276` 和 `0x12068376`。设取出的表值为 `a`、`m`,
字节序号 `i = 0..7`,则:

```text
S8[i] = (a + m * ((i + 1) * 0x260 + i * (i + 1) / 2)) mod 256
SHA1(解码主体 || (B8 XOR S8)) == 文件头[0:20]
```

`analyze/upgrade_signature.py` 的 `--boot-key` 调用方输入约定仍是
原始 `B8`,函数内部完成变换。旧实现把序列误写为
`a + m * (0x260 + i)`;它只在第一个字节一致。已修正并以独立的
寄存器累加测试及三组合成输入的固件原指令执行结果核对。只做
“构造后再检查”的往返测试不足以发现这种共同的算法偏差。
此前依赖旧公式的候选材料排除记录不能作为最终结论,本页撤回
“已排除所有分发成员窗口”的断言。本次没有提供 B8,因此没有
验证三个原厂包的 SHA-1 头部摘要,也没有确认其跨版本是否相同。

公开项目另外提出 E6 的 seed 可能由指令立即数构造。当前读取
`0x10000088` 的证据不能确定该窗口的初始化来源,不能据此排除
从更新代码恢复候选材料的可能。公开源码的支持范围与验证边界见
[公开资料对照](public_update_evidence.md)。

### 烧录是否需要 K8

- **正常安装未修改的原厂整包**:不需要另外提供 K8。整包已携带
  期望摘要,相机在内部读取自己的引导材料完成检查。
- **修改主体后仍按整包形式提交**:按已确认的 C 1.70 检查需要正确的
  最终 K8,或者能派生它的 B8 与对应变换参数,才能重算匹配摘要。
  解码成功、成员 CRC 正确或容器 CRC 正确都不能代替这一检查。
- **模拟器直接加载本地成员**:加载、身份检查和 CRC 校验本身不需要
  K8。控制台的单成员安装也是实验室本地流程。
- **向 Z7 II 相机提交独立成员**:固件内有 `0x37C47E` 的独立处理路径,
  其中没有上述整包 SHA-1 调用;但类别 2/4 先经过 `0x37BC0E` 的
  包目录检查。与 Z6 II C 1.70 对照后确认,`+0x68` 对应已解析的
  包格式标志,不是成员数。两机型原始目录例程均接受原厂整包并
  拒绝各自的原厂裸 master/slave。因此不能把非整包处理入口当成
  裸 EG 安装支持。该结果仍限于局部执行,见[双机型对照](z6ii_update_comparison.md)。

### 三版本容器对照

本地 C 1.10-01、C 1.61、C 1.70 样本的结构与身份记录见
[版本对照数据](update_versions.json)。本次只在内存中检查包体,
没有写出成员文件或改动原始固件。

| 更新包 | 原始字节数 | master 版本记录 | master 字节数 | slave 字节数 |
| --- | ---: | --- | ---: | ---: |
| `Z7_2_0110_01.bin` | 47,640,392 | `Ver.01.10.e0` | 37,437,242 | 8,782,594 |
| `Z7_2_0161.bin` | 48,381,064 | `Ver.01.61.00` | 38,126,522 | 8,833,986 |
| `Z7_2_0170.bin` | 48,494,024 | `Ver.01.70.02` | 38,239,098 | 8,834,370 |

三版的 32 字节空格标记、五成员目录与 `0xD0` 头长一致。目录内
都是 EX、TPJ、master、VR、slave,未列出单独的引导区成员;
这不能证明包体内不存在任何特定 8 字节值。15 个成员 CRC 和
3 个容器 CRC 均通过。容器 CRC 在最后成员后立即出现,其后
14 字节为零。TPJ 三版逐字节相同;EX 与 VR 在后两版相同。
C 1.10 的版本记录含小写字母 `e`,不能据此当作无效固件;
现有安装器仍只支持 C 1.70 的已验证启动结构,并未新增旧版启动支持。

`analyze/update_container.py` 校验已解码包体的目录边界、连续成员范围、
名称唯一性、保留字段、各成员 CRC 与容器尾部,仅返回元数据或内存中
选定的 master。控制台先完成整包摘要检查,再检查容器并选择唯一的
master,避免把目录当作可执行镜像。其他成员只校验,不安装。

## 刷入后的整机复位重启

菜单更新在原厂路径的末端由固件写入机身存储并复位重启。实验室以
`nikon-z72-boot-store` 设备补上这一段:每个引擎一个启动存储,每次
整机复位把存储的镜像集(固件镜像与 `path@address` 辅助文件)重新
复制进代码窗口,并把两个核心的程序计数器重置到镜像入口,模拟
"机身从存储启动"。控制台的安装流程因此变为:

1. 菜单前台门控与摘要检查如上;
2. 镜像与清单提交到持久更新存储;
3. 待装镜像写入运行中机器的启动存储(`qom-set` 的 `image` 属性即
   编程步骤);
4. QMP `system_reset` 整机复位,板卡重载存储镜像,两个引擎从镜像
   入口重新启动,控制台按首次启动的同一步骤(观察同步等待、供给
   同步边沿与帧同步)放行,机器从刷入镜像回到拍摄前台——全过程
   不重启主机进程。

`/update/remove` 回退走同一复位路径(编程回原厂镜像再复位)。
运行中镜像的版本记录(`0x10020020` 的 12 字节)由状态接口从机器
内读出,作为"机器确实从刷入镜像启动"的机内侧证据。

## 实验更新存储与菜单门控安装

存储卡、文件系统与机身闪存控制器尚未建模,包校验在主机侧完成,
控制台以实验更新存储代替原厂更新的落盘环节:

- `analyze/update_store.py` 定义候选接受与存储。候选 master 必须保持
  可执行启动结构:长度在主控存储窗口内、成员 CRC 余数为零、版本
  记录格式正确、复位分支与初始化表记录数不变、通信窗口零记录与
  引导前缀(首 MMIO 存储及其页表恒等映射)不变。原厂镜像与本地
  重建镜像(含尾部追加代码、重算 CRC)都通过;截断、CRC 破坏、
  版本记录畸形、启动布局改变都被拒绝。**原厂研究探针锁定的
  显示窗口摘要在此不适用**——更新本来就可能改写这些字节。
- 安装把镜像与清单(`master.bin` + `manifest.json`,记录 SHA-256、
  长度、版本、时间)原子写入持久目录;清单是提交点,无清单的
  镜像视为残留。每次启动重新校验存储镜像与清单一致,不一致则
  回退原厂镜像并显示存储错误,不静默掩盖。
- 安装入口 `tools/web_console.py` 的 `/update/install` 要求前台为
  菜单应用(应用索引 1):菜单未打开时拒绝,浏览器面板同样只在
  菜单打开时启用按钮。整包输入先完成摘要、容器及成员检查,再编程运行中
  机器的启动存储并整机复位,机器从存储镜像重新启动;
  `/update/remove` 以同一复位路径回退原厂。
- 待安装更新文件由控制台启动参数 `--update-image` 提供(整包或
  实验室本地 master 成员文件),整包另需 `--boot-key` 提供 8 字节
  原始引导区材料。它们都是本地研究输入;本仓库没有导出成员文件
  的命令行工具。更新存储目录由 `--update-store` 指定。

该流程在"菜单内的固件更新"这一语义上还原了操作路径(打开菜单、
执行更新、复位加载),整文件摘要校验已按上文恢复的算法实现;仍由
主机侧代替的环节是卡扫描与文件读取(无存储卡模型),检查通过后
的编程与复位由启动存储设备在机内完成。菜单项目前不要求到达原厂
"固件版本"条目,只要求菜单应用为前台。固件内 `FWUpdate` 服务的
运行时激活、版本页显示与通知回报仍属未验证边界。

## 验证

### 显示条件候选的菜单更新检查（2026-10-22）

对 C 1.70 生成直方图与水平仪显示条件候选：两处显示判断钩子、九个
可见性掩码及尾部追加的 68 字节代码发生修改。master 长度为
38,239,166 字节，整包长度为 48,494,092 字节。成员和容器 CRC 均
通过，但构造脚本保留了原始外层摘要；整包在缺少 B8 时不能完成
控制台摘要检查。本次没有确认原厂整包升级资格或相机安装。

实验 master 路径经 HTTP 检查了菜单外拒绝、菜单打开、菜单内安装、
整机复位及返回拍摄前台。复位后进一步核对机内两处显示钩子、掩码
源数据以及追加代码和 CRC，四个区域均与候选一致。候选版本记录
仍为 `Ver.01.70.02`，因此不能仅凭版本号确认已加载修改内容。
完整身份与检查结果见[显示候选菜单更新记录](../../artifacts/patched_menu_update_validation/report.json)。

该检查同时发现并修正了启动器的镜像覆盖问题：启动存储与带文件的
通用加载器同时拥有相同的代码窗口时，通用加载器注册的镜像会在复位
时恢复，覆盖启动存储刚写入的候选。`tools/dual_boot_probe.py` 现在
对已配置启动存储的引擎只设置加载器入口地址，由启动存储负责镜像
装载。未配置启动存储的探针仍使用原有文件加载路径。

本次使用已有模拟器二进制，没有编译项目。通过的是控制台菜单门控
的实验更新存储流程；未执行原厂存储卡扫描、完整更新服务和机身闪存
编程，也没有验证直方图与水平仪同屏的实际显示效果。
