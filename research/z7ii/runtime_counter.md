# 计数模块、内核初始化与多核就绪等待

本阶段分析 C 1.70 的计时回调，实现 `0x04266000` 的有限计数模型，继续执行原厂
内核模块初始化和启动任务 API。以下代码偏移为 EG 文件偏移，运行地址加 `0x10020000`。

## 原厂回调

| 偏移 | 观察到的作用 |
| --- | --- |
| `0x12C` | 取计数器地址，关闭控制位 0、1，清零两个计数字，写入频率 |
| `0xD4` | 写 CPU 的 CNTFRQ，初始化物理定时器、计数访问控制和虚拟偏移 |
| `0xF8` | 设置物理定时器 TVAL，并按参数选择使能状态 |
| `0x158` | 设置 MMIO 控制位 0、1 |
| `0x234` | 依次调用上述计数清零、CPU 初始化、TVAL 配置及 MMIO 使能 |
| `0x120` | 读取 CPU CNTFRQ |

两个角色的频率字面量均为 `48000000`，与计数设备 `+0x10` 写入值一致。
原厂 `0x234` 设置 TVAL 为 `0xBB80`（48000），但这里不据此证明完整 tick 频率。
计时调用发生在后续内核模块初始化期间，早于启动任务创建。

## 有限计数设备

`nikon-z72-counter` 位于早期配置容器的空隙中，提供以下 32 位字：

| 寄存器偏移 | 实验行为 |
| --- | --- |
| `0` | 控制字；位 0 控制 MMIO 计数推进，位 1 保存；其他位写入报错 |
| `8`、`0xC` | 64 位计数低／高字；停止时可分别写入，运行时写入报错 |
| `0x10` | 频率字段；停止时接受原厂 48 MHz，其他频率写入报错 |

复位清零控制、计数和频率字段。运行计数基于 CPU 通用定时器使用的 QEMU 虚拟时间
周期，停止时保存计数，重新使能后继续推进；不是静态寄存器存储。
洞、字节及非对齐访问保持数据异常。支持接口关闭属性
`-global nikon-z72-counter.enabled=off`，用于在原厂首次读处重现异常。
计数设备状态格式为版本 1，早期配置设备格式保持版本 6；完整主板迁移仍未验证。

CPU 声明频率设为 48 MHz。QEMU 10.2.4 使用整数纳秒周期，因此周期为 20 ns，
实际虚拟时间计数推进对应 50 MHz。该量化误差与 CPU 定时器一致；模型不能证明实际
硬件频率或真实 tick 时间。MMIO 计数器与 CPU 使用相同时间周期，但 MMIO 清零、
停止不会改变 CPU 计数器的起点或门控；其完整硬件连接仍待确认。

## 内核和启动任务

两个角色完成后续 18 次内核模块调用，返回值均通过原厂的非负检查，调用者栈保持
不变。原厂启动任务描述符给出属性 `0x41`、优先级 1、栈大小 `0x2000`，任务入口为
master `0xE3BC8` / slave `0x15678`。创建返回任务 ID `0x01000001`，启动返回零；
这些是原厂 API 的实际执行结果，没有写入返回值、改指令或重新指定 PC。
本阶段的单核检查不执行启动任务；后续[第二核阶段](smp_startup.md)已验证实际任务入口。

随后完成核内初始化，并到达以下原厂等待：

| 角色 | 等待循环 | 就绪计数字 |
| --- | --- | --- |
| master | `0xFE660` | `0xB18AED90` |
| slave | `0x30034` | `0xC1017D40` |

原厂参数读取键为 `TKerPrNum`；当前配置要求另外 1 个核就绪，内存中的到达计数仍为
零。连续四次加载、比较、条件跳转均回到原厂循环。这个软件配置不能证明物理芯片
实际核数。本阶段使用默认单核配置，因此无法满足等待；没有伪造就绪计数。
后续第二核阶段增加可选双核，执行原厂启动和就绪发布，并验证定向核间中断和启动任务入口。
