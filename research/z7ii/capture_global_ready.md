# 驱动双位就绪与全局通知

解除拍照门控的 `0x0410000d` 有一条独立于操作 13 请求槽的生产路径。
此前观察到 `0xb23f6a7c` 与 `0xb23f7018` 为零，不能据此认定全局
就绪通知必须等待操作 13 的异步请求。以下控制流与执行契约修正该推断。

| 入口或状态 | 原厂行为 |
| --- | --- |
| `0x1031dd62` | 将驱动 `0xb1868af0 + 0x78` 按位或 1 |
| `0x10326700` | 将同一状态字按位或 2，并调用两个本地控制入口 |
| 两个入口更新后的状态恰为 3 | 经驱动全局回调 `+0x48` 发送 `0x04160003`，负载为零 |
| 总路由 `0x103ed470` 的 `0x103ed7ac` 分支 | 经 `0xb18695a0 + 0x0c` 的全局回调发送 `0x0410000d` |
| 同一总路由分支 | 将后续入口 `0x103ecf8d` 入队 |

这两个驱动入口的顺序不影响最终通知；状态已经是 3 时再次进入也会
发送通知，不能把它解释为仅在状态发生变化时发送。缺少相应全局回调
时不会发送通知。

输入族全局通知包装 `0x1022594e` 形成 `0x04160000 | index`；
捕获族全局包装 `0x102282ba` 形成 `0x04100000 | index`。
后者与此前调查的按操作回调包装 `0x102282b4` 是不同入口。
应用将 `0x0410000d` 映射为事件 1，再由既有事件消费路径清除
`0xb1821e84` 的拍照门控，见[机身快门](body_shutter.md)。

控制流还定位到第一个就绪位的上游：通知入口 `0x10321a4c` 收到
`0x04190040`，经 `0x10322666` 将 `0x1031dd63` 入队。
请求包装 `0x1038e7b8` 将操作与通知码、调用者回调一起放入
`0xb21e26c0` 队列，唤醒任务 `0xb21e2654` 的事件 `0x10`。
后台工作函数 `0x1038e2ec` 在对应操作执行后调用所保存的回调。
初始化内部有 `0x43140000/0x43140001` 请求及等待；这些地址与码族
尚不足以判定设备身份或认定它是整机当前阻塞点。

第二个位来自另一条通知：`0x10327976` 收到 `0x041b0040`，经
`0x103281b2` 将 `0x10326701` 入队。执行契约使用零负载确认了
两条上游通知各自的入队目标。[分阶段快门记录](../../artifacts/processing_staged_shutter/report.json)
的末次工作队列确实含有 `0x10326701`，同时队列计数达到容量 60。
这证明该窗口中已有第二位的待执行回调，不能继续将其上游通知
缺失作为唯一解释；需检查驱动任务执行队列的实际进展。

`tools/capture_global_ready_probe.py` 使用本地 C 1.70 原厂映像执行
上述两个就绪入口和总路由。合成状态覆盖各初值 0、1、2、3，以及
总路由全局订阅存在/缺失两种情况；操作 13 请求和回调始终保持零。
[执行记录](../../artifacts/capture_global_ready_contract/report.json)
验证了就绪位合并、通知码及后续入队目标。宿主边界只记录通知和队列，
隔离就绪后的本地记账与两个控制入口；不包含固件字节。

该合同不代表整机自然产生了这两个就绪位，也不代表已完成照片。
整机探针新增两个就绪入口、全局发送点和后台初始化等待点，并只读
采样驱动状态字、两级全局订阅者及后台状态。下一步应据实际命中和
状态值确定缺失的生产者或未执行的回调，不能直接写入就绪字、门控或应用事件。

[两级订阅与驱动状态实测](../../artifacts/processing_global_ready/report.json)
在模式 1 输入实验的完整前置条件满足后开始观察，推进 1.540212 个
计数器秒。开始和结束的驱动状态字均为 `1`，驱动全局回调为
`0x103ed471`，总路由全局回调为 `0x10204e3d`；两级订阅者都存在，
第一个就绪位已在窗口之前产生。后台状态两字节均为零，窗口未进入
后台模式请求或初始化等待，不能把这些等待当作当前已证实的阻塞。

窗口内记录到八次驱动工作函数返回；末次队列为 36 项，全部是
`0x10325ff7`，此时尚未看到较长窗口中的第二位回调。处理完成
3 帧，门控仍为 1。该短窗口不能证明驱动任务一直不返回；需要结合
更长窗口的入队、执行与保存栈位置，区分后续积压和永久等待。

进一步的原厂输入回调契约补齐了同步事件 `0xb188814c` 的以下映射：

| 输入状态银行、位 | 回调 | 同步事件位 |
| --- | --- | --- |
| 0、3 | `0x102391b2` | `0x00100000` |
| 0、4 | `0x102391b2` | `0x00200000` |
| 3、5 | `0x10239480` | `0x00800000` |
| 3、0 | `0x10239436` | `0x01000000` |
| 4、7 | `0x1023931c` | `0x04000000` |

五项合成 `0x05b00000`。`tools/input_frame_contract.py` 现有九项
[执行记录](../../artifacts/input_frame_contract/report.json)覆盖这些事件，
仅在宿主事件 API 边界记录原厂调用。该映射不代表已经实现相应输出
传输，也不能单凭等待参数就断定实际等待对象是此同步事件。

## 输入配置等待的任务栈证据

[修正布局后的任务观察](../../artifacts/processing_driver_tasks/report.json)
推进 2.868865 个计数器秒，处理 41 帧。驱动任务为 `0x0100001b`，
任务块 `0xb2c345f8`，末次保存上下文 SP 为 `0xb51dfcdc`；
等待时 SP 为 `0xb51dfd28`。候选代码地址来自该保存栈起的 1024 字节
窗口，属于地址线索，不是自动展开的完整调用栈。

候选续行地址 `0x103611a9 → 0x102389c7 → 0x1023b01b →
0x102321d3 → 0x10233ccb → 0x1026bcf3 → 0x10325719` 与原厂
调用指令交叉对应。输入配置包装 `0x1023b00e` 先调用
`0x10238974` 等待，再调用 `0x1023aed8` 更新配置。
等待函数把通道掩码转换为前述同步事件掩码，在 `0xb188814c`
以全位匹配等待，超时参数为 200 毫秒；完成后按调用参数清除事件位。
因此这里是输入配置更新前的同步等待，不能解释为处理端口的停止等待。

观察开始时驱动和后台任务都在通用分发器等待；结束时后台任务仍在
相同等待，驱动任务已进入上述嵌套配置路径。驱动就绪字始终为 1，
队列达到容量 60，仍有 `0x10326701` 待执行。单次等待有超时，
不能据末次栈位置宣称永久死锁；连续输入配置的同步缺口与队列积压
需要通过受控输入事件对照进一步确认。

整机探针的 `--input-boundary-events` 对照选项在原厂等待调用点
`0x102389c2` 检查请求掩码，只支持上述五项映射。只有 RAW DMA
计数相对上次提供事件时已推进、且所请求的输入原因全部已使能，
才通过输入引脚提供一组同步沿；逐项记录请求掩码、RAW 计数和
实际输入线。它不写入同步对象、驱动就绪字、应用事件或拍照门控，
也不把该对照当作已经实现所有输入通道的数据传输。

[首次边界对照](../../artifacts/processing_input_boundaries/report.json)
推进 4.181059 个计数器秒，处理 110 帧，执行了第二位回调及全局
通知分支；就绪字变为 3，门控变为零，全按也越过了门控检查。
本次第一组沿使用已完成的 RAW 批次 145，与观察前计数相同，
因此另做严格要求观察后新帧的对照，不将首组沿当作新帧证据。

[严格新帧对照](../../artifacts/processing_input_boundaries_fresh/report.json)
在批次 145 的首次等待未提供任何沿；从批次 151 开始、每次计数
推进后才提供事件，共 17 组。该窗口推进 0.804759 个计数器秒，
处理 9 帧，驱动就绪字同样变为 3、门控归零，末次队列仅 3 项，
四核无执行异常。全按发生在门控解除之前，其检查仍返回 1；
不能把这个结果当作实际拍摄已开始。

设备模型的 `frame-notify` 后续增加这些已使能的同步原因：只在
实际 RAW 写入成功后产生，银行 0 的新增位为 `0x18`，银行 3 为
`0x21`，银行 4 为 `0x80`，均按各自使能掩码过滤。它不写原厂
同步对象或软件就绪状态，也不声明辅助输出已经传输。五种输入
DMA/单色处理配置的检查覆盖掩码、确认、停止、失败传输无事件及
既有像素结果。模式 1 的两次诊断事件仍是独立的初始化实验条件。

`--shutter-on-ready` 与 `--shutter-on-preview` 是互斥对照：前者在
原厂显示提交、已有处理帧且门控实际为零时才全按。新增后续动作
资格与配置分发观察点，用于继续区分门控通过、拍摄请求和照片落盘。

## 新构建的原厂整机确认

[模型同步原因整机记录](../../artifacts/processing_native_boundaries/report.json)
不启用 `--input-boundary-events`。这些同步原因由新构建设备模型在
真实 RAW 写入后产生；模式 1 的两次初始化诊断事件仍保留。
本次等待状态 4 用时 7.031 个宿主秒，观察推进 3.524495 个计数器秒，
RAW 计数从 6 增至 104，处理完成 91 帧，四核无执行异常。

原厂执行第二位回调、全局就绪通知，状态字变为 3，应用门控自然归零。
在已处理 29 帧、门控实际为零的显示提交点全按，门控检查也返回零。
末次驱动队列计数为零。保存栈仍可采样到输入同步等待，但这次存在
持续帧处理且无队列积压，不能仅凭相同栈位置继续认定任务阻塞。

LCD 最终使用 `0xdd088800/0xdd1b5c00`。完整 Y 平面为 698368 字节，
仅含 16 和 235，摘要为
`15bae3184a9d50e0ec0549770a0fa196df141ffd65b87a990e9a63602723d23d`。
该结果确认模型完成输入同步并持续交付已有单色预览。

全按后的动作资格函数 `0x105548ca` 返回 `0x100`，随后进入
`0x104e16b4` 的配置分发。原厂上下文字节 `0xb202c017` 仍为零，
`0xb202c97a` 从零变为 2，捕获状态仍为 `(2,0)`。
此处需要继续追踪实际拍摄请求；不能将资格返回值直接命名为拒绝，
也不能把门控解除或配置分发等同于曝光、编码或照片落盘。
