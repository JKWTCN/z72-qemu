# 驱动双位就绪与全局通知

解除拍照门控的 `0x0410000d` 有一条独立于操作 13 请求槽的生产路径。
此前观察到 `0xb23f6a7c` 与 `0xb23f7018` 为零，不能据此认定全局
就绪通知必须等待操作 13 的异步请求。以下控制流与执行契约修正该推断。

| 入口或状态 | 原厂行为 |
| --- | --- |
| `0x1031dd62` | 将驱动 `0xb1868af0 + 0x78` 按位或 1 |
| `0x10326700` | 将同一状态字按位或 2，并调用两个本地控制入口 |
| 两个入口更新后的状态恰为 3 | 经驱动全局回调 `+0x48` 发送 `0x04160003`，负载为零 |
| 总路由 `0x103ed470` 的 `0x103ed7ac` 分支 | 经 `0xb18695a0 + 0x0c` 的全局回调发送 `0x0410000d` |
| 同一总路由分支 | 将后续入口 `0x103ecf8d` 入队 |

这两个驱动入口的顺序不影响最终通知；状态已经是 3 时再次进入也会
发送通知，不能把它解释为仅在状态发生变化时发送。缺少相应全局回调
时不会发送通知。

输入族全局通知包装 `0x1022594e` 形成 `0x04160000 | index`；
捕获族全局包装 `0x102282ba` 形成 `0x04100000 | index`。
后者与此前调查的按操作回调包装 `0x102282b4` 是不同入口。
应用将 `0x0410000d` 映射为事件 1，再由既有事件消费路径清除
`0xb1821e84` 的拍照门控，见[机身快门](body_shutter.md)。

控制流还定位到第一个就绪位的上游：通知入口 `0x10321a4c` 收到
`0x04190040`，经 `0x10322666` 将 `0x1031dd63` 入队。
请求包装 `0x1038e7b8` 将操作与通知码、调用者回调一起放入
`0xb21e26c0` 队列，唤醒任务 `0xb21e2654` 的事件 `0x10`。
后台工作函数 `0x1038e2ec` 在对应操作执行后调用所保存的回调。
初始化内部有 `0x43140000/0x43140001` 请求及等待；这些地址与码族
尚不足以判定设备身份或认定它是整机当前阻塞点。

第二个位来自另一条通知：`0x10327976` 收到 `0x041b0040`，经
`0x103281b2` 将 `0x10326701` 入队。执行契约使用零负载确认了
两条上游通知各自的入队目标。[分阶段快门记录](../../artifacts/processing_staged_shutter/report.json)
的末次工作队列确实含有 `0x10326701`，同时队列计数达到容量 60。
这证明该窗口中已有第二位的待执行回调，不能继续将其上游通知
缺失作为唯一解释；需检查驱动任务执行队列的实际进展。

`tools/capture_global_ready_probe.py` 使用本地 C 1.70 原厂映像执行
上述两个就绪入口和总路由。合成状态覆盖各初值 0、1、2、3，以及
总路由全局订阅存在/缺失两种情况；操作 13 请求和回调始终保持零。
[执行记录](../../artifacts/capture_global_ready_contract/report.json)
验证了就绪位合并、通知码及后续入队目标。宿主边界只记录通知和队列，
隔离就绪后的本地记账与两个控制入口；不包含固件字节。

该合同不代表整机自然产生了这两个就绪位，也不代表已完成照片。
整机探针新增两个就绪入口、全局发送点和后台初始化等待点，并只读
采样驱动状态字、两级全局订阅者及后台状态。下一步应据实际命中和
状态值确定缺失的生产者或未执行的回调，不能直接写入就绪字、门控或应用事件。
