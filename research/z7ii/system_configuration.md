# Z7 II C 1.70 系统配置首批写入

本阶段根据原厂主从固件分析，从 EG 入口连续执行过 `0x394`，验证系统配置
第一批 58 次字写入，停在首次状态轮询调用前。偏移为 EG 文件偏移，执行地址
为 `0x10020000 + 偏移`。原厂指令和页表保持不变。

| 路径 | 配置入口 | 停止偏移 | 轮询例程 |
| --- | --- | --- | --- |
| master | `0x4C6C` | `0x4E40` | `0x8D4` |
| slave，选择字位 2 为 0 | `0x361C` | `0x37F0` | `0x920` |
| slave，选择字位 2 为 1 | `0x4CB8` | `0x4E8C` | `0x920` |

slave 先将 `0x0428242C` 的位 2 置位，保留其他位，再读取 `0x0428202C` 的
位 2 选择路径。两个地址不同，不能将前一次写入当成后一次读取的反馈。
零复位值是实验配置，尚未确认实际硬件默认选择哪条路径。

三条路径写入相同的 57 个独立配置字；`0x20022000` 先写 1，再写 0。
slave 位 2 为 0 的路径对 `0x200300B8` 写 1、对 `0x2002010C` 写 `0x101`；
其他两条路径分别写 3、`0x303`。完整顺序和数值保存在
`analyze/system_configuration.py`。地址落在 `0x20020000..0x20030910`，
不能据此断定内存控制器的型号、实际配置生效条件或状态反馈时序。

主板总计支持 63 个独立配置字：之前的四个早期配置字、两个 slave 分支字，
以及本批 57 个字。两个稀疏容器只映射这些四字节位置，容器内空洞仍会触发
访问异常。每个字支持对齐小端 32 位访问、机器复位清零和状态序列化。
状态格式升级到版本 2，不兼容先前仅四字的设备快照；整机迁移仍未验证。
当前实现只保存配置值，没有模拟内存控制器、时钟或就绪反馈。

```sh
python tools/system_boot_probe.py --master /path/to/eg1840_mas_01700.bin --slave /path/to/eg1840_sla_01700.bin --qemu .build/build/qemu-system-arm --destination .local/system-boot-run
```

每个角色执行原厂零复位场景、配置字预先污染为 `0xDEADBEEF` 的场景，以及
使 `0x200` section 无效的负对照。slave 另执行位 2 置位的分支场景。
预置数据只影响独立实验实例，不修改输入固件。检查包括：

- 原厂调用者分支和配置入口，58 次写入的地址、值、顺序及逐次读回。
- slave 分支字的读改写保留和选择字保持不变。
- 临时 SRAM 中的两层栈保存、配置例程返回地址以及原厂页表保持不变。
- 无效 section 在首次系统写入触发各自原厂数据异常向量。
- 两块主板所有 63 个字的合成读写和复位清零，以及未支持访问的异常。
