# 机身 VR 成员(Body VR / NikonBVR)结构

分析固件与随包成员确定了 `vr1840_010100` 成分的身份与完整布局。
该成员不是引擎固件,与引擎引导窗口或更新摘要的密钥材料无关。

## 身份

- 主控固件的更新枚举字符串把该类文件称为 **"BobyVR"**(机身 VR);
  卡上单成员文件名为 `VR1840??.BIN`(类别 3)。
- 该成员只出现在带机身防抖(IBIS)的机型包内:Z7 II 包有,无 IBIS
  的 Z30 包没有——与"机身防抖单元"一一对应。
- 成员负载按页重建后是一个独立的 **RX 控制器**映像，目标地址从
  `0xFFF00000` 起、按 256 字节页连续递增。启动入口 `0xFFF00010`
  能连续解释为寄存器保存、控制寄存器设置、外设初始化和 COPY/ZERO
  表遍历；搬运后的应用入口与调用目标相符。
- 先前按 ROM 地址和大端指令命中比例作出的 FR 判断撤回。地址窗口
  和随机编码命中率不能替代连贯控制流、数据引用与搬运表的验证。
  指令编码核对使用 [RX 指令集手册](https://www.renesas.com/en/document/mas/rx-family-rxv2-instruction-set-architecture-users-manual-software)
  （R01US0071EJ0100，Rev.1.00，2013-11-12）；具体 MCU 型号尚未确定。

结论:**vr1840 = 机身防抖(VR/IBIS)单元自带控制器的闪存映像**,
主控通过串行接口与它通信，更新时另行按页转写。

## 容器与页格式

成员(去掉末尾 2 字节容器 CRC)由 0x106 字节的定长记录组成:

| 记录 | 布局 |
| --- | --- |
| 记录 0(头) | `[04 01][四个 16 位字段][NikonBVR 标签]` 后接零填充;原厂字段为 `04 00 00 01 01 00`(与文件名中的 0101.00 版本对应) |
| 记录 1..N | `[04 01][u32 小端目标地址][256 字节页数据]` |

页地址 0x100 对齐且逐页 +0x100;原厂成员 3200 页覆盖
`0xFFF00000..0xFFFC8000`(800 KiB 闪存窗口),其中约 495 页有内容
(约 120 KiB 代码与数据),其余为 0xFF 擦除态填充。主控对独立
VR 文件只做成员 CRC 检查并记录指针/长度(类别 3 走独立成员路径,
不经过整文件摘要检查),随后按页转写。

## 重建映像的内容分布

| 区域 | 内容 |
| --- | --- |
| `0xFFF00010` 起 | RX 启动代码，包含外设初始化和应用段搬运 |
| `0xFFF00C00..0xFFF00C9B` | 13 条 COPY 记录，每条为小端源起点、源终点、目标地址 |
| `0xFFF00C9C..0xFFF00CF3` | 11 条 ZERO 记录，每条为小端起点、终点 |
| `0xFFF00CF4..0xFFF010F3` | 搬至 `0x162D0` 的中断向量表 |
| `0xFFF01400..0xFFF1ED11` | 应用代码及初始化数据，按 COPY 表分段搬运 |
| `0xFFFC7C00..0xFFFC7FFF` | 搬至 `0x39C00` 的 DTC 向量表；槽 108、109、212 分别指向 `0x160FC`、`0x1611C`、`0x1613C` |

应用最大的搬运段为 `[0xFFF029B8,0xFFF1D8C7)` → `0x166D0`。
下文应用地址均指搬运后的地址，不能把整幅映像简单减去 ROM 基址。
完整表、成员摘要和核对范围见[静态核对记录](../../artifacts/body_vr_protocol/validation.json)。

## 原始成员的执行边界

启动代码在 COPY/ZERO 后，于 `0xFFF00167` 读取 `0xFFFC8008` 的
函数指针，随后间接调用。该地址超出成员上限 `0xFFFC8000`，
不能从这个更新成员恢复驻留实现。此处是静态依赖证据；本轮没有运行
RX 原厂固件，也没有取得原厂控制器生成回复的运行记录。

不能以补 `rts`、全零高地址页或固定回复代替缺失的驻留环境。

本地提供的 12 个历史更新包也已逐一核对目录、全部成员 CRC 和包 CRC。
机身固件 1.01 至 1.30 携带 VR 1.00，1.31 至 1.70 携带 VR 1.01；
同组成员摘要完全相同，共两种 VR 成员。所有成员上限均为
`0xFFFC8000`，均未提供 `0xFFFC8008` 槽。这个结果只覆盖更新包，
不说明相机实机没有驻留程序。各包及成员摘要见
[历史成员清单](../../artifacts/body_vr_protocol/historical_members.json)。

## 正常 SPI4 通信的设备侧消费者

重建应用的 `0x175D1` 配置 SCI5，基址 `0x8A0A0`；DMA0 源为
接收寄存器 `0x8A0A5`，DMA1 目标为发送寄存器 `0x8A0A3`。
初始化发送窗口为 276 字节。`0x17D2D` 处理片选边沿并重装 DMA，
`0x177C3` 分发接收命令。GPIO 片选边界与 SPI 开始/停止不能混用。

| 命令 | 原厂消费者和已核对的行为 |
| --- | --- |
| `F1` | `0x1786C` 解析标志、长度、键和地址；`0x180EB` 分阶段校验并将载荷复制到目标段 |
| `F1`，标志 4 | `0x179DE` 选择 `0xA4000` 基址，长度须不大于 256；主控 `0x103B86EC` 将 66 字节载荷及校验写入请求 |
| `F2`，标志 0 | `0x17A1C` 解析读取范围；`0x17ADD` 安排 `0x17EA8`，由后者从请求指定的数据段生成回复 |
| `F2`，标志 1 | 命令分发保留普通收尾；不进入标志 0 的读取初始化路径 |
| `D0` | `0x17C61` 仅将标志 1 请求排入控制队列；其他标志走普通收尾，不能简单回显命令字当作应答 |

`F1`/`F2` 的长度字段均包含 16 字节附加区，实际数据量需减去 16。
`F2` 请求中的填充零不是向控制器写入零数据；主控 `0x103B847E`
只构造读取头，设备端另行填充读取结果。`F1` 的校验与复制分阶段执行，
不能收到命令头就宣布数据处理完成。

带镜头拍摄时的 [SPI4 越界复制](lens.md) 仍需一个具备片选、缓冲区、
长度、数据和状态语义的对端。这些静态入口尚不等于可用的设备实现，
也未验证防抖执行器或传感器行为。

## 复现

`analyze/body_vr.py` 校验并描述本地提供的 VR 成员(记录数、地址
窗口、内容页数、头字段);`checks/test_body_vr.py` 用合成成员覆盖
接受与拒绝路径。对原厂成员的描述输出:3201 条记录、基址
0xFFF00000、窗口上限 0xFFFC8000、3200 页中 495 页有内容。

## 与更新流程的关系

该成员经过的检查只有容器 CRC;菜单更新对它没有整文件摘要(类别
3 不进 `0x37C638`)。因此它既不携带也不需要 K8;对 K8 的追踪仍以
加载器更新文件或引擎引导窗口为准(见
[菜单固件更新](firmware_update.md) 的排除记录)。
