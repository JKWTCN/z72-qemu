# 播放返回拍摄：操作 19 与重新初始化

本页接续[播放停止链](playback_stop.md)。目标仍是有效 LCD 实时像素与
拍照写入；以下记录只定位重新初始化路径，不代表功能已完成。
地址为 C 1.70 master 运行地址，文件偏移减去 `0x10020000`。

## 返回路径先进入空闲应用，再等待采集重新初始化

[首次返回追踪](../../artifacts/playback_return_trace/report.json)确认，
半按后 `0x1062e474` 收到来源 `0xb1828108`、请求 `0x00010001`。
`0x106ddc1e` 的目标为 `0xb181d8a4`，即 `APPIDLE`，并非直接启动
`APPLV`。静态分发器对请求高半字 `0x1` 选择空闲应用 getter
`0x104377b4`；`0x10` 才选择拍摄应用 getter `0x1053cf34`。

该通知函数把来源信息写入目标上下文，随后通过来源上下文的
`+0x24` 回调处理切换事件。因此，仅命中通知写入不能证明目标的
主入口已运行。拍摄应用的线程主入口实际为 `0x1053cfb8`，由对象
`0xb181d9b8 + 0x34` 指向；此前观察的 `0x10540770` 是后续界面入口。

[委托追踪](../../artifacts/playback_return_delegate/report.json)取得
以下实际调用链：

| 层次 | 原厂执行证据 |
| --- | --- |
| 操作 19 API `0x103f261a` | 回调 `0x10632f0d`，返回地址 `0x1063324b` |
| 原厂任务入口 `0x103ef390` | 内部请求 10、参数 1，进入 `0x103e7312` |
| 驱动 `0x10323198` | 原状态 12，请求目标 7，迁移到状态 13 |
| 驱动初始化 `0x10322886` | 参数 1，返回点 `0x103234b2` 的结果为 1 |
| 处理任务 `0x10397c16` | 收到事件 `0x1000`，命令字节置为 `0x0b` |
| `0x10397526` | 经 `0x1026d7be` 发布配置及唤醒后续委托 |
| 委托 `0x1026c6cc` | 接收事件位 0，委托状态置为 3 |
| `0x1026c26a → 0x102d7238` | 进入采样配置 |

观察结束时，采集状态为 `(5,0)`，驱动为 13，处理状态为 2，
委托状态为 3；操作 19 槽 `0xb23f7030` 仍为 `0x10632f0d`，控制字段
`0xb23f6a90` 为 `0x13ec`。这些字段尚不能独立说明具体等待原因。
不能把本次请求称为操作 13、14 或 15，也不能套用菜单退出后曾经
观察到的空闲应用重复请求路径；本窗口没有命中该重复请求点。

## 配置确认成功，资源确认等待失败

该长窗口用 300 个宿主秒只推进约 3.913 个计数器秒。
以下时刻相对半按前快照，按公告 48 MHz 计算：

| 计数器秒 | 实际返回或通知 |
| --- | --- |
| 0.047488 | 委托等待对象 `0xb18685c0` 位 4，参数 3000 |
| 0.047489 | `0x1026c708`，前一等待返回 1 |
| 0.047489 | 同对象等待掩码 `0x10a00000`，参数 200、诊断标签 `0x15` |
| 0.248096 | `0x1026c37c` 广播 `0x04200181`，参数 `(21,3,0x10a00000)` |
| 0.248097 | `0x1026c71e`，前一等待返回 0 |

输入配置成功确认的生产者可静态连接为：
`0x1022fca6 → 0x1023ad8e → 0x1023abaa`，返回非零时在
`0x1022fcfc` 调用 `0x103981f6 → 0x1026dba6`，设置上述位 4。
本次实际等待返回成功，不能将停留归因于这一确认缺失。

后一个掩码关联资源通知处理器 `0x1026d534`：通知 `0x04400048`
携带对象编号 `0x47`、`0x0b`、`0x50` 时，分别置位
`0x10000000`、`0x00800000`、`0x00200000`。它们合成
`0x10a00000`。订阅由 `0x1026d608..0x1026d64a` 经
`0x103c039c` 登记，不能把这些资源对象号当成同步中断位号。

## 后续采样序列与执行异常检查

[执行与资源快照](../../artifacts/playback_return_faults/report.json)
进一步命中 `0x102d9780(0) → 0x102d93a2`。随后：

- `0x102d949e` 等待对象 `0xb18a764c` 位 8、参数 50，返回 1；
- `0x102d950c` 的内部计数器完成等待返回 1；
- `0x102d954c` 的第二次内部计数器完成等待也返回 1。

两次计数器等待使用包装器 `0x103610da`，其返回包装固定为 1，
到达调用续行点才是本次证明等待已经返回的直接证据。不能仅凭
常量返回值推断内部事件数据或完整采样运行成功。

四个引擎核心在前后快照中的 `DFAR_S`、`IFAR_S`、`DFSR_S`、
`IFSR_S` 均为零。末次指令位置在各自内核等待代码中，尚未定位
后续究竟等待哪个对象；这些检查不能推广为所有执行路径均无异常。
末次延时通道运行位为 `0x20`；第 7 通道已停止，计数为 `0x12`。
这不支持把已观察到的两次计数器续行解释为该通道永久没有完成。

## 资源对象、存储输入与剩余验证

对象表 `0xb185eb70` 每项 28 字节。前后快照读取结果相同：

| 对象 | 缓冲地址 | 长度 | 存储组 | 订阅状态字 |
| --- | --- | --- | --- | --- |
| 11 | `0x50300000` | `0x24fff8` | 11 | 0 |
| 71 | `0xb7e6e000` | `0xd2000` | 23 | 0 |
| 80 | `0xb7d00000` | `0x16e000` | 32 | `0x1ac` |

订阅状态字来自 `0xb20a3288 + 对象号 * 48 + 0x28`，对象 11、71
的订阅者数分别为 1、2。`0x04400048` 对应订阅位 `0x20`，
对象 80 有此位，另两项没有。缓冲地址非零不等于加载已经完成，
单凭此快照尚不能区分未发起读取、读取失败或后续验证未完成。

原始存储区域表给出：组 11 起点 `0x12a80000`、备用
`0x12e60000`、区域大小 `0x260000`；组 23 起点
`0x13420000`、区域大小 `0xe0000`；组 32 起点
`0x13e80000`、区域大小 `0x180000`。区域容量与对象有效长度应分开。
交互台当前显式提供组 17、18、32 的实验输入；组 32 只是资源头，
不能当作完整采样参数。尚未验证其他存储输入的正确内容与加载过程。

### 从复位观察资源读取

[资源读取记录](../../artifacts/capture_resource_reads/report.json)从复位
同时监视普通读取、重新读取及各自的主区/备用区返回点。对象 80
主区读取返回 1；对象 71 主区读取返回 0；对象 11 备用区读取返回
`0xffffffff`。三项各观察到五次，结果一致。本窗口没有重新读取
入口命中，结束时原厂拍摄前台已就绪。

主区读取 `0x102a80a8` 以非零表示接受；备用区读取 `0x102a80f2`
以非负表示接受。因此这里能确认 11、71 的读取失败，而不能把
备用区返回 0 误判为失败。失败的底层原因及正确存储输入仍待定位。

## 资源等待失败后仍发出启动完成通知

[采样与委托完成记录](../../artifacts/playback_return_completion/report.json)
使用前述实验停止事件完成回放切换，再观察返回路径；240 个宿主秒
推进约 3.208 个计数器秒。资源等待失败后，`0x102d97fc` 采样运行
返回 0，`0x1026c732` 收到同一返回值。随后 `0x1026c766` 发出
`0x04200102`、参数 0，实际进入处理通知回调 `0x10394762`。

委托类型字节 `0xb1868511` 为 1。`0x1026c73c` 的跳转表对类型
0、1、2、4、5 直接进入 `0x1026c75c`；类型 3 及越界值才执行
`0x1026c758` 的最终等待。因此 `0x1026c75c` 是汇合点，命中它
不能当成最终等待曾经执行或成功返回的证据。

通知 `0x04200102` 经 `0x1039491e → 0x103949fc → 0x10394bb6`
设置处理任务 `0xb23ecc80` 的事件 `0x2000`。本次启动选择的处理
分支是 `0x10399ff6`，它调用 `0x10397526` 后的续行地址为
`0x1039a006`；应继续观察该分支，而非套用冷启动另一选择器分支
`0x1039a062` 的结果。

操作 19 仍未完成，处理命令仍为 `0x0b`。资源读取失败是独立需要
处理的问题，但不能再据此认定采样启动没有返回。当前输入几何
仍为零，快门门控为 1，没有有效取景像素或照片写入证据。

## 输出触发响应已越过原来的等待

[自动握手记录](../../artifacts/playback_return_automatic_handshake/report.json)
启用 `input-handshake`，关闭观测点 GPIO 脉冲；回放停止仍使用实验
停止事件。进入返回路径前，字段 `0xb1868334`、适配层模式与活动
字段均为 0。返回时未进入 `0x10395a88`，而是按该字段的选择直接
越过旧等待，在相对半按 0.016527 秒到达输出配置续行。

`0x10395158` 的输出准备在 0.016539 秒返回 1，
`0x10395052` 的参数生成随后也返回 1，并进入 `0x1039a03c`。
本次观察进一步排除了这两项配置尚未返回的判断。

600 个宿主秒只推进 2.679874 个计数器秒。处理分支末尾仍未命中，
采样配置已进入、尚未进入委托等待位 4 的后续部分。操作 19 仍
挂起，应用仍为 `APPIDLE`，四核执行异常寄存器均为零。

延时块快照中第 4 通道运行、事件配置 9、终止值 0、分频值 49，
状态位 0 保持挂起。这对应旧模型每微秒重复一次的计时路径。
原厂对此输出计时器还配置了目标次数 1，相关寄存器与限次模型
见[延时计数器](delay_counter.md#有限次数配置与输出计时器)。
本记录完成于限次修复之前；后续运行需检查该通道的完成次数、
定时器调用续行以及采样配置是否继续推进。
